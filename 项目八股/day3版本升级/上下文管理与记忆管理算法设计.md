# 上下文管理与记忆管理算法设计

本文基于当前仓库真实源码，讲解 agent 管线的统一上下文管理（Context Manager）与记忆管理（会话持久化 + 长期记忆）的算法流程与工程取舍。

范围说明：

- 分析当前版本的 `rag_modules/context_management.py`、`rag_modules/memory.py`、`rag_modules/agentic_rag.py`、`rag_modules/generation_integration.py`、`main.py`、`api/app.py`、`config.py` 及相关测试。
- 演算示例中的 token 数为按 tiktoken cl100k_base 构造的说明性数字，非逐字节实测。
- 所有 A/B 实验数字来自 `.artifacts/eval/` 真实报告（2026-08-30）。

---

## 一、先建立直觉

改造前的 agent 管线，上下文是"拼"出来的：

```text
改造前
  question = 对话历史前缀（固定最近 4 轮 × 120 字符）+ 当前问题
  context  = 检索父文档按 6000 字符顺序拼接（首篇超长拦腰截断，后排整体丢弃）
```

三个问题：① 对话历史无预算概念，抢的是 question 的空间而不是独立预算；② 上下文只有一种来源（检索），一旦加入记忆，"谁该被保留、谁被牺牲"没有任何机制；③ 字符预算与模型真实的 token 口径脱节，截断位置不可控。

改造后：

```text
改造后（Context Manager 管道）
  三类来源 → ContextItem 列表
      conversation（对话轮次，最新优先保留）
      retrieval  （检索父文档，带【食谱 N】引用头）
      memory    （用户偏好，软约束注入）
          ↓ 按 (priority, order) 分配 token 预算
          ↓ 超限确定性降级：P3 丢弃 → P2 截断 → P1 保留/兜底截断
          ↓ 语义去重（cosine > 0.93）
      FinalContext（渲染顺序与分配顺序分离）
          ↓
      LLM
```

记忆侧同样分层：会话历史（SessionStore，SQLite 持久化，替代进程内存 dict）与长期记忆（MemoryStore，结构化偏好 + 写入策略 + 冲突 supersede + 衰减）分离，检索出相关记忆后以 memory 类型 ContextItem 进入同一管道。

核心直觉：**上下文管理是"多源调度问题"，记忆管理是"写入治理问题"**——前者解决"有限预算里谁留下"，后者解决"什么值得记、记了之后怎么更新"。

## 二、总体框架

```text
                      用户提问（携带 session_id / user_id）
                                ↓
                    ┌───────────────────────┐
                    │  Query Contextualizer  │  history 非空时 LLM 消解指代
                    │  "那第二种呢" → 独立查询 │  （RAG_QUERY_CONTEXTUALIZATION）
                    └───────────┬───────────┘
                                ↓
                         Agent Router（function calling 选工具）
                                ↓
                    检索（Milvus hybrid + expr 下推）
                                ↓
        ┌───────────────────────────────────────────────┐
        │              Context Manager                  │
        │                                               │
        │  conversation ← SessionStore 历史轮次          │
        │  retrieval    ← parent 文档（【食谱 N】头）     │
        │  memory       ← MemoryStore 召回的偏好条目      │

        │  token 预算 → 优先级分配 → 降级 → 去重 → 渲染    │

                            ↓
                      generate_basic_answer(context_text=...)

                            ↓

                │  → SQLite（supersede/TTL）  │
                └───────────────────────────┘
```

## 三、Context Manager 算法详解

### 3.1 ContextItem 数据结构（逐字段）

```python
@dataclass
class ContextItem:
    content: str          # 最终进入 prompt 的文本（渲染直接使用，不再二次加工）
    source_type: str      # conversation | retrieval | memory
    priority: int         # 预算优先级：retrieval=1, conversation=2, memory=3（越小越优先）
    order: int = 0        # 同优先级内的分配顺序；conversation 最新轮次取 0
    truncatable: bool = True   # 是否允许部分截断（retrieval 仅首篇允许）
    item_id: str = ""     # trace/统计中的标识（如 retrieval:1, conv:3）
    metadata: dict = field(default_factory=dict)
```

设计要点：

- **`priority` 与 `order` 分离**：priority 决定"预算紧张时哪类先牺牲"，order 决定"同类内谁先保留"；
- **conversation 的 order 取反向**：构造时最新一轮 `order=0`，预算紧张时最新上下文优先保留（旧轮次先牺牲）；
- **retrieval 仅首篇 `truncatable=True`**：对齐 `_build_context` 的"至少保留首篇一部分"行为，其余篇目整条保留或整条丢弃——避免语义碎片。

### 3.2 token 计数

```python
try:
    _ENCODING = tiktoken.get_encoding("cl100k_base")   # ragas 依赖已带入，零新增
except Exception:
    _ENCODING = None

def count_tokens(text):
    if _ENCODING: return len(_ENCODING.encode(text))   # 首次需联网下载编码表
    return max(1, int(len(text) * 0.85))               # 中文经验估算降级
```

截断同理：`_truncate_to_tokens(text, max_tokens)` 用 `encode → 切片 → decode` 精确截断，tiktoken 不可用时按字符估算截断。

### 3.3 build() 主算法（六步）

```text
输入：items（调用方按展示顺序构造）、budget_tokens（默认 6000）、image_paths
输出：ContextResult(context=最终字符串, stats={input_items, input_tokens,
      final_tokens, dropped, truncated})

Step 1  input_tokens = Σ count_tokens(item.content)
Step 2  去重：精确内容去重（strip 后相同）；提供 embeddings 时再做语义去重
        （截取前 2000 字符嵌入，cosine > 0.93 的后到项丢弃）
Step 3  分配：按 (priority, order) 升序遍历，贪心装箱
        - 剩余预算足够        → 整条保留
        - 超预算且 memory      → 整条丢弃（偏好缺失不致命）
        - 超预算且 conversation→ 截断到剩余预算（remaining > 50 才截，否则丢）
        - 超预算且 retrieval   → 首篇截断到剩余，非首篇整条丢弃
Step 4  兜底：一条都没保留 → 截断第一条可截断项至 max(budget//2, 200)，
        对齐 _build_context"至少保留首篇一部分、避免空上下文"的行为
Step 5  渲染：按调用方传入顺序（时间序/引用序），不是分配序——
        对话块在最前（【对话历史（供理解指代用，回答只针对当前问题）】）
        → 检索文档逐篇（保持【食谱 N】引用序）
        → 记忆块最后（【用户偏好（回答时必须遵守）】）
        → 图片区块【相关图片】（若有，格式与 _build_context 一致）
        分隔线 = "\n" + "="*50 + "\n"；全部为空 → "暂无相关食谱信息。"
Step 6  stats = {input_items, input_tokens, final_tokens, dropped[], truncated[]}
        经 AgentState.context_stats → QueryTrace 事件 context_built 上报
```

### 3.4 演算示例（按源码算法构造）

预算 `budget_tokens = 300`，输入四条（token 数为构造值）：

| item | source | priority | order | tokens | truncatable |
|---|---|---|---|---:|---|
| A | conversation（最老轮次） | 2 | order=3 | 120 | ✓ |
| B | conversation（次新） | 2 | order=1 | 80 | ✓ |
| C | conversation（最新） | 2 | order=0 | 60 | ✓ |
| D | retrieval【食谱 1】 | 1 | order=1 | 150 | ✗ |
| E | retrieval【食谱 2】 | 1 | order=2 | 90 | ✗ |
| F | memory"对花生过敏" | 3 | order=0 | 20 | ✓ |

分配过程（按 (priority, order) 排序：D(1,1)、E(1,2)、C(2,0)、B(2,1)、A(2,3)、F(3,0)）：

```text
D: 150 ≤ 300-0   → 保留，used=150
E: 90  ≤ 300-150 → 保留，used=240
C: 60  ≤ 300-240 → 保留，used=300
B: 80  > 0       → conversation 可截断但 remaining=0 ≤ 50 → 丢弃
A: 120 > 0       → 同上丢弃
F: 20  > 0       → memory → 丢弃
```

结果：`kept={D,E,C}`，`dropped=[A,B,F]`，`final_tokens=300`。渲染按传入顺序：对话块只含最新轮次 C（时间序），检索 D、E 保持【食谱 1】【食谱 2】引用序，记忆 F 消失。**这就是"最新对话优先保留、记忆先牺牲、检索保底"的直觉在算法上的体现。**

### 3.5 与既有路径的对齐关系（兼容性设计）

| 对齐点 | 处理 |
|---|---|
| 首篇部分保留 | retrieval 首篇 `truncatable=True` + build() 的空结果兜底截断 |
| 【食谱 N】引用序 | retrieval item 的 content 自带与 `_build_context` 完全相同的头格式，与 `format_citations` 的序号对齐 |
| 图片区块 | build(image_paths=...) 复刻 `_build_context` 的【相关图片】追加 |
| 空上下文 | "暂无相关食谱信息。"文案一致 |
| classic 零改动 | `generate_basic_answer` 新增 `context_text=None` 旁路参数：传入时跳过 `_build_context`；classic 调用点不传，行为逐字节不变（有单测锁定：同一 prompt 两种断言） |

### 3.6 接入点（agent 管线）

```python
# agentic_rag.py _generate_node（双分支）
if self.context_manager is not None:
    items = build_agent_context_items(history, parents, memories=state.get("memory_items"))
    built = self.context_manager.build(items, image_paths=state.get("image_paths"))
    state["context_stats"] = built.stats                      # 进 trace
    state["events"] += [_event("context_built", **built.stats)]
    answer = generation_module.generate_basic_answer(
        state["question"], parents, image_paths=..., context_text=built.context)
else:
    question = self._history_prefix(history) + state["question"]   # 原路径
    answer = generation_module.generate_basic_answer(question, parents, ...)
```

构造入口 `build_agent_context_items(history, parents, memories)`：conversation 取最近 6 轮、每轮一条、最新 order=0；retrieval 每篇一条；memories 每条 dict → `- {content}（{type}）` 文本。

开关：`RAG_CONTEXT_MANAGER`（`config.context_manager_enabled`，默认 true——A/B 验证后翻转），`RAG_CONTEXT_BUDGET`（默认 6000）。false 时走原路径，保证可回退对比。

### 3.7 A/B 实测（45 条 agent 臂，2026-08-30）

| 指标 | CM 关闭 | CM 开启 | Δ |
|---|---|---|---|
| faithfulness | 0.9209 | 0.9168 | -0.004（噪声级） |
| answer_relevancy | 0.8491 | 0.8522 | +0.003 |
| answer_correctness | 0.6846 | 0.6900 | +0.005 |
| context_precision | 0.8656 | 0.8660 | +0.000 |
| context_recall | 0.7737 | 0.7372 | -0.037（整篇丢弃 vs 字符部分保留的语义差异，已记录） |

**结论：生成质量持平（这是一次架构投资而非指标投资），同时为记忆注入提供统一载体。**

## 四、Memory 算法详解

### 4.1 数据模型与存储

```python
@dataclass
class MemoryRecord:
    memory_id: str        # uuid4 hex[:16]
    user_id: str          # JWT sub（认证时）或 session_id
    type: str             # allergen | diet_preference | taste_preference | constraint
    key: str              # 冲突匹配键（有规范，见 4.4）
    value: str            # 结构化值
    content: str          # 注入 prompt 的自然语言表述
    importance: float     # 0-1
    confidence: float     # 0-1
    created_at: str       # ISO
    expires_at: str|None  # TTL（constraint 类常有）
    status: str           # active | superseded
    supersedes: str|None  # 被本条替换的旧记忆 id
```

`SQLiteMemoryStore` 两张表：

```sql
sessions(session_id PK, messages JSON, updated_at)        -- 会话历史
memories(memory_id PK, user_id, type, key, value, content,
         importance, confidence, created_at, expires_at,
         status, supersedes)                              -- 长期记忆
-- 索引 idx_memories_user(user_id, status)
```

**为什么 SQLite 而不是 PostgreSQL/Redis**：记忆量级为每用户个位数条，策略层（写入门槛/冲突/衰减）才是考点；SQLite 标准库零运维，WAL 模式 + 单锁保证 FastAPI 多线程安全。`SessionStore`/`MemoryStore` 是 Protocol——迁移到英语平台项目（Gin + MySQL 栈）时新写 `MySQLMemoryStore` 实现，上层策略代码零改动。

**user_id 的来源**：`principal.subject or body.session_id`——认证时用 JWT sub（跨会话身份），开发模式用客户端传入的 session_id。

### 4.2 会话持久化流程（SessionStore）

```text
save_turn(session_id, question, answer):
    读 messages → append user+assistant（assistant 截 400 字符）
    → del messages[:-12]        # 保留最近 6 轮
    → UPSERT 回表

load_history(session_id):
    SELECT → JSON 反序列化 → list[dict]；无记录返回 []
```

替换了原 API 层的 `app.state.sessions` 内存 dict（重启即失、多实例不可用）；`load_history/save_turn` 函数签名不变，读写异常降级（读失败按无历史、写失败跳过，不影响主回答）。测试用例验证了**跨 store 重开持久化**与**12 条裁剪边界**。

### 4.3 写入策略算法（Write Policy）

```python
def apply_write_policy(candidates):
    for c in candidates:
        过滤 temporary=True                        # "今晚想吃面" → 不写
        过滤 type ∉ {allergen, diet_preference,
                     taste_preference, constraint}  # 非法类型
        过滤 key/content 为空
        过滤 importance < 0.6 或 confidence < 0.6
        规范化后保留
```

四道闸的语义：**临时性**（一次性需求不留痕）、**类型合法**（枚举收口）、**字段完整**（防 LLM 半截输出）、**双阈值**（防低价值记忆稀释注入）。每道闸都有多轮评测用例锁定（temporary_not_written / memory_write_allergen）。

### 4.4 冲突 supersede 算法

```python
add_memory(record):
    查同 (user_id, type, key) 且 status=active 的旧记录
    若存在：UPDATE 旧记录 status='superseded'
            record.supersedes = 旧 memory_id
    INSERT 新记录（status='active'）
```

**key 规范是 supersede 生效的前提**——第一版评测暴露了 LLM 两次抽取的 key 不一致（"辣" vs "微辣"）导致冲突检测失效（superseded=0, active=2），修复方式是在抽取 prompt 中写死 key 规范：

| type | key 规范 |
|---|---|
| allergen | 过敏原名称（如"花生"、"海鲜"） |
| taste_preference | 固定"口味"，value=具体偏好 |
| diet_preference | 固定"饮食方式" |
| constraint | 固定"当前约束"，value=约束内容 |

配套判断标准也写进 prompt：稳定偏好 importance/confidence ≥0.8 必须记；阶段性约束（"最近在减脂"）temporary=false 且给 expires_days；一次性需求 temporary=true。

### 4.5 衰减与召回排序算法

```python
recency_score(created_at, now) = 2 ^ (-age_days / 30)      # 30 天半衰期
score(record, question) = importance × recency × (1.8 if 命中问题 else 1.0)
命中判定：key / value / content[:20] 任一是 question 的子串
rank_memories = 按 score 降序
```

演算示例（构造值）：

| 记忆 | importance | created_at | recency | 问题命中 | score |
|---|---|---|---|---|---|
| M1 花生过敏（90 天前） | 0.9 | -90d | 2^(-3)=0.125 | ✓("花生" in query) | 0.9×0.125×1.8=0.203 |
| M2 花生过敏（今天） | 0.9 | now | 1.0 | ✓ | 0.9×1.0×1.8=1.620 |
| M3 喜欢清淡（今天） | 0.8 | now | 1.0 | ✗ | 0.8 |

query="花生能吃什么" → 排序 M2 > M3 > M1：新鲜的同主题记忆优先，未命中的偏好居中，陈旧记忆沉底。TTL 独立于衰减：`expires_at` 过期的记录在 SQL 层就被过滤（`active_memories` 的 WHERE 条件），不进入排序。

### 4.6 召回与注入流程（ask_agent 内）

```text
ask_agent(question, role, query_id, history, user_id)
  ↓ memory_enabled 且 user_id 非空
  store.active_memories(user_id)                    # SQL 过滤 active + 未过期
  rank_memories(active, question)[:3]               # 最多注入 3 条
  → memory_items = [{"content": ..., "type": ...}]
  → trace.event("memory_recalled", count=3)         # 有记忆才发事件
  ↓ agent.invoke(..., memory_items=memory_items)
  _generate_node：memory_items → ContextItem(memory) → ContextManager
  ↓ 回答完成
  remember_turn(store, extractor, user_id, question, answer)
      extract（LLM）→ apply_write_policy → add_memory（含 supersede/TTL）
  → trace.event("memory_written", count=n)          # 失败静默
```

设计原则：**记忆是软约束注入而非硬过滤**——语料元数据没有食材/过敏原字段，Milvus expr 硬过滤需要重建索引（如实标注为未来项）；召回失败/抽取失败全部静默跳过，记忆故障不影响主回答；`RAG_MEMORY_ENABLED` 可整体关闭。

### 4.7 指代消解流程（Query Contextualizer）

```text
_route_node：路由判定为 search_recipes 且 history 非空且开关开启
    ↓ _contextualize_query(question, history)
    prompt = 结合最近 4 轮对话，把追问改写为独立完整、适合菜谱检索的查询
    （消解指代，补全菜品名/食材/烹饪方式），只输出改写后查询
    ↓ state["standalone_query"] = 改写结果 + event("query_contextualized")
_act_node：search_recipes 的查询取 standalone_query 优先，
    其次路由 LLM 给的 query，最后原始 question
```

与既有 `_rewrite_query` 的关系：后者只在**检索 0 命中**的 reflect 兜底触发一次；contextualizer 是**首轮检索前**的主动消解——两者覆盖不同失败模式，互不替代。LLM 调用失败静默返回空串（回退原始问题）。多轮用例实测："那第二种需要哪些食材"消解为含"红烧鱼头"的查询并检回目标。

### 4.8 隐私端点

`GET /api/memory`（列出全部含 status）、`DELETE /api/memory/{memory_id}`、`DELETE /api/memory`（清空）——user_id 解析同上，未认证且无 session_id 返回 400。这是计划 P2.8 的最小集。

## 五、记忆评测算法（run_memory_eval.py）

断言体系与检查方式详见《RAGAS 评测体系与自动化流水线》第六节，此处只列算法要点：

- 每回合快照 `store.list_memories(user_id)` 前后对比，写入/未写入/supersede 全部用 **store 状态**断言（不依赖 LLM 判断"是否写了"）；
- 指代消解用 **trace 事件内容**断言（`query_contextualized.query` 包含目标菜名）；
- 约束遵守用 **LLM 判分**（≥4 通过，judge 与主链同源的限制已在评测篇声明）；
- 运行时强制特性开启 + 每次独立临时 SQLite 库（可复现、不污染业务库），`--case` 单用例调试，`--keep-db` 保留库供检查。

首轮 7 组跑分 2/7，暴露评测器事件未合并、prompt key 不规范、用例菜名不在语料三类问题，逐条归因修复后 **7/7**——评测自身的迭代过程见 RAGAS 篇 6.3。

## 六、关键参数

| 参数 | 默认 | 说明 |

## 七、收益 / 代价 / 已知边界

**收益**

- 多轮能力从零到一：指代消解 + 会话持久化，行为用例可验证；
- 记忆四机制（写入门槛/冲突更新/时效/隐私）全部有用例锁定；
- 上下文从"字符串拼接"升级为可观测管道（input/dropped/final tokens 进 trace）；
- classic 链路零改动（单测锁定 context_text 旁路的两种行为）。

**代价**

- 每轮 agent 回答增加最多 2 次 LLM 调用（指代消解 + 记忆抽取），失败静默但有延迟；
- context_recall 微降 0.037（整篇丢弃语义）；
- SQLite 单机存储，多副本部署需换 Store 实现（接口已预留）。

**已知边界（诚实记录）**

- 过敏原**硬过滤**未实现：需要语料增加食材元数据并重建 Milvus 索引，当前为软约束注入；
- 会话摘要（summary）字段已建但摘要压缩策略未启用（当前按 6 轮窗口裁剪）；
- 语义去重的 cosine 阈值 0.93 未做扫描调优（bge 下不同菜谱很少超过）；
- tiktoken 离线降级路径（编码表不可用）有代码但未在测试中强制覆盖。

## 八、面试口述版本（约 90 秒）

> 我给 agent 管线做了一层统一的上下文管理。改造前对话历史是固定四轮硬拼进 question、检索文档按字符顺序拼接，两类来源没有预算概念。改造后所有来源抽象成 ContextItem——对话、检索、记忆三类，按优先级分配 token 预算：检索是 P1 整条保留、对话 P2 可截断且最新轮次优先、记忆 P3 超限先丢；分配顺序和渲染顺序是分离的，保证引用序号和时间序不被破坏。生成了 context_stats 进 trace，上下文第一次变得可观测。
>
> 记忆分两层。会话层把 API 进程内存 dict 换成 SQLite 持久化，重启可恢复。长期记忆做了领域化——记忆类型就是饮食偏好：过敏原、饮食方式、口味、阶段性约束。写入有四道闸：LLM 抽取时判临时性，写入策略过滤低重要度，同 user+type+key 的新记忆会 supersede 旧记忆，阶段性约束带 TTL 且检索时按 30 天半衰期衰减排序。注入是软约束——作为 memory 类型 ContextItem 进 Context Manager，失败静默不影响主回答。
>
> 验证是两层：RAGAS A/B 证明生成质量持平（faithfulness 0.921 对 0.917）；七组多轮行为用例 7/7——指代消解命中正确菜品、过敏原写入并跨会话生效、口味变化正确 supersede、一次性需求正确不写。另外这轮 A/B 还抓出一个 env 默认值与字段默认值不一致的配置 bug——grounding 被静默关闭导致 faithfulness 异常，逐 case 归因才暴露，这也验证了"配置治理要进评审"这件事。

## 九、源码事实边界

当前源码可以确认：

- ContextItem/ContextManager/build 算法、降级顺序、渲染格式如上（`rag_modules/context_management.py`）；
- 记忆存储两张表结构、supersede 事务、衰减公式、写入策略四道闸（`rag_modules/memory.py`）；
- agent 双分支接线、`context_text` 旁路、指代消解事件、记忆召回/写入的 trace 事件（`agentic_rag.py`/`main.py`）；
- API 会话委托与三个记忆端点（`api/app.py`）；
- A/B 数字与 7/7 用例来自 `.artifacts/eval/` 报告。

需要保留的边界：

- 演算示例中的 token 数为构造值；
- `context_stats` 只进 trace 与 state，未持久化到评测报告（run_ragas_eval 的 records 未包含该字段）；
- 会话 summary 字段与过敏原硬过滤属"已建接口/未启用策略"，不应描述为已实现的能力；
- tiktoken 计数对中文的实际比率未做基准测量，降级估算 0.85 为经验值。
