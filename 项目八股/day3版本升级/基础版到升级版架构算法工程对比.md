# 基础版 → 升级版：架构、算法与工程变化

> 分析对象：当前仓库中的可见旧版与当前版，而不是根据典型 RAG 项目推测。
>
> - Baseline：`config_old.py`、`main_old.py`、`rag_modules_old/`
> - Upgrade：`config.py`、`main.py`、`api/`、`rag_modules/`、`eval/`、`tests/`
> - 结论时间：2026-08-28

---

## 0. 先给结论：哪些说法需要纠偏

从仓库可见版本差异看，不能简单把这个项目概括为“Dense RAG 升级成 Hybrid RAG”。旧版已经包含 Dense、BM25、RRF、Query Router、Query Rewrite、Metadata Filter 和 Parent-Child Retrieval。

更准确的升级主线是：

```text
可运行的单机教学型 RAG
    ↓
中文检索适配 + 可切换向量后端 + 服务端混合检索/过滤
    ↓
确定性索引、权限、图片、引用、可观测、评测等工程加固
    ↓
在相同 Retrieval Stack 上增加可选的 Agentic 编排
```

因此，面试时应区分三类变化：

1. **旧版已有、升级版加固**：Hybrid、RRF、Parent-Child、Query Rewrite、Metadata Filter。
2. **升级版真实新增**：中文 BM25 分词、Milvus、过滤下推、图片摄取、Reranker 实验、Agent、Observability、Backend Abstraction、Citation/Provenance、认证与权限、系统化评测。
3. **实验存在但不应声称带来收益**：Reranker 默认关闭；Agent 评测没有优于 Classic；图片检索没有数值效果评测。

### 全局对比

| 维度 | 可见 Baseline | Upgrade | 判断 |
|---|---|---|---|
| 运行形态 | CLI 单进程 | FastAPI + CLI，支持 SSE、JWT、会话 | 工程升级 |
| 检索 | FAISS Dense + 本地 BM25 + RRF | FAISS 中文 BM25；Milvus Dense + server-side BM25 + RRF | 算法适配 + 系统升级 |
| Metadata Filter | FAISS 召回后过滤 | Milvus filter pushdown；FAISS 扩池后过滤 | 检索架构升级 |
| Parent-Child | 已存在 | 确定性 ID、版本信息、快速 parent lookup | 工程加固，不是首次引入 |
| 图片 | 无 | Vision Caption 转文本后进入同一检索体系 | 新增能力 |
| Reranker | 无 | 可选 Cross-Encoder；评测后默认关闭 | 实验型算法升级 |
| Query 编排 | 固定 Classic 流程 | Classic 保留，新增 LangGraph Agent | 编排层升级 |
| 可观测 | `print` 为主 | QueryTrace JSONL + 可选 LangSmith | 工程升级 |
| 向量库 | 代码绑定 FAISS | `VectorStoreBackend` 抽象，FAISS/Milvus 双后端 | 架构升级 |
| 引用 | Prompt 回答，无确定性来源附录 | 确定性来源附录 + Agent 结构化 citations | 可信度工程升级 |
| 索引持久化 | FAISS pickle 风险、缺少版本校验 | JSON 文档映射、Manifest、哈希、原子写入 | 可靠性升级 |
| 评测 | 无系统评测 | 73 条检索集 + LLM Judge + Reranker 消融 | 方法论/工程升级 |

# 一、重点升级逐项分析

## 1. Dense → Hybrid：这不是当前可见版本之间的真实升级

### 1. Baseline 原来怎么做

旧版已经是 Hybrid Retrieval：

- 文件：`rag_modules_old/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 函数：`__init__()`、`hybrid_search()`、`_rrf_rerank()`
- Dense：`vectorstore.as_retriever(search_kwargs={"k": 5})`
- Sparse：`BM25Retriever.from_documents(child_chunks)`，`k = 5`
- Fusion：两路结果交给 `_rrf_rerank()`，以排名而不是原始分数融合。

`main_old.py::RecipeRAGSystem.ask_question()` 已经调用 `retrieval_module.hybrid_search()`。

### 2. 原来有什么问题

- BM25 使用 LangChain 默认预处理，对没有空格的中文句子适配较差。
- 两路候选数固定为 5，可配置性弱。
- 与 FAISS 类型强绑定，无法把混合检索和过滤交给服务端执行。
- 文档去重用 `MD5(page_content)`，内容相同但来源不同的文档会被视为同一个结果。
- 只有本地、内存内融合，数据规模和并发能力有限。

### 3. Upgrade 改成了什么

升级版保留 Dense + BM25 + RRF 的主思路，但改为两种执行路径：

- FAISS：本地 Dense + 使用 `tokenize_chinese()` 的 BM25 + `_rrf_rerank()`。
- Milvus：Dense ANN 与服务端 BM25 两路 `AnnSearchRequest`，由 Milvus `RRFRanker(60)` 融合。
- `candidate_k`、`top_k` 等候选规模进入统一配置；客户端 RRF 使用 `RAGConfig.rrf_k`。
- 去重优先使用 `child_id`，而不是仅依赖正文哈希。

### 4. 代码在哪里体现

- `rag_modules/retrieval_optimization.py`
  - `tokenize_chinese()`
  - `RetrievalOptimizationModule._build_client_retrievers()`
  - `RetrievalOptimizationModule.hybrid_search()`
  - `RetrievalOptimizationModule._rrf_rerank()`
- `rag_modules/vector_store.py`
  - `MilvusVectorStore.hybrid_search()`
- `config.py::RAGConfig.candidate_k`、`RAGConfig.rrf_k`、`RAGConfig.top_k`

### 5. 解决了什么问题

- 保留语义召回能力，同时改善中文精确词、菜名和食材词召回。
- 支持在 Milvus 内完成两路检索与融合，减少应用侧全量状态依赖。
- 配置化候选池，为 Recall、Latency 和重排实验提供调节入口。

### 6. 带来了什么代价

- 需要维护 FAISS 客户端融合和 Milvus 服务端融合两套行为。
- 两个后端的分词器、索引和检索细节不完全一致，结果不能保证完全等价。
- Hybrid 至少执行两路检索，计算量和排障维度高于纯 Dense。
- 当前 Milvus 路径在 `MilvusVectorStore.hybrid_search()` 中写死 `RRFRanker(60)`，没有读取上层传入的 `RAGConfig.rrf_k`；因此修改 `RAG_RRF_K` 只会影响客户端 RRF 和 CE/Recall 二次融合，不会改变 Milvus 第一次服务端融合。这是一个真实的配置一致性缺口。

### 7. 是算法优化还是工程优化

旧版已经有 Hybrid 算法。当前变化主要是**中文算法适配 + 后端执行架构优化**，不是从无到有引入 Hybrid。

### 8. 有没有可能复杂度增加但收益有限

有。如果语料很小、用户问题主要是语义描述、精确关键词并不重要，BM25 和双路融合可能只增加延迟。FAISS 与 Milvus 两套路径还可能产生行为漂移。

### 9. 如果有评测证据，列出来

当前检索基线产物：`.artifacts/eval/retrieval_eval_20260823-122239.json`，73 条、Milvus、`top_k=5`：

- `hit_rate = 1.0`
- `overall_mrr = 0.9315`

但这只是升级版 Hybrid 管线的绝对结果，并没有与“纯 Dense”在同一数据集上做 A/B。因此：**源码未提供 Dense → Hybrid 因果收益的评测证据**。

### 10. 最终判断

这是有价值的检索能力，但简历不能写成“把旧版 Dense 升级成 Hybrid”。更严谨的说法是：

> 在旧版已有 Hybrid 的基础上，完成中文 BM25 适配，并把混合检索扩展为 FAISS 客户端融合与 Milvus 服务端融合两种执行模式。

## 2. 中文 BM25

### 1. Baseline 原来怎么做

`rag_modules_old/retrieval_optimization.py::RetrievalOptimizationModule.__init__()` 直接调用：

```python
BM25Retriever.from_documents(child_chunks)
```

没有传入中文预处理函数，依赖 LangChain/`rank_bm25` 默认的 whitespace split。

### 2. 原来有什么问题

中文自然句通常没有空格。例如“宫保鸡丁怎么做”可能被视为一个长 token，而不是“宫保鸡丁”“怎么做”等可匹配单元。精确菜名、食材和烹饪动作的词项匹配能力因此受限。

### 3. Upgrade 改成了什么

FAISS 路径新增 `tokenize_chinese(text)`，产生：

- 小写后的英文/数字 token；
- 单个汉字；
- 相邻中文二元组；
- 不超过 8 个汉字时的完整中文短语。

Milvus 路径把正文设为启用 analyzer 的 `VARCHAR`，通过 BM25 Function 生成 sparse field，并依次尝试 `jieba`、`chinese`、默认 analyzer。

### 4. 代码在哪里体现

- `rag_modules/retrieval_optimization.py::tokenize_chinese()`
- `rag_modules/retrieval_optimization.py::RetrievalOptimizationModule.setup_retrievers()`
- `rag_modules/vector_store.py::MilvusVectorStore._build_schema()`
- `rag_modules/vector_store.py::MilvusVectorStore._create_collection()`

### 5. 解决了什么问题

让中文精确菜名、食材、难度词等在 Sparse Retrieval 中产生稳定匹配信号，并与 Dense 的语义信号互补。

### 6. 带来了什么代价

- 单字、二元组和短语会增加 token 数量和本地 BM25 内存占用。
- 单字 token 可能带来噪声和高频词误匹配。
- FAISS 自定义 tokenizer 与 Milvus analyzer 并非同一个分词实现，后端结果可能不一致。

### 7. 是算法优化还是工程优化

以**算法适配**为主，同时包含 Milvus schema/index 的工程实现。

### 8. 有没有可能复杂度增加但收益有限

有。如果 Query 和文档主要是英文、已经有明确空格，中文 tokenizer 的价值有限；如果短文本中大量汉字共现，单字和二元组也可能提升无关文档排名。

### 9. 如果有评测证据，列出来

- `tests/test_retrieval_optimization.py` 对中文 token 生成和精确菜名检索提供功能性回归测试。
- 73 条检索集包含 `exact_dish_name` 等 Query，升级版总体 Hit@5 为 1.0。

但没有“默认 whitespace BM25 vs `tokenize_chinese`”的独立数值消融。因此：**源码未提供中文 tokenizer 单独提升多少的评测证据**。

另外，Milvus 会尝试多种 analyzer；静态源码不能确认某次部署最终采用哪一个，必须查看实际建表日志或 schema。

### 10. 最终判断

这是小而实用、符合中文 RAG 场景的真实算法升级，技术价值高于“只是接入 BM25”的表述。

## 3. FAISS → Milvus

### 1. Baseline 原来怎么做

- 文件：`rag_modules_old/index_construction.py`
- 类：`IndexConstructionModule`
- 函数：`build_vector_index()`、`save_index()`、`load_index()`

旧版只支持本地 FAISS：文档向量在单进程内构建，索引保存到本地目录后再次加载。

### 2. 原来有什么问题

- 与单机进程、内存和本地磁盘绑定。
- Metadata Filter 无法在 ANN 搜索前下推。
- BM25 语料和 FAISS 索引由应用进程维护，不利于扩容与多实例共享。
- 旧版 `load_local(..., allow_dangerous_deserialization=True)` 有 pickle 反序列化风险。
- 缺少索引与当前语料/模型配置的一致性校验，可能加载陈旧索引。

### 3. Upgrade 改成了什么

- `RAGConfig.backend` 默认选择 `milvus`，仍保留 `faiss` 作为本地回退。
- Milvus collection 同时存储 dense vector、sparse vector、正文和标量 metadata。
- Dense 使用 HNSW/COSINE，Sparse 使用 BM25/SPARSE_INVERTED_INDEX。
- Collection 支持 partition key、标量索引、服务端 Hybrid Search 和 filter expression。

### 4. 代码在哪里体现

- `config.py::RAGConfig.backend`、Milvus 相关配置项
- `rag_modules/vector_store.py::MilvusVectorStore`
  - `_build_schema()`
  - `_create_collection()`
  - `build_index()`
  - `similarity_search()`
  - `hybrid_search()`
- `main.py::RecipeRAGSystem.initialize_system()`
- `main.py::RecipeRAGSystem.build_knowledge_base()` 中的 `backend == "milvus"` 分支

### 5. 解决了什么问题

- 把索引、ANN、BM25 和标量过滤放到专业向量数据库中执行。
- 支持更大语料、持久化、多进程/多服务实例共享和过滤下推。
- 为权限隔离、图片/文本 modality 过滤和服务端 RRF 提供基础。

### 6. 带来了什么代价

- 新增 Milvus 部署、连接、Collection 生命周期、兼容性和运维成本。
- 服务端 analyzer、Function、索引参数依赖 Milvus 版本。
- 网络调用使错误类型、延迟波动和故障面扩大。
- 双后端意味着测试矩阵翻倍。

### 7. 是算法优化还是工程优化

主要是**系统与工程架构升级**。HNSW、服务端 BM25 和 RRF 改变了执行方式，但“拥有 Hybrid Retrieval”的算法思想旧版已经存在。

### 8. 有没有可能复杂度增加但收益有限

有。当前菜谱语料若规模很小，FAISS 的本地速度和简单性可能已经足够；没有并发、共享索引、权限过滤需求时，Milvus 的部署成本可能大于收益。

此外，FAISS Manifest 会绑定 embedding 模型、revision、归一化、维度和 chunking version；Milvus Manifest 当前只记录 collection、语料 fingerprint 和文档数，模型配置校验反而更弱。

### 9. 如果有评测证据，列出来

Milvus 管线在 73 条检索集上取得 Hit@5=1.0、MRR=0.9315。`tests/test_vector_store.py` 提供 schema、BM25、过滤和 hybrid 调用的功能测试。

但是仓库没有同一语料下 FAISS 与 Milvus 的 Recall、P95 latency、吞吐、内存和构建时间对比。因此：**源码未提供 FAISS → Milvus 性能收益的评测证据**。

### 10. 最终判断

如果目标是生产化、权限过滤、多实例和未来扩容，这项升级值得；如果目标只是小规模本地 Demo，则可能过度工程化。

## 4. Filter Pushdown

### 1. Baseline 原来怎么做

`rag_modules_old/retrieval_optimization.py::metadata_filtered_search()`：

1. 先调用 `hybrid_search(query, top_k * 3)`；
2. 再在 Python 中检查 `category`、`difficulty`；
3. 过滤后截断到 `top_k`。

这属于 post-filter。

### 2. 原来有什么问题

如果真正符合条件的文档没有进入前 `top_k * 3` 个候选，后处理无法把它找回来。这不只是浪费计算，还会降低过滤 Query 的 Recall。

旧版也没有 role/visibility 权限过滤。

### 3. Upgrade 改成了什么

- Milvus：把白名单 metadata 条件转换为 expression，并附在 Dense 和 Sparse 两个 `AnnSearchRequest` 上，在候选排序前过滤。
- FAISS：仍然只能 post-filter，但候选数扩为 `min(语料量, max(candidate_k, top_k * 5))`。
- `main.py::RecipeRAGSystem._visibility_expr_for_role()` 根据角色生成 `visibility` 条件，并与 Query Router 提取的业务 filter 合并。

### 4. 代码在哪里体现

- `rag_modules/vector_store.py::build_filter_expr()`
- `rag_modules/vector_store.py::MilvusVectorStore.hybrid_search()`
- `rag_modules/retrieval_optimization.py::RetrievalOptimizationModule.metadata_filtered_search()`
- `rag_modules/retrieval_optimization.py::RetrievalOptimizationModule.metadata_filtered_search()` 内的 `candidate_count` 计算
- `main.py::RecipeRAGSystem._visibility_expr_for_role()`
- `main.py::RecipeRAGSystem.ask_question()`

### 5. 解决了什么问题

- Milvus 只在满足类别、难度、visibility、modality 等条件的集合中排序。
- 改善严格过滤条件下的有效候选 Recall。
- 权限限制进入 Retrieval 层，不依赖生成后再隐藏内容。

### 6. 带来了什么代价

- 需要安全地维护可过滤字段白名单、值转义和不同后端语义。
- FAISS 仍不是严格等价实现；候选池再大也不能保证找回所有过滤目标。
- 扩大候选池增加 Dense/BM25 排序、RRF 和可选 Reranker 成本。

### 7. 是算法优化还是工程优化

属于**检索执行架构优化**，同时会影响 Recall，不能只当作性能优化。

### 8. 有没有可能复杂度增加但收益有限

如果 metadata 条件很少、过滤比例低、语料小，pushdown 的质量收益可能不明显；但 visibility 属于安全约束，即使性能收益有限也有工程必要性。

### 9. 如果有评测证据，列出来

73 条检索集包含：

- `browse` 18 条；
- `permission_allowed` 5 条；
- `permission_denied` 5 条。

升级版整体 Hit@5 为 1.0，测试也覆盖 filter expression 与权限行为。

但没有 Milvus pushdown 与 FAISS post-filter 的严格 A/B。因此：**源码未提供 filter pushdown 单独带来多少 Recall/Latency 提升的评测证据**。

### 10. 最终判断

这是生产 RAG 中非常有价值的升级，尤其适合讲“为什么权限必须在召回阶段生效”。但要诚实说明 FAISS 只是扩大候选池近似补偿，不是同等语义的 pushdown。

## 5. Parent-Child Retrieval：算法模式旧版已有，升级的是可靠性

### 1. Baseline 原来怎么做

- `rag_modules_old/data_preparation.py::DataPreparationModule.load_documents()` 和 `chunk_documents()` 已经生成 parent document 和 child chunk。
- `rag_modules_old/data_preparation.py::DataPreparationModule.get_parent_documents()` 已经按 child 命中的 `parent_id` 恢复 parent。
- `main_old.py::RecipeRAGSystem.ask_question()` 已经执行“检索 child → 恢复 parent → 构造答案”。

旧版 parent ID 是相对路径的 MD5；child ID 使用随机 UUID。

### 2. 原来有什么问题

- 随机 child ID 导致同一语料重建后 ID 改变，不利于增量索引、复现和引用。
- `get_parent_documents()` 为每个 parent ID 扫描 `all_documents`，查找效率较低。
- 缺少 `source_hash`、`revision_id`、`chunking_version` 等可追踪信息。
- Chunk 失败的兜底文档可能保留 parent 的 `doc_type`，语义不够稳定。
- 相同 parent 下多个 child 命中后的排序和去重规则较粗。

### 3. Upgrade 改成了什么

- parent/child 改用 SHA-256 生成稳定 ID。
- metadata 增加 `source_hash`、`revision_id`、`chunking_version`、`source_path` 等。
- `_parent_documents` 字典提供按 `parent_id` 的 O(1) 恢复。
- `get_parent_documents()` 按 child 命中次数排序，并用首次出现位置稳定打破平局。
- 文本和图片都以 child 形式进入同一个 parent 恢复接口。

### 4. 代码在哪里体现

- `rag_modules/data_preparation.py::DataPreparationModule`
  - `_stable_id()`
  - `load_documents()`
  - `chunk_documents()`
  - `get_parent_documents()`
- `rag_modules/image_ingestion.py::ImageIngestionModule._build_chunk()`
- `rag_modules/data_preparation.py::DataPreparationModule.CHUNKING_VERSION`

### 5. 解决了什么问题

- 检索继续使用更细、主题集中的 child，提高匹配粒度。
- 生成恢复完整 parent，降低上下文残缺。
- ID 和版本稳定后，索引校验、引用、去重和问题定位更可靠。

### 6. 带来了什么代价

- parent 上下文通常比 child 长，增加 Prompt Token、LLM 成本和上下文竞争。
- 多个 child 可能恢复为同一个 parent，需要计数、去重和排序。
- 需要同时维护 parent 列表、child 列表、映射和 parent 字典。

### 7. 是算法优化还是工程优化

Parent-Child Retrieval 算法模式是**Baseline 已有能力**；当前版本主要做**确定性、效率与 provenance 的工程加固**。

### 8. 有没有可能复杂度增加但收益有限

有。对本身很短、一个 chunk 就能完整表达的文档，Parent-Child 只增加映射和上下文长度。当前 `parent_child_map` 仍被构建，但恢复主要依赖 child metadata 与 `_parent_documents`，存在一定重复状态。

### 9. 如果有评测证据，列出来

测试覆盖稳定 ID、映射、parent 恢复、顺序稳定和语料搬迁等行为。

但没有“直接用 child 生成 vs 恢复 parent 生成”的答案质量、Faithfulness、Token Cost A/B。因此：**源码未提供 Parent-Child 质量收益的数值评测证据**。

### 10. 最终判断

设计本身有价值，但不应作为当前版本“新发明”的升级点。真正可讲的是：把教学版的 Parent-Child 机制改造成可复现、可校验、可引用的工程实现。

## 6. Image Ingestion

### 1. Baseline 原来怎么做

`rag_modules_old/` 没有图片摄取模块；知识库只加载 Markdown 文本。

### 2. 原来有什么问题

菜谱仓库中的图片信息完全不参与检索，用户无法按图片内容、摆盘或图中菜品召回来源。

### 3. Upgrade 改成了什么

新增 `ImageIngestionModule`：

1. 扫描 jpg/jpeg/png/webp；
2. 跳过 Git LFS pointer 和过小文件；
3. 调用视觉模型生成中文 caption；
4. 将 caption 包装成 `Document`，标记 `modality=image`；
5. 生成稳定 `parent_id`/`child_id`；
6. 与文本 child 一起写入 FAISS 或 Milvus；
7. 用文件哈希、视觉模型和 Prompt 版本组成缓存键。

### 4. 代码在哪里体现

- `rag_modules/image_ingestion.py::ImageIngestionModule`
  - `ingest_images()`
  - `_caption_image()`
  - `_build_chunk()`
  - `_cache_key()`
- `main.py::RecipeRAGSystem._ingest_images()`
- `config.py::RAGConfig.enable_image_ingestion` 及 Vision 配置

### 5. 解决了什么问题

- 把原先不可搜索的图片转成可由现有文本 Embedding/BM25 检索的语义描述。
- 缓存避免每次建库重复支付视觉模型调用成本。
- 单张图片失败可降级，不必阻塞整套文本知识库。

### 6. 带来了什么代价

- 视觉模型调用带来网络延迟和费用。
- Caption 会丢失细粒度视觉信息，并可能产生幻觉。
- 图片变更、模型变更和 Prompt 变更需要正确失效缓存。
- 增加并发、错误恢复、LFS 检测和缓存文件维护复杂度。

### 7. 是算法优化还是工程优化

属于**检索模态扩展 + 工程实现**。它不是 CLIP 或原生多模态向量检索，而是“图片 → 文本 caption → 文本检索”。

### 8. 有没有可能复杂度增加但收益有限

有。如果用户几乎不问图片相关问题，或者图片只起装饰作用，视觉 caption 的成本和错误面可能大于召回收益。Caption 路线也无法可靠处理颜色、数量、版式等精细视觉条件。

### 9. 如果有评测证据，列出来

测试覆盖 caption 文档生成、缓存命中、失败降级、LFS pointer 跳过等功能。

没有图片 Query 的 Recall、Caption 准确率、成本或延迟数据。因此：**源码未提供 Image Ingestion 检索效果的评测证据**。

### 10. 最终判断

是有展示效果的新增能力，但面试时必须称为“caption-based image retrieval”，不能包装成真正的跨模态向量检索。

## 7. Reranker

### 1. Baseline 原来怎么做

旧版没有 Cross-Encoder。Dense 与 BM25 的结果经 RRF 后直接截断，再恢复 parent。

### 2. 原来有什么问题

Dense/BM25/RRF 主要解决候选召回与排名融合，但不能像 Cross-Encoder 一样联合阅读 Query 和候选正文，可能把表面相关但答案不匹配的文档排在前面。

### 3. Upgrade 改成了什么

- 新增可选 `BAAI/bge-reranker-base`。
- 只对 `rerank_pool` 个候选打分，而不是全库打分。
- 模型 lazy load，并支持 offline-first；未缓存时直接跳过，避免隐式下载。
- 当前实现不是纯 CE 排序，而是把 CE rank 与原始 recall rank 再做一次 RRF。
- 配置默认 `rerank_enabled=False`。

### 4. 代码在哪里体现

- `rag_modules/reranker.py::RerankerModule`
  - `_load_model()`
  - `rerank()`
- `rag_modules/retrieval_optimization.py::RetrievalOptimizationModule`
  - `_pool_size()`
  - `_apply_rerank()`
- `main.py::RecipeRAGSystem._build_reranker()`
- `config.py::RAGConfig.rerank_enabled`
- `config.py::RAGConfig.rerank_model`
- `config.py::RAGConfig.rerank_pool`

### 5. 解决了什么问题

提供二阶段精排能力，并通过 lazy/offline-first 避免默认启动时下载大模型。保留原召回排名再融合，也降低 CE 单模型误判把正确结果完全压下去的风险。

### 6. 带来了什么代价

- Cross-Encoder 对每个 Query-Document pair 前向计算，延迟明显增加。
- 新增模型内存、依赖、缓存和设备管理。
- CE rank + recall rank 再融合增加解释和调参复杂度。
- 如果训练域与菜谱语料不匹配，理论上更强不代表实际更好。

### 7. 是算法优化还是工程优化

属于**算法实验 + 防御性工程实现**。

### 8. 有没有可能复杂度增加但收益有限

不仅“可能”，本项目现有评测已经显示它没有超过基础 RRF。因此默认关闭是合理决策。

### 9. 如果有评测证据，列出来

同一套 Milvus、73 条、`top_k=5`：

| 方案 | 产物 | Hit@5 | MRR |
|---|---|---:|---:|
| RRF baseline | `.artifacts/eval/retrieval_eval_20260823-122239.json` | 1.000 | 0.9315 |
| 纯 Cross-Encoder | `.artifacts/eval/retrieval_eval_20260823-124424.json` | 1.000 | 0.8790 |
| CE rank + Recall rank RRF | `.artifacts/eval/retrieval_eval_20260823-130000.json` | 1.000 | 0.9018 |

结论：三种方案 Hit@5 相同，但 MRR 都没有超过原始 RRF；纯 CE 最差，二次融合有所恢复但仍低于 0.9315。

### 10. 最终判断

Reranker 代码本身不是亮点；**用消融评测证明它在当前语料上负收益，并据此默认关闭**才是亮点。这体现了不盲目堆模型的工程判断。

## 8. Classic → Agentic

### 1. Baseline 原来怎么做

`main_old.py::RecipeRAGSystem.ask_question()` 是固定 Classic Pipeline：

```text
query_router → 可选 query_rewrite → hybrid/metadata retrieval
→ child 恢复 parent → 按 route_type generation
```

需要注意：旧版已经有 Router 和 Rewrite，不是完全没有 LLM 决策。

### 2. 原来有什么问题

- 所有 Query 都被固定流程约束，无法自然选择“直接回答、图片检索、条件浏览、普通食谱搜索”等工具。
- 检索结果不足时没有结构化的反思、重写和有限重试环。
- 工具失败、检索失败、生成失败缺少分层降级策略。

### 3. Upgrade 改成了什么

在保留 Classic 的同时新增 LangGraph Agent：

- Node：`route`、`act`、`reflect`、`generate`。
- Tool：`search_recipes`、`search_images`、`list_by_metadata`、`direct_answer`。
- `route` 由 LLM 选择工具；失败时回退 `search_recipes`。
- `act` 执行工具，仍调用原 Retrieval Stack。
- `reflect` 判断结果是否充分，不足时重写并回到 `act`。
- `MAX_REWRITES = 1`，避免无界循环。
- 检索异常回退到 hybrid，生成异常回退到检索摘要。

### 4. 代码在哪里体现

- `main.py::RecipeRAGSystem.ask_agent()`
- `main.py::RecipeRAGSystem._get_agent()`
- `rag_modules/agentic_rag.py::RecipeAgent`
  - `_build_graph()`
  - `_route_node()`
  - `_act_node()`
  - `_reflect_node()`
  - `_generate_node()`
  - `_decide_after_reflect()`
- `rag_modules/agentic_rag.py::build_agent_tools()`

真实图中没有独立 `rewrite` node；Rewrite 发生在 `reflect` node 内部。

### 5. 解决了什么问题

- 根据 Query 选择不同检索场景或直接回答路径。
- 对低质量召回提供一次有界 rewrite/retry。
- 对路由、工具、检索和生成故障提供明确回退。
- 支持 recent history 进入 Agent 路由与生成上下文。

### 6. 带来了什么代价

- 一般需要额外的路由 LLM 调用；触发反思重写时还会增加调用与检索。
- 状态图、工具协议、JSON 解析和重试分支增加测试与排障复杂度。
- LLM 路由具有不稳定性，可能选错工具。
- 对明确需要普通 RAG 的 Query，Agent 很可能只是增加延迟和成本。

### 7. 是算法优化还是工程优化

主要是**系统编排和 Harness 工程升级**，不是替代 Dense、BM25、RRF、Milvus 的检索算法。

### 8. 有没有可能复杂度增加但收益有限

有，而且现有评测没有证明 Agent 的答案质量更强。项目把 Classic 保留为默认可选路径是合理的。

### 9. 如果有评测证据，列出来

`.artifacts/eval/judge_eval_20260823-064000.json`，仅 8 个样本：

| Pipeline | Faithfulness | Relevance |
|---|---:|---:|
| Classic | 4.875 / 5 | 5.0 / 5 |
| Agent | 4.75 / 5 | 5.0 / 5 |

这组小样本没有证明 Agent 优于 Classic，Agent 的 Faithfulness 反而略低。仓库也没有 Agent 与 Classic 的 P50/P95 latency、Token 和费用对比。因此不能声称“Agent 提高了答案准确率或降低了成本”。

测试能证明的是路由、direct answer、一次重试、失败降级和历史信息等控制流按预期工作。

### 10. 最终判断

Agent 的真实价值是细分场景、工具选择、有界重试和降级，而不是提高底层召回算法。适合作为可选高级编排层，不适合无条件替代 Classic。

## 9. Observability

### 1. Baseline 原来怎么做

旧版主要通过 CLI `print()` 展示初始化、路由、改写和检索过程，没有结构化、可查询的 Query 生命周期记录。

### 2. 原来有什么问题

- 出错后无法按 Query 还原执行链。
- 无法系统统计某个阶段的耗时、路由选择、过滤条件和候选数量。
- Classic、Agent、Search API 的行为缺乏统一审计信息。

### 3. Upgrade 改成了什么

新增 `QueryTrace`：

- 为 Query 生成短 `query_id`；
- 记录 pipeline、role、开始时间、elapsed、events、answer 和 error；
- 追加写入 JSONL；
- 提供读取近期 trace 的接口；
- 可选接入 LangSmith；
- Classic、Agent 和 Search 路径都写入 trace。

### 4. 代码在哪里体现

- `rag_modules/observability.py::QueryTrace`
  - `event()`
  - `finish()`
- `rag_modules/observability.py::append_trace()`、`load_traces()`
- `main.py::RecipeRAGSystem.ask_question()`
- `main.py::RecipeRAGSystem.ask_agent()`
- `api/app.py::create_app()` 内部的 `search()`

### 5. 解决了什么问题

支持按 Query 观察路由、改写、过滤、检索、parent 恢复、Agent 工具和异常，明显改善调试、审计和线上复盘能力。

### 6. 带来了什么代价

- 每次请求都有序列化和磁盘追加写开销。
- Trace 中可能包含完整问题、答案和工具参数，需要隐私与访问控制。
- 本地 JSONL 会持续增长，需要轮转和保留策略。

### 7. 是算法优化还是工程优化

纯**工程可靠性与可运维性升级**。

### 8. 有没有可能复杂度增加但收益有限

小型 Demo 中收益有限。当前实现仍不是完整生产 Observability：

- 线程锁只保护单进程，多 worker 追加并非完整事务方案；
- 没有脱敏、采样、日志轮转和指标聚合；
- 没有自动把检索质量异常转成告警。

### 9. 如果有评测证据，列出来

测试覆盖 trace 结束、异常、近期读取和 Agent 事件合并。

没有 MTTR、问题定位时间或运行开销对比。因此：**源码未提供 Observability 工程收益的数值证据**。

### 10. 最终判断

这是从 Demo 走向可维护服务的必要一步，但面试时应称为“轻量 Query Trace”，不要包装成完整的分布式可观测平台。

## 10. Backend Abstraction

### 1. Baseline 原来怎么做

- `rag_modules_old/index_construction.py` 直接返回 `FAISS`。
- `rag_modules_old/retrieval_optimization.py` 构造函数参数直接声明为 `vectorstore: FAISS`。
- 检索逻辑、向量库实现和 FAISS 类型耦合。

### 2. 原来有什么问题

切换向量库需要修改索引模块、检索模块和系统初始化逻辑；上层无法通过能力判断选择 client-side 或 server-side hybrid。

### 3. Upgrade 改成了什么

新增统一接口 `VectorStoreBackend`，核心契约包括：

- `build_index()`
- `add_documents()`
- `count()`
- `similarity_search()`
- `hybrid_search()`
- `supports_server_side_hybrid`

当前实现：

- `FaissBackend`
- `MilvusVectorStore`

`RetrievalOptimizationModule` 依赖接口能力，不再依赖具体 FAISS 类型。

### 4. 代码在哪里体现

- `rag_modules/vector_store.py::VectorStoreBackend`
- `rag_modules/vector_store.py::FaissBackend`
- `rag_modules/vector_store.py::MilvusVectorStore`
- `rag_modules/retrieval_optimization.py::RetrievalOptimizationModule`
- `main.py::RecipeRAGSystem.initialize_system()`

### 5. 解决了什么问题

- 隔离向量库差异。
- 上层可以按 backend capability 选择服务端或客户端 Hybrid。
- 保留轻量本地 FAISS，同时提供 Milvus 生产路径。
- 提升替换、Mock 和测试能力。

### 6. 带来了什么代价

- 需要设计最低公共接口，还要暴露 Milvus 特有能力。
- 不同后端并不能真正完全等价，抽象可能隐藏 analyzer、metric、filter 和持久化差异。
- 双实现、双配置和双测试路径增加维护量。

### 7. 是算法优化还是工程优化

典型的**架构与可维护性工程优化**。

### 8. 有没有可能复杂度增加但收益有限

有。如果项目永远只使用一种向量库，抽象层会变成额外跳转。当前 `FaissBackend.hybrid_search()` 与 `RetrievalOptimizationModule` 自己维护的客户端 Hybrid 也存在职责重叠迹象。

### 9. 如果有评测证据，列出来

`tests/test_vector_store.py` 和检索测试证明接口行为与分支可用。

没有维护成本、迁移时间或双后端一致性指标。因此：**源码未提供 Backend Abstraction 收益的数值评测证据**。

### 10. 最终判断

在确实需要 FAISS/Milvus 双后端时值得；其技术含量不在“写了抽象类”，而在上层基于 capability 正确选择执行路径，并承认两种后端语义不完全一致。

## 11. Citation / Provenance

### 1. Baseline 原来怎么做

`rag_modules_old/generation_integration.py` 把 parent 文本拼入 Context，由 LLM 生成答案，但没有确定性追加来源列表，也没有结构化 citation 返回。

### 2. 原来有什么问题

- 用户难以判断回答依据哪篇菜谱。
- LLM 即使拿到来源，也不保证稳定输出引用。
- 无法从答案追溯到 `source_path`、稳定 parent 或语料版本。

### 3. Upgrade 改成了什么

- `format_citations(docs)` 按 `dish_name` 和 `source_path` 确定性生成去重来源附录。
- 非流式和流式生成都在答案末尾追加来源。
- Prompt 鼓励使用 `【食谱 N】` 内联引用。
- Agent API 额外返回结构化 citation 列表。
- 文档 metadata 增加稳定 ID、相对来源路径、source hash 和 revision 信息。

### 4. 代码在哪里体现

- `rag_modules/generation_integration.py::format_citations()`
- `rag_modules/generation_integration.py::GenerationIntegrationModule._build_context()`
- `rag_modules/generation_integration.py::GenerationIntegrationModule.generate_basic_answer()`、`generate_step_by_step_answer()`
- `rag_modules/generation_integration.py::GenerationIntegrationModule.generate_basic_answer_stream()`、`generate_step_by_step_answer_stream()`
- `api/app.py::create_app()` 内部的 `ask()`：遍历 Agent 返回的 parents 组装 citations
- `api/schemas.py::AskResponse`
- `rag_modules/data_preparation.py::DataPreparationModule.load_documents()`、`chunk_documents()`

### 5. 解决了什么问题

- 至少能稳定说明答案使用了哪些检索文档。
- 支持用户核验、问题排查和来源展示。
- 稳定 ID/Hash 为后续语料版本追踪提供基础。

### 6. 带来了什么代价

- 来源附录占用输出 Token 和界面空间。
- 必须维护 metadata 完整性和路径稳定性。
- Classic 主要在答案字符串中携带来源，而 Agent API 才显式填充结构化 citations，接口表现存在差异。

### 7. 是算法优化还是工程优化

属于**可信度、可解释性和 provenance 工程升级**。

### 8. 有没有可能复杂度增加但收益有限

有。当前 citation 只证明“该文档被检索并放入上下文”，不证明“每条回答陈述被该来源蕴含”。错误召回或 LLM 误读仍会得到格式正确的引用；这不是 sentence-level citation verification。

### 9. 如果有评测证据，列出来

测试覆盖 citation 去重、空列表和 API 结构化返回。LLM Judge 给出了整体 Faithfulness，但没有做“启用引用前后”或引用正确率评测。

因此：**源码未提供 Citation Accuracy 或 Citation Faithfulness 的专项评测证据**。

### 10. 最终判断

这是实用的来源展示和追踪能力，但面试时不要把它描述成“已解决幻觉”或“实现逐句可验证引用”。

# 二、其他值得注意的工程升级

## 12. 索引持久化安全与可复现性

### 1. Baseline 原来怎么做

`rag_modules_old/index_construction.py::IndexConstructionModule.load_index()` 使用 `FAISS.load_local(..., allow_dangerous_deserialization=True)`；索引目录存在就尝试加载，没有验证语料、Embedding 配置和 chunking 版本。

### 2. 原来有什么问题

- pickle 反序列化存在供应链/本地文件篡改风险。
- 数据变了但目录还在时，可能静默使用陈旧索引。
- 随机 child UUID 使重建结果难以复现。

### 3. Upgrade 改成了什么

- FAISS 只持久化 index 和 JSON document map，不再加载危险 pickle。
- Manifest 绑定语料 fingerprint、文档数、Embedding model/revision、normalize、dimension、metric、chunking version。
- 索引与 JSON 文件记录 SHA-256 artifact hash。
- 使用临时文件/目录后原子替换。
- 当前 child ID 确定性生成。

### 4. 代码在哪里体现

- `rag_modules/index_construction.py::IndexConstructionModule`
  - `build_manifest()`
  - `save_index()`
  - `load_index()`
  - `_read_verified_manifest()`
- `rag_modules/data_preparation.py::DataPreparationModule._stable_id()`

### 5. 解决了什么问题

避免危险反序列化和陈旧索引静默复用，使同一语料与配置的建库结果可验证、可复现。

### 6. 带来了什么代价

Manifest、哈希、原子替换和兼容校验增加代码量；任何绑定配置变化都可能触发全量重建。

### 7. 是算法优化还是工程优化

纯**安全性、数据一致性与可复现性工程优化**。

### 8. 有没有可能复杂度增加但收益有限

本地一次性 Demo 中收益不直观；但对持续更新知识库的系统非常值得。需要注意 Milvus Manifest 当前校验维度少于 FAISS，双后端的一致性保障尚未完全对齐。

### 9. 如果有评测证据，列出来

测试覆盖 round-trip、语料顺序无关 fingerprint、内容变化失效、搬迁稳定和 artifact hash 校验。

这些是正确性测试，不是性能评测；**源码未提供其对故障率的数值证据**。

### 10. 最终判断

这是最容易被忽略、但最能体现工程成熟度的升级之一，简历价值很高。

## 13. Evaluation Harness

### 1. Baseline 原来怎么做

可见旧版没有系统化 golden set、检索指标脚本和答案 Judge 产物。

### 2. 原来有什么问题

无法回答“升级是否真的更好”，容易凭理论直觉开启 Reranker、Agent 或其他复杂组件。

### 3. Upgrade 改成了什么

### 4. 代码在哪里体现

- `eval/generate_golden_set.py`
- `eval/run_eval.py`
- `eval/run_judge.py`
- `.artifacts/eval/*.json`
- `README.md` 中的评测说明和结果表

### 5. 解决了什么问题

使技术选择从“理论更强”变成“在本语料、本 Query 分布上是否更好”。Reranker 默认关闭就是直接例子。

### 6. 带来了什么代价

需要维护数据集、预期 parent ID、Judge Prompt 和结果版本；LLM Judge 本身也有成本、随机性和偏差。

### 7. 是算法优化还是工程优化

属于**评测工程与研发方法升级**。

### 8. 有没有可能复杂度增加但收益有限

### 9. 如果有评测证据，列出来

这是直接承载评测证据的模块：

它不是用户可见功能，却是本项目最值得写进简历的升级之一。高级工程师的亮点不是“组件多”，而是知道哪些组件不该开启。

### 7. 是算法优化还是工程优化

### 8. 有没有可能复杂度增加但收益有限

API、认证、权限、SSE、DomainConfig 和 Session 均有功能测试。没有并发、吞吐、安全渗透和多实例一致性数据，因此：**源码未提供服务化性能与安全强度的评测证据**。

适合作为“从算法 Demo 到可调用服务”的工程背景，不应包装成 RAG 算法创新。

# 四、A. 最值得写进简历的 5 个升级点

## 亮点 1：Milvus 服务端 Hybrid + Metadata/Visibility Pushdown

推荐表述：

> 将单机 FAISS 检索扩展为可切换的 FAISS/Milvus 双后端；在 Milvus 中使用 Dense、BM25 Sparse 与 RRF 服务端融合，并将类别、难度、模态和角色可见性条件下推到候选生成前，避免 post-filter 导致有效候选被提前截断。

为什么值得：它同时体现 Retrieval、数据库执行位置、Recall 与权限边界的理解。

证据边界：73 条评测 Hit@5=1.0、MRR=0.9315，但没有 FAISS/Milvus 性能 A/B。

## 亮点 2：评测驱动的 Reranker 取舍

推荐表述：

> 搭建 73 条检索评测和 Reranker 消融，比较 RRF、纯 Cross-Encoder、CE 与召回排名再融合；MRR 分别为 0.9315、0.8790、0.9018，据此将 Cross-Encoder 设计为 lazy、offline-first 且默认关闭，避免理论更强但实际负收益的组件增加延迟。

为什么值得：这比“接入了 Reranker”更高级，因为有证据、有取舍。

## 亮点 3：可复现、安全的索引生命周期

推荐表述：

> 将旧版随机 child UUID 和危险 FAISS pickle 加载改为稳定 SHA-256 文档 ID、JSON 文档映射、artifact hash、原子写入与 Manifest 校验；把语料 fingerprint、Embedding revision、归一化、维度和 chunking version 纳入索引兼容性判断，避免静默加载陈旧索引。

为什么值得：它解决真实的知识库一致性和安全问题，而不是增加模型调用。

## 亮点 4：中文 Sparse Retrieval 适配

推荐表述：

> 针对默认 whitespace tokenizer 不适合中文的问题，在 FAISS 路径实现汉字、二元组、短语和英文数字组合 token；在 Milvus 路径建立 BM25 sparse field/index，使精确菜名与食材关键词和 Dense 语义召回互补。

为什么值得：问题具体、实现明确、容易通过一个中文 Query 解释设计原因。

证据边界：没有 tokenizer 单独消融，不能声称提升了具体百分比。

## 亮点 5：可选 Agentic RAG Harness，而不是替换 Retrieval

推荐表述：

> 在保留 Classic Pipeline 的基础上，通过 LangGraph 增加 route-act-reflect-generate 编排，为普通检索、图片、条件浏览和直接回答提供工具路由；复用原 Dense/BM25/RRF Retrieval Stack，并设置一次有界 rewrite、工具失败回退、检索失败回退和生成失败降级。

为什么值得：能体现你理解 Agent 的价值在决策、状态和故障控制，而不是“让 LLM 自由调用工具”。

证据边界：8 条 Judge 中 Agent 没有优于 Classic；应描述为可选 Harness 能力，而不是质量提升结论。

# 五、B. 3 个最容易被面试官质疑的点

## 质疑 1：“你说从 Dense 升级到 Hybrid、引入 Parent-Child，但旧版源码已经有了？”

正确回答：

> 是的，当前仓库保留的 Baseline 已经有 FAISS Dense、BM25、RRF 和 Parent-Child。我不会把它们说成从无到有的升级。真实变化是中文 BM25、Milvus 服务端 Hybrid/过滤下推，以及稳定 ID、Manifest 和 parent lookup 等工程加固。如果更早的教程阶段是纯 Dense，当前仓库没有保留足够代码证据，不能据此认领。

## 质疑 2：“Agent 到底提升了什么？是不是多调一次 LLM、把流程弄复杂？”

正确回答：

> 现有 8 条 Judge 没有证明 Agent 的答案质量更强，Faithfulness 还从 4.875 变为 4.75。它的主要价值是场景路由、direct-answer 跳过检索、一次有界重写和分层降级；对明确需要普通 RAG 的 Query，Classic 更直接。项目保留双模式，就是承认这个 trade-off。当前也没有 latency/cost A/B，所以不能声称 Agent 降本增效。

## 质疑 3：“图片检索真的是多模态吗？Milvus/Reranker 的复杂度有实证收益吗？”

正确回答：

> 图片路径是视觉模型生成 caption，再复用文本 Embedding 和 BM25，不是 CLIP 式跨模态向量检索；仓库也没有图片 Recall 评测。Milvus 有扩展性和 pushdown 的架构收益，但没有对 FAISS 的吞吐/延迟 A/B。Reranker 则有反向证据，因此默认关闭。我的结论会严格区分功能可用、架构合理和评测已证明三件事。

# 六、C. 每个简历亮点对应的可追问问题

## 亮点 1：Milvus Hybrid + Filter Pushdown

1. 为什么 filter pushdown 会影响 Recall，而不仅是 Latency？
2. 为什么 FAISS 扩大到 `max(candidate_k, top_k * 5)` 仍不能等价于 pushdown？
3. Dense 和 Sparse 为什么不能直接相加原始 score？
4. Milvus 的 expression 如何防止任意字段和字符串注入？
5. FAISS 和 Milvus 两条路径如何做一致性测试？
6. 语料很小时，为什么你可能仍选择 FAISS？

回答抓手：先过滤决定候选全集；post-filter 已被截断的文档无法恢复。`build_filter_expr()` 使用字段白名单和值转义。RRF 只使用 rank，规避异构分数尺度。

## 亮点 2：评测驱动的 Reranker 取舍

1. 为什么 Cross-Encoder 理论更强，MRR 反而下降？
2. 为什么三组 Hit@5 都是 1.0，MRR 却不同？
3. `rerank_pool` 为什么不能无限增大？
4. CE rank 与 recall rank 再做 RRF 的目的是什么？
5. 73 条评测集有什么偏差？如何扩大才有统计说服力？
6. 什么新证据会让你重新开启 Reranker？

回答抓手：领域不匹配、候选短文本与 Query 类型、模型排序偏差都可能导致下降；Hit 只看 Top-K 是否命中，MRR 对正确结果的位置更敏感。

## 亮点 3：可复现、安全的索引生命周期

1. 为什么仅检查索引目录存在不够？
2. 哪些配置改变后必须重建索引？
3. 为什么 child ID 不能继续用 UUID？
4. Manifest 为什么要同时记录配置与 artifact hash？
5. 为什么 JSON 文档映射比允许危险反序列化更安全？
6. 当前 Milvus Manifest 相比 FAISS 还缺少哪些校验？

回答抓手：索引与语料、Embedding、归一化、维度、chunking 是一组不可分割的版本；稳定 ID 是去重、增量更新、评测和 provenance 的基础。

## 亮点 4：中文 BM25

1. “宫保鸡丁怎么做”在默认 whitespace split 下可能是什么 token？
2. 为什么同时保留单字、二元组和完整短语？
3. 单字 token 会引入什么噪声？
4. 为什么精确菜名 Query 对 BM25 友好，而描述性 Query 更依赖 Dense？
5. FAISS tokenizer 与 Milvus analyzer 不一致会造成什么问题？
6. 怎样设计 tokenizer 的独立消融评测？

回答抓手：中文无空格；不同粒度在 Recall 和 Precision 间折中；应该固定语料、Query、Dense 和融合参数，只替换 tokenizer 做对照。

## 亮点 5：Agentic RAG Harness

1. Agent 与 Classic 真正改变的是哪一层？
2. 为什么 Dense、BM25、RRF、Milvus 没有被 Agent 替代？
3. Rewrite 为什么不做成独立 node？当前真实图是什么？
4. 为什么只允许一次 rewrite？
5. route、tool、retrieval、generation 分别如何降级？
6. 哪类 Query 应直接走 Classic，哪类才值得 Agent？
7. direct_answer 如何避免把本应检索的问题错误地跳过知识库？

回答抓手：Agent 改的是 Orchestration；真实 node 是 route、act、reflect、generate，rewrite 在 reflect 内；`MAX_REWRITES=1` 控制成本、延迟和循环风险。

# 七、2 分钟口述版

这个项目的可见旧版其实已经不是纯 Dense RAG，它已经有 FAISS Dense、BM25、RRF、Query Router、Query Rewrite 和 Parent-Child Retrieval。所以我不会把升级包装成“从零实现 Hybrid”。真正的变化，是把一个单机教学型 RAG 加固成更接近可服务、可评测、可追踪的系统。

检索侧，项目首先针对中文修正了 BM25 分词；然后通过 `VectorStoreBackend` 把 FAISS 与 Milvus 隔离。FAISS 继续在客户端做 Dense、中文 BM25 和 RRF，Milvus 则在服务端维护 dense vector、BM25 sparse field 和标量字段，把 Hybrid Search 与 metadata、visibility filter 一起下推。它的意义不仅是性能：先召回再过滤可能把真正符合条件的文档提前截掉，因此会损失 Recall。

数据和可靠性侧，Parent-Child 思路虽然旧版已有，但升级版把随机 child UUID 改成稳定 ID，并加入 source hash、revision、chunking version；FAISS 持久化也从允许危险 pickle 改为 JSON document map、Manifest、artifact hash 和原子写入，防止语料或模型变化后静默使用陈旧索引。图片通过视觉模型生成 caption，再作为 image child 进入同一文本检索体系；这不是原生跨模态检索。

编排侧，Classic 没有被替代。Agent 只是在相同 Retrieval Stack 上增加 route、act、reflect、generate，支持不同工具、一次有界重写和故障降级。现有 8 条 Judge 没有证明 Agent 比 Classic 更好，所以它应是可选 Harness。项目还做了 73 条检索评测和 Reranker 消融：原始 RRF 的 MRR 是 0.9315，纯 CE 是 0.8790，融合后是 0.9018，因此 Reranker 默认关闭。对我来说，最有价值的升级不是组件更多，而是能用真实评测决定哪些组件不应该开启。

# 八、证据边界清单

以下结论有直接数值证据：

- 当前 Milvus Hybrid：73 条，Hit@5 1.0，MRR 0.9315。
- Reranker 消融：RRF 0.9315、CE 0.8790、CE+Recall RRF 0.9018。
- 8 条 LLM Judge：Classic Faithfulness 4.875、Agent 4.75；Relevance 均为 5.0。

以下只有源码与功能测试，**源码未提供专项数值评测证据**：

- Dense → Hybrid 的因果提升；
- 中文 tokenizer 相比 whitespace split 的独立提升；
- FAISS → Milvus 的吞吐、延迟、资源和 Recall 对比；
- filter pushdown 相比 post-filter 的独立提升；
- Parent-Child 相比直接 child context 的答案质量与 Token 成本；
- Image Ingestion 的图片检索 Recall 和 Caption 准确率；
- Agent 的 latency、Token、成本收益；
- QueryTrace 对问题定位效率的提升；
- Backend Abstraction 对维护效率的提升；
- Citation 的逐句正确率和引用 Faithfulness。

这条边界本身很重要：**源码能证明“实现了”，测试能证明“按预期运行”，A/B 评测才能证明“比原来更好”。**
