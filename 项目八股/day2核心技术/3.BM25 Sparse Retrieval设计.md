# BM25 Sparse Retrieval 设计

本文基于当前仓库真实源码，分别分析 FAISS 模式与 Milvus 模式下的 BM25 Sparse Retrieval。

范围说明：

- 分析当前版本的 `config.py`、`main.py`、`rag_modules/retrieval_optimization.py`、`rag_modules/vector_store.py` 及相关测试。
- 不分析 `rag_modules_old/` 中的旧实现。
- 先讲直觉和数据流，再补充必要的 BM25 原理。
- 对源码无法确认的运行时行为，会明确标注。

---

## 一、先建立直觉

Dense Retrieval 更像“按意思找”，BM25 更像“按字词证据找”。

例如用户问：

```text
红烧鲤鱼怎么做？
```

Dense Retrieval 可能认为以下文档都很接近：

- 红烧鲤鱼
- 红烧草鱼
- 清蒸鲤鱼
- 家常烧鱼

因为它们在语义上确实相似。但用户给出了非常明确的菜名“红烧鲤鱼”，此时最有价值的信号不是“大概都在讲鱼”，而是文档中是否真的出现了“红烧”“烧鲤”“鲤鱼”等词面片段。

BM25 正好负责保留这类精确词面证据。

当前项目的核心思路不是在 Dense 与 BM25 中二选一，而是：

```text
Dense：找语义相近的 Child Chunk
BM25：找关键词准确匹配的 Child Chunk
                    ↓
              RRF 合并两路排名
                    ↓
               返回 Top-K Child
```

两种后端的逻辑目标相同，但执行位置不同：

```text
FAISS 模式
Dense：FAISS
BM25：Python 进程内的 LangChain BM25Retriever
RRF：Python 进程内

Milvus 模式
Dense：Milvus 服务端
BM25：Milvus 服务端
RRF：Milvus 服务端
```

---

## 二、两种模式的真实结构

| 项目 | FAISS 模式 | Milvus 模式 |
|---|---|---|
| Dense 后端 | LangChain FAISS | Milvus HNSW |
| BM25 所在位置 | 应用进程内 | Milvus 服务端 |
| BM25 实现 | `BM25Retriever` / `rank_bm25` | Milvus BM25 Function |
| 中文分词 | 项目自定义 `tokenize_chinese()` | Milvus Analyzer |
| 首选中文 Analyzer | 不适用 | `{"tokenizer": "jieba"}` |
| Sparse 存储 | Python 内存中的 BM25 数据结构 | `SPARSE_FLOAT_VECTOR` 字段 |
| Sparse 索引 | `BM25Okapi` 内部结构 | `SPARSE_INVERTED_INDEX` |
| Fusion | `_rrf_rerank()` | `RRFRanker(60)` |
| Metadata Filter | 融合召回后在客户端过滤 | `expr` 下推到 Dense/Sparse 请求 |

## 三、1. 为什么项目需要 BM25

### 源码事实

- 文件：`rag_modules/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 函数：`hybrid_search()`

在 FAISS 模式中，该函数同时执行：

```python
vector_docs = self.vectorstore.similarity_search(query, k=candidate_count)
bm25_docs = self.bm25_retriever.invoke(query)
fused = self._rrf_rerank(vector_docs, bm25_docs, self.rrf_k)
```

在 Milvus 模式中，则调用：

```python
self.vectorstore.hybrid_search(...)
```

由 Milvus 同时完成 Dense、BM25 和 RRF。

`config.py` 中还记录了当前语料的评测结论：73 条 golden set 上，RRF 基线 MRR 为 `0.931`；源码注释明确指出当前菜谱语料的 BM25 精确菜名信号很强。

### 工程解释

项目需要 BM25，主要不是因为 Dense 完全无效，而是因为 Dense 和 BM25 的错误类型不同：

- Dense 擅长同义表达，但可能把“语义相似但对象错误”的菜谱排得很高。
- BM25 擅长准确词面匹配，可以保护菜名、食材名、专有词和部分数字等信号。

如果只用 Dense，用户明确说出“红烧鲤鱼”时，系统仍可能被“红烧草鱼”或“清蒸鲤鱼”等语义近邻干扰。

如果只用 BM25，用户使用文档中没有出现的同义说法时，又容易漏检。

因此，BM25 在本项目中的角色是：**补充精确词面召回，并与 Dense 的语义召回互相兜底。**

## 四、2. 中文 BM25 在 FAISS 模式下如何分词

### 建立本地 BM25 的位置

- 文件：`rag_modules/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 函数：`setup_retrievers()`

当后端是 FAISS 时：

```python
self.server_side_hybrid = False
```

因此项目创建本地 BM25：

```python
self.bm25_retriever = BM25Retriever.from_documents(
    self.chunks,
    k=self.candidate_k,
    preprocess_func=tokenize_chinese,
)
```

这里有三个重要事实：

1. 建立 BM25 的语料是 `self.chunks`，即 Child Chunk，不是 Parent Document。
2. 文档预处理函数被明确替换为项目自己的 `tokenize_chinese()`。
3. Query 检索时，`BM25Retriever.invoke(query)` 会使用同一个 `preprocess_func` 处理 Query。

### 分词策略

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`tokenize_chinese(text)`

它不依赖 jieba，也不加载分词模型或外部词典，而是使用正则和字符组合：

```text
输入文本
  ↓ casefold，统一英文大小写
英文/数字连续串 → 一个 token
中文连续串      → 单字 token
                → 相邻双字 token
                → 若整段长度 ≤ 8，再加入完整短语 token
```

这种实现的目标是：在任何 CPU 环境中都能为中文精确菜名和部分菜名提供稳定的词面召回。

## 五、3. `tokenize_chinese` 具体产生哪些 token

源码：

```python
def tokenize_chinese(text: str) -> list[str]:
    normalized = text.casefold()
    tokens = re.findall(r"[a-z0-9]+", normalized)
    for sequence in re.findall(r"[\u3400-\u4dbf\u4e00-\u9fff]+", normalized):
        tokens.extend(sequence)
        tokens.extend(sequence[index : index + 2] for index in range(len(sequence) - 1))
        if len(sequence) <= 8:
            tokens.append(sequence)
    return tokens
```

### 例子：`红烧鲤鱼 BGE-v1`

函数实际产生：

```python
[
    "bge", "v1",
    "红", "烧", "鲤", "鱼",
    "红烧", "烧鲤", "鲤鱼",
    "红烧鲤鱼",
]
```

仓库测试：

- 文件：`tests/test_retrieval_optimization.py`
- 测试：`test_tokenize_chinese_produces_characters_bigrams_and_exact_phrase()`

该测试明确验证：

- 单字：`红`、`烧`、`鲤`、`鱼`
- 双字：`红烧`、`烧鲤`、`鲤鱼`
- 完整短语：`红烧鲤鱼`
- 英文数字：`bge`、`v1`

### 每一步的准确行为

#### 1. `casefold()`

英文统一为小写：

```text
BGE → bge
```

它比单纯 `lower()` 更通用，但当前语料主要体现为英文大小写归一。

#### 2. 英文和数字连续串

正则：

```regex
[a-z0-9]+
```

因此：

```text
BGE-v1 → bge, v1
abc123 → abc123
```

连字符、空格和标点会形成边界。

#### 3. 中文连续串

正则范围：

```regex
[\u3400-\u4dbf\u4e00-\u9fff]+
```

它匹配 CJK Extension A 和常用中日韩统一表意文字范围中的连续字符。

#### 4. 单字 token

源码的：

```python
tokens.extend(sequence)
```

会把 Python 字符串按字符展开。

例如：

```text
红烧鲤鱼 → 红, 烧, 鲤, 鱼
```

#### 5. 相邻双字 token

通过长度为 2 的滑动窗口生成：

```text
红烧鲤鱼 → 红烧, 烧鲤, 鲤鱼
```

这里没有跳字组合，也没有三元组。

#### 6. 长度不超过 8 的完整短语

```text
红烧鲤鱼 → 红烧鲤鱼
```

如果一个连续中文序列超过 8 个字符，就不会加入完整序列 token，但仍保留单字和相邻双字。

### 需要注意的边界

- 函数不执行停用词过滤，“的”“了”“怎么”等也会成为 token。
- 函数不做词形还原或同义词扩展。
- 函数不会对 token 去重；重复词可以重复出现，这会参与词频计算。
- 标点和空格会切断中文连续序列。
- 它不是语言学意义上的中文分词，而是字符 n-gram 风格的轻量切词。

## 六、4. 为什么 LangChain 默认 whitespace split 对中文不够好

### 已核对的依赖行为

当前项目锁定：

```text
langchain-community==0.4.2
```

该版本 `BM25Retriever` 的默认预处理函数是：

```python
def default_preprocessing_func(text):
    return text.split()
```

它按空白符切分。

### 中文的问题

英文天然用空格分词：

```text
how to cook fish
→ how / to / cook / fish
```

中文通常不在词之间加空格：

```text
红烧鲤鱼怎么做
```

如果只调用 `split()`，整句话可能成为一个 token：

```text
["红烧鲤鱼怎么做"]
```

而文档标题可能得到：

```text
["红烧鲤鱼"]
```

两个 token 并不相等，于是 BM25 看不到它们内部共享的“红烧”和“鲤鱼”。

`tokenize_chinese()` 将中文拆成单字、双字和短语后，即使 Query 多了“怎么做”，也仍能通过以下 token 与文档相遇：

```text
红 / 烧 / 鲤 / 鱼 / 红烧 / 烧鲤 / 鲤鱼
```

这就是项目替换默认 whitespace split 的直接原因。

## 七、5. Milvus 中 BM25 如何建立 sparse field/index

Milvus 模式不创建本地 `BM25Retriever`。

### 跳过本地 BM25

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 类属性：`supports_server_side_hybrid = True`

`RetrievalOptimizationModule.setup_retrievers()` 检测到该属性后直接返回：

```python
if self.server_side_hybrid:
    logger.info("检测到服务端混合检索后端，跳过本地 BM25 索引")
    return
```

因此，Milvus 模式下 `self.bm25_retriever` 保持为 `None`。

### Schema 中的三个关键部分

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 函数：`_build_schema()`

#### 1. 原始文本字段 `content`

```python
schema.add_field("content", DataType.VARCHAR, ...)
```

如果有 Analyzer 配置，还会加入：

```python
enable_analyzer=True
analyzer_params=analyzer_params
```

#### 2. Sparse 向量字段 `sparse`

```python
schema.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)
```

#### 3. BM25 Function

```python
Function(
    name="content_bm25",
    input_field_names=["content"],
    output_field_names=["sparse"],
    function_type=FunctionType.BM25,
)
```

含义是：Milvus 读取 `content`，经过 Analyzer 和 BM25 Function，自动生成 `sparse` 表示。

### Sparse Index

- 函数：`MilvusVectorStore._create_collection()`

创建索引时：

```python
index_params.add_index(
    field_name="sparse",
    index_type="SPARSE_INVERTED_INDEX",
    metric_type="BM25",
)
```

所以完整关系是：

```text
content 文本
→ Milvus Analyzer
→ BM25 Function
→ sparse: SPARSE_FLOAT_VECTOR
→ SPARSE_INVERTED_INDEX
```

### 应用端不会自己写入 `sparse`

`MilvusVectorStore._rows_for_insert()` 只写入：

- `chunk_id`
- Dense `vector`
- `content`
- metadata 字段

不会写 `sparse`。

测试：

- 文件：`tests/test_vector_store.py`
- 测试：`test_build_index_creates_collection_and_skips_sparse_field()`

明确断言：

```python
assert "sparse" not in row
```

原因是 Sparse 字段由服务端 BM25 Function 负责生成。

## 八、Milvus 使用什么中文分词器

### 源码事实

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 常量：`BM25_ANALYZER_CANDIDATES`

候选顺序为：

```python
(
    {"tokenizer": "jieba"},
    {"type": "chinese"},
)
```

`_create_collection()` 实际尝试顺序是：

```text
1. {"tokenizer": "jieba"}
2. {"type": "chinese"}
3. None
```

每次会用候选 Analyzer 创建完整 collection。如果创建失败，就删除本次残留 collection 并尝试下一个候选；全部失败才抛出 `RuntimeError`。

成功后，实际候选保存在：

```python
self._analyzer_params = candidate
```

并输出日志：

```text
BM25 分词器选用: ...
```

### 结论边界

源码只能确认“优先使用 jieba，并有降级候选”。在不知道当前 Milvus 服务端能力和运行日志的情况下，**不能断言实际 collection 一定使用了 jieba**。

Milvus 的具体 token 序列由服务端 Analyzer 产生，当前 Python 仓库没有把这些 token 取回或打印。因此：

> 当前代码不足以确认某条中文文本在实际 Milvus 服务端最终被切成了哪些 token。

这也是为什么不能把 FAISS 的 `tokenize_chinese()` 结果直接套到 Milvus 模式。

## 九、6. 查询时两种 BM25 分别怎么执行

## 6.1 FAISS：本地 BM25

真实调用链：

```text
main.py
RAGSystem.retrieve(query)
  ↓
rag_modules/retrieval_optimization.py
RetrievalOptimizationModule.hybrid_search(query, top_k)
  ↓
candidate_count = max(pool_size, candidate_k)
  ↓
Dense: FaissBackend.similarity_search(query, k=candidate_count)
BM25:  BM25Retriever.invoke(query)
  ↓
BM25Retriever 使用 tokenize_chinese(query)
  ↓
返回 BM25 排名的 candidate_count 个 Child
  ↓
_rrf_rerank(vector_docs, bm25_docs, rrf_k)
  ↓
可选 reranker
  ↓
Top-K Child
```

默认配置：

```text
top_k = 3
candidate_k = 10
rrf_k = 60
reranker = disabled
```

默认情况下，Dense 和 BM25 各召回最多 10 个候选，再由本地 `_rrf_rerank()` 融合，最终返回 3 个 Child。

`BM25Retriever.invoke(query)` 内部先执行 `tokenize_chinese(query)`，再由 `BM25Okapi` 对本地全部 `self.chunks` 评分并取 Top-N。

### FAISS 模式下的过滤顺序

FAISS 后端不能把 Milvus 风格的表达式下推到索引。因此源码采用：

```text
先 Dense + BM25 召回并 RRF
→ 再按 expr / metadata 过滤
→ 再截断 Top-K
```

`metadata_filtered_search()` 会扩大候选池，但仍存在“满足过滤条件的文档在召回前已被遗漏”的可能。

## 6.2 Milvus：服务端 BM25

真实调用链：

```text
main.py
RAGSystem.retrieve(query)
  ↓
RetrievalOptimizationModule.hybrid_search()
  ↓ server_side_hybrid=True
MilvusVectorStore.hybrid_search()
  ↓
Dense AnnSearchRequest
  +
Sparse AnnSearchRequest
  ↓
MilvusClient.hybrid_search(..., ranker=RRFRanker(60))
  ↓
Top-K Child
```

Sparse 请求的真实构造：

```python
sparse_request = AnnSearchRequest(
    data=[query],
    anns_field="sparse",
    param={"metric_type": "BM25"},
    limit=limit,
    expr=expr,
)
```

这里传入的是原始字符串 `query`，不是 Python 端生成的 Sparse 向量。Milvus 服务端使用 collection 的 Analyzer 和 BM25 Function 处理 Query。

Dense 与 Sparse 请求随后一起交给：

```python
client.hybrid_search(
    reqs=[dense_request, sparse_request],
    ranker=RRFRanker(60),
    limit=k,
)
```

### Milvus 模式下的过滤顺序

源码把同一个 `expr` 同时挂到 Dense 和 Sparse `AnnSearchRequest` 上，因此逻辑是：

```text
先按 metadata / visibility 缩小合法候选范围
→ 在合法范围内分别执行 Dense 与 BM25
→ 服务端 RRF
→ Top-K
```

代码注释特别说明：在当前 `pymilvus 2.5` 行为下，表达式必须放到每个 `AnnSearchRequest`，不能只传给最外层 `hybrid_search()`。

### 一个参数一致性细节

本地 FAISS 融合使用：

```python
self.rrf_k
```

其默认值来自 `RAGConfig.rrf_k=60`。

Milvus 服务端当前写死：

```python
RRFRanker(60)
```

因此，即使环境变量修改 `RAG_RRF_K`，当前源码也不会把新值传入 Milvus 的这次服务端 RRF。这个结论是源码事实，也是一个配置一致性上的改进空间。

## 十、7. BM25 擅长什么 Query

## 1. 精确菜名

例如：

```text
红烧鲤鱼怎么做
宫保鸡丁需要哪些材料
```

菜名中的稀有字符、双字组合或分词结果会形成强词面证据。

## 2. 精确食材名

例如：

```text
哪些菜会用到五花肉
用秋葵能做什么
```

只要相同食材词真实出现在 Child 内容中，BM25 通常能稳定捕获。

## 3. 专有名词、缩写和英文数字串

FAISS 的 `tokenize_chinese()` 会保留 `[a-z0-9]+` 连续串，因此类似型号、缩写和字母数字组合可以作为精确 token。

## 4. 用户基本复制了文档措辞

Query 与文档有较多原词重合时，BM25 通常比依赖语义近似更直接。

## 5. 罕见词比常见词更有辨识度的查询

BM25 会让跨文档较少出现的词拥有更强区分力。例如某个少见菜名或食材名，往往比“怎么做”“步骤”“好吃”等高频词更能定位目标文档。

---

## 十一、8. BM25 容易在哪些 Query 上失败

## 1. 同义改写但没有共同词

例如：

```text
Query：怎么让肉不柴？
Document：小火慢炖可以保持软嫩。
```

语义相关，但词面重合弱。Dense Retrieval 更适合补足这种情况。

## 2. 抽象需求或描述性推荐

例如：

```text
适合夏天吃的清爽家常菜
想做一道对新手友好的下饭菜
```

文档未必原样出现“夏天”“清爽”“新手友好”，纯 BM25 Recall 容易不足。

## 3. 中文分词边界不一致

FAISS 使用字符和双字 n-gram，可以降低边界不一致的风险，但也会带来噪声；Milvus 的结果则取决于实际启用的 Analyzer。复合菜名、领域新词或罕见食材可能被切得不理想。

## 4. 大量常见字词造成误匹配

字符级 token 的 Recall 较高，但单字也可能产生噪声。两个无关菜谱只要共享很多常用汉字，就可能获得部分 BM25 分数。

## 5. 否定和语序关系

BM25 主要看 token 是否出现，不真正理解：

- 不要辣
- 不含花生
- 不是清蒸做法

含有“辣”“花生”“清蒸”的文档反而可能获得词面匹配分数。

## 6. 需要推理或组合多个事实

例如“没有烤箱且只有十五分钟能做哪一道菜”，答案可能需要同时理解设备、时长和步骤，BM25 只能提供局部词面证据。

## 7. 数字含义相近但形式不同

例如：

```text
15 分钟
一刻钟
十五分钟
```

含义相同，但 token 不同。BM25 本身不会自动进行数值归一化或同义转换。

## 十二、9. 为什么精确菜名 Query 对 BM25 特别友好

可以从四层理解。

## 第一层：菜名是强词面标识

“红烧鲤鱼”不是泛化主题，而是接近文档标识符的短语。用户给出精确菜名时，目标文档通常真的包含相同文字。

## 第二层：FAISS 分词为菜名制造了多级证据

`红烧鲤鱼` 会生成：

```text
红 / 烧 / 鲤 / 鱼
红烧 / 烧鲤 / 鲤鱼
红烧鲤鱼
```

即使 Query 是“红烧鲤鱼怎么做”，完整 Query token 与文档标题不完全相同，双方仍共享多个单字和双字 token。

如果 Query 就是“红烧鲤鱼”，还会额外共享完整短语 token。

## 第三层：罕见组合区分度高

“怎么”“做”在很多文档或 Query 中都很常见，而“烧鲤”“鲤鱼”出现范围更窄。BM25 的 IDF 机制会让较少见的匹配词拥有更高区分力。

## 第四层：标题被保留在 Child 文本中

项目 Markdown 切分使用 `strip_headers=False`，所以标题不会从 Child 的 `page_content` 中删除。BM25 的输入是 Child 文本，因此菜名标题可以直接参与检索。

需要注意：BM25 并没有单独对 metadata 中的 `dish_name` 字段加权。

- FAISS 本地 BM25 使用 `Document.page_content`。
- Milvus BM25 Function 的输入字段只有 `content`。

精确菜名之所以有效，是因为标题保留在 `content/page_content` 中，而不是因为系统为 `dish_name` 配置了独立 BM25 boost。

- 测试：`test_chinese_bm25_recalls_the_exact_dish_name()`

测试构造“清蒸鲈鱼”“番茄炒蛋”“红烧鲤鱼”“拍黄瓜”等 Child，并查询：

## 十三、必要的 BM25 原理

无需先背公式。BM25 可以理解为对每个 Query token 检查三件事：

## 1. 文档里有没有这个词

没有出现就没有这部分分数；出现则提供词面相关证据。

## 2. 这个词在整个语料中稀不稀有

几乎每篇文档都有的词，区分能力弱；只在少量文档出现的词，区分能力强。

这就是为什么“红烧鲤鱼”里的特征组合通常比“怎么做”更有用。

## 3. 它在当前文档中出现多少次，以及文档有多长

出现多次通常会提高得分，但不是无限线性增长；BM25 会做词频饱和。同时会做一定的文档长度归一化，避免长文档仅仅因为词多就总是占优势。

因此可以把它概括为：

```text
BM25 分数
≈ 精确词匹配
× 词的稀有程度
× 经过饱和处理的词频
× 文档长度修正
```

当前项目没有在 `BM25Retriever.from_documents()` 中传入自定义 `bm25_params`，因此 FAISS 模式使用底层 `BM25Okapi` 的默认参数。Milvus 模式的 BM25 内部参数由服务端实现管理，当前 Python 代码没有显式设置 `k1`、`b` 等参数。

## 十五、关键参数与设计点

## 1. `candidate_k=10`

Dense 和 BM25 在融合前的候选规模。

- 调大：通常增加 Recall，也增加搜索和融合成本。
- 调小：更快，但相关 Child 可能在 RRF 前已被截掉。

## 2. `top_k=3`

默认最终保留的融合结果数量。

- 调大：可能召回更多相关 Parent，也可能引入噪声和 Context 压力。
- 调小：结果更精炼，但更容易漏掉目标。

## 3. `rrf_k=60`

FAISS 本地 `_rrf_rerank()` 使用该配置；Milvus 当前写死 `RRFRanker(60)`。

它控制 RRF 对排名位置差异的敏感程度，本篇不展开公式。需要记住的是：两条路径默认都使用 60，但配置传播方式并不一致。

## 4. `tokenize_chinese()` 的完整短语阈值 `8`

代码中写死：

```python
if len(sequence) <= 8:
    tokens.append(sequence)
```

- 阈值更大：可以保留更多长短语精确匹配，但 token 更稀疏、更容易只在完全相同文本时命中，也会增加词表规模。
- 阈值更小：减少长短语 token，更多依赖单字和双字，Recall 可能更宽但精确短语信号变弱。

## 5. Milvus Analyzer 候选顺序

当前依次尝试：

```text
jieba → chinese → None
```

它决定服务端如何切分中文。更换 Analyzer 会改变 Sparse 表示，需要重新创建 collection 和索引，不能假定与旧索引兼容。

## 十六、收益与代价

### 收益

- 保护精确菜名、食材名和专有词信号。
- 补足 Dense 容易出现的“语义相似但实体错误”。
- 与 Dense 通过 RRF 组合，不要求两路分数处于同一数值尺度。
- FAISS 模式无需额外搜索服务即可获得中文 Sparse Retrieval。
- Milvus 模式可把 BM25、过滤和融合放到服务端执行。

### 代价

- FAISS 模式需要在应用内为全部 Child 额外维护一份 BM25 结构，增加启动时间和内存。
- FAISS 的字符和双字 token 提高 Recall，也可能引入单字匹配噪声。
- Milvus 模式依赖服务端版本对 Analyzer、BM25 Function 和 Hybrid Search 的支持。
- 两种模式的中文分词算法不同，切换后端可能导致 Sparse 排名变化。
- Dense 与 BM25 双路召回和 RRF 比单路检索更复杂，也有额外延迟。

## 十七、源码事实边界

当前源码可以确认：

- FAISS 模式使用本地 `BM25Retriever`。
- FAISS 的文档和 Query 都通过 `tokenize_chinese()` 预处理。
- `tokenize_chinese()` 生成英文数字连续串、中文单字、相邻双字和不超过 8 字的完整短语。
- Milvus 模式跳过本地 BM25。
- Milvus Schema 包含 `content`、`sparse` 和 `content_bm25` Function。
- Milvus 的 Sparse Index 是 `SPARSE_INVERTED_INDEX`，metric 是 `BM25`。
- Milvus 查询将原始 Query 字符串传给 Sparse `AnnSearchRequest`。
- FAISS 在客户端进行 RRF，Milvus 在服务端进行 RRF。

当前源码不足以确认：

- 实际运行中的 Milvus 最终选中了 `jieba`、`chinese` 还是 `None`；需要查看创建 collection 时的日志或服务端 Schema。
- Milvus Analyzer 对某条具体 Query 最终产生了哪些 token；Python 代码没有输出服务端 token。
- BM25 在完整真实评测集上对每类 Query 的独立 Recall、Precision 和延迟；现有注释提供了整体 RRF/重排实验结果，但不是 BM25 单路完整评测报告。
