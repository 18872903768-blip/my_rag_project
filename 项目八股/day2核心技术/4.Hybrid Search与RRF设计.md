# Hybrid Search 与 RRF 设计

本文基于当前仓库真实源码，分析 Dense + BM25 Hybrid Search，以及两条检索结果如何通过 RRF 融合。

范围说明：

- 分析当前版本的 `config.py`、`main.py`、`rag_modules/retrieval_optimization.py`、`rag_modules/vector_store.py` 及相关测试。
- 不分析 `rag_modules_old/` 中的旧实现。
- 示例中的排名会明确标注为“按源码算法构造的演算示例”，不是伪装成真实模型运行结果。

---

## 一、先建立直觉

Hybrid Search 的核心原因是：Dense 与 BM25 看到的“相关”不是一回事。

```text
Dense Retrieval
看语义是否接近
擅长同义表达、描述性需求、不同措辞

BM25 Retrieval
看字词是否准确重合
擅长精确菜名、食材名、专有词
```

例如用户问：

```text
红烧鲤鱼怎么做？
```

Dense 可能觉得“红烧草鱼”“清蒸鲤鱼”也很相似，因为主题和烹饪语义接近；BM25 则能通过“红烧”“烧鲤”“鲤鱼”等精确 token 强化真正的“红烧鲤鱼”。

反过来，如果用户问：

```text
怎么把肉炖得软嫩不柴？
```

文档可能只写“小火慢炖”，词面重合很少。Dense 更有机会通过语义找到它。

因此当前项目采用：

```text
Query
  ├─ Dense 排名
  └─ BM25 排名
         ↓
    RRF 按名次融合
         ↓
      Top-K Child
```

RRF 的作用不是重新理解 Query，也不是重新阅读文档，而是回答：

> 哪些 Child 同时被两种不同检索方式排在较靠前的位置？

## 四、1. Dense 和 BM25 为什么要结合

### 源码事实

- 文件：`rag_modules/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 类说明：`Combine dense and Chinese-aware BM25 retrieval using RRF`

FAISS 路径明确产生两路结果：

```python
vector_docs = self.vectorstore.similarity_search(query, k=candidate_count)
bm25_docs = self.bm25_retriever.invoke(query)
fused = self._rrf_rerank(vector_docs, bm25_docs, self.rrf_k)
```

Milvus 路径也构建 Dense 与 Sparse 两个 `AnnSearchRequest`，再交给 `RRFRanker`。

`config.py` 的注释记录了当前 73 条 golden set 的实验：RRF 基线 MRR 为 `0.931`，并指出该菜谱语料中的 BM25 精确菜名信号很强。

### 工程解释

两路结合的价值来自互补性：

- Dense 提高语义 Recall，减少“换一种说法就检索不到”。
- BM25 保护精确词 Precision，减少“意思相近但菜名或食材错了”。
- RRF 不要求两路分数具有相同尺度，只利用排名就能合并。

如果两路犯的是不同错误，融合通常比任何单路更稳。

但“结合”不等于必然提升。如果两路都漏掉正确文档，或者两路同时偏向同一个错误候选，RRF 无法创造新的正确候选。

## 五、2. FAISS 模式下两路结果在哪里产生

### 前置初始化

- 文件：`main.py`
- 函数：`RAGSystem.build_knowledge_base()`

FAISS 分支先创建：

```python
self.backend = FaissBackend(vectorstore)
```

再创建：

```python
RetrievalOptimizationModule(
    self.backend,
    all_chunks,
    candidate_k=self.config.candidate_k,
    rrf_k=self.config.rrf_k,
    reranker=self._build_reranker(),
)
```

`FaissBackend.supports_server_side_hybrid = False`，所以 `RetrievalOptimizationModule.setup_retrievers()` 会为全部 Child Chunk 创建本地 `BM25Retriever`。

### Dense 结果

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`RetrievalOptimizationModule.hybrid_search()`

调用：

```python
vector_docs = self.vectorstore.similarity_search(
    query,
    k=candidate_count,
)
```

其中 `self.vectorstore` 是：

- 文件：`rag_modules/vector_store.py`
- 类：`FaissBackend`
- 函数：`similarity_search()`

它继续调用：

```python
self.vectorstore.similarity_search(query, k=k)
```

得到按 FAISS L2 距离排好的 `list[Document]`。

### BM25 结果

同一个 `RetrievalOptimizationModule.hybrid_search()` 中：

```python
previous_k = self.bm25_retriever.k
self.bm25_retriever.k = candidate_count
try:
    bm25_docs = self.bm25_retriever.invoke(query)
finally:
    self.bm25_retriever.k = previous_k
```

得到按本地 BM25 排好的 `list[Document]`。

`BM25Retriever` 在初始化时使用项目自定义 `tokenize_chinese()`，因此文档和 Query 都经过中文字符、双字和短语 token 化。

### 为什么临时修改 `bm25_retriever.k`

初始化 BM25 时，`k` 默认等于配置的 `candidate_k`。但某次查询可能显式传入更大的 `candidate_k`，或者 `top_k` 本身大于默认候选数。

源码先临时将 BM25 的 `k` 改成当前 `candidate_count`，查询结束后在 `finally` 中恢复，确保 Dense 和 BM25 使用同样的候选数量，又不永久污染 Retriever 状态。

## 六、3. FAISS 模式下 RRF 在哪里计算

- 文件：`rag_modules/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 函数：`_rrf_rerank()`

入口：

```python
fused = self._rrf_rerank(
    vector_docs,
    bm25_docs,
    self.rrf_k,
)
```

核心计算：

```python
for result_set in (vector_docs, bm25_docs):
    for rank, document in enumerate(result_set, start=1):
        document_id = self._document_id(document)
        documents.setdefault(document_id, document)
        scores[document_id] = (
            scores.get(document_id, 0.0)
            + 1.0 / (k + rank)
        )
```

随后：

```python
ranked = sorted(
    scores,
    key=lambda document_id: scores[document_id],
    reverse=True,
)
```

返回的新 `Document` metadata 中加入：

```python
"rrf_score": scores[document_id]
```

### 如何识别两路中的同一个 Child

`_document_id(document)` 优先使用：

```python
document.metadata["chunk_id"]
```

因此，同一个 Child 同时出现在 Dense 与 BM25 中时，会合并成一个结果并累加两次贡献。

如果没有 `chunk_id`，代码才使用以下内容计算 SHA-256 fallback ID：

```text
source_path + chunk_index + page_content
```

当前建库链路要求每个 Chunk 都有稳定 `chunk_id`，所以正常运行时主要使用 `chunk_id`。

### 同分时的行为

Python 的排序是稳定的，`scores` 字典保持首次插入顺序。代码先遍历 `vector_docs`，再遍历 `bm25_docs`。

因此两个文档 `rrf_score` 完全相同时，较早进入字典的文档排在前面；通常 Dense 列表中先出现的文档有顺序优势。

测试 `test_rrf_fuses_and_deduplicates_by_chunk_id()` 明确验证：

- 同一个 `chunk_id` 在两路出现时只保留一次。
- 双路命中的文档分数更高。
- 两个单路文档同分时，Dense 先插入的文档在前。

## 七、4. Milvus 模式下 RRF 在哪里执行

Milvus 的主 RRF 不在 `RetrievalOptimizationModule._rrf_rerank()` 中计算，而是在 Milvus 服务端执行。

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 函数：`hybrid_search()`

它构建两路请求：

```python
dense_request = AnnSearchRequest(
    data=[vector],
    anns_field="vector",
    param={"metric_type": self.metric_type},
    limit=limit,
    expr=expr,
)

sparse_request = AnnSearchRequest(
    data=[query],
    anns_field="sparse",
    param={"metric_type": "BM25"},
    limit=limit,
    expr=expr,
)
```

然后调用：

```python
client.hybrid_search(
    collection_name=self.collection_name,
    reqs=[dense_request, sparse_request],
    ranker=RRFRanker(60),
    limit=k,
    output_fields=self._output_fields(),
)
```

因此：

```text
Dense 排名产生于 Milvus
BM25 排名产生于 Milvus
RRF 融合也发生在 Milvus
```

服务端返回的融合结果分数出现在 Hit 的 `distance` 字段中。项目将它改名为：

```python
document.metadata["rrf_score"]
```

避免下游继续把融合分数误称为 Dense distance。

### 参数传播上的真实差异

`main.py` 虽然把：

```python
rrf_k=self.config.rrf_k
```

传给了 `RetrievalOptimizationModule`，但 `MilvusVectorStore.hybrid_search()` 内部写的是：

```python
RRFRanker(60)
```

并没有接收 `self.rrf_k`。

所以：

- FAISS 主 RRF 使用可配置的 `RAGConfig.rrf_k`。
- Milvus 主 RRF 当前固定使用 60。
- 修改环境变量 `RAG_RRF_K` 不会改变 Milvus 主融合的 `RRFRanker(60)`。

这是当前源码中的配置一致性问题，不应在介绍项目时忽略。

## 八、5. RRF 使用的到底是什么信息

FAISS 的 `_rrf_rerank()` 直接证明，RRF 使用：

## 1. 每条结果来自哪一个结果列表

当前共有两条主召回列表：

- `vector_docs`
- `bm25_docs`

## 2. Document 在每个列表中的名次 `rank`

名次从 1 开始：

```python
enumerate(result_set, start=1)
```

名次越靠前，贡献：

```text
1 / (rrf_k + rank)
```

越大。

## 3. 跨列表识别同一 Child 的 ID

正常情况下使用：

```text
metadata["chunk_id"]
```

同一个 Child 在两路中出现，会获得两次分数并去重。

## 4. 是否在多条结果列表中重复出现

一个 Child 同时进入 Dense 与 BM25 候选，其最终分数是两路贡献之和。

在 `rrf_k=60` 且候选池较浅时，“双路都认可”通常是非常强的信号。

---

## 九、6. RRF 没有使用什么信息

本项目的主 RRF 没有直接使用：

## 1. Dense 原始距离或相似度

FAISS 的 L2 distance 没有传入 `_rrf_rerank()`；函数只接收已排序的 `Document` 列表。

## 2. BM25 原始分数

`BM25Retriever.invoke()` 返回排序后的文档，项目没有读取每篇文档的 BM25 score。

## 3. Query 与 Document 的文本内容

RRF 不重新阅读 `query` 或 `page_content`，也不判断语义、否定、数字和事实正确性。

`page_content` 只可能在缺失 `chunk_id` 时参与构造 fallback ID，不参与相关性评分。

## 4. Embedding 向量

RRF 不读取向量坐标，也不重新计算 cosine 或 L2。

## 5. Metadata 的业务含义

`category`、`difficulty`、`visibility`、`dish_name`、`parent_id` 不参与 RRF 公式。

Metadata Filter 可以在 RRF 之前或之后限制候选，但那是过滤步骤，不是 RRF 自己理解 metadata。

## 6. 检索器置信度和质量

两条结果列表在公式中默认等权。代码没有根据 Query 类型动态决定“这次更相信 BM25”或“这次更相信 Dense”。

## 7. Parent 层面的聚合

RRF 融合的是 Child Chunk。Parent 恢复发生在检索完成之后，位于 `DataPreparationModule.get_parent_documents()`。

因此同一 Parent 的多个 Child 在 RRF 阶段仍是不同候选，不会先合并成 Parent score。

## 十、7. 为什么不直接把 Dense score 和 BM25 score 相加

因为两种分数不在同一尺度上。

当前项目中：

- FAISS Dense 使用 L2 distance，数值越小越好。
- Milvus Dense 使用 COSINE，结果语义与 L2 不同。
- BM25 score 通常数值越大越好，并受 Query 长度、token 稀有程度和语料统计影响。

即使把 L2 先取负数，也不能保证它与 BM25 score 的范围和分布可比。

例如：

```text
Dense score: 0.12 与 0.16
BM25 score: 18.5 与 7.2
```

直接相加时，BM25 的数值尺度可能完全主导结果；换一个 Query 后，BM25 分数范围又可能变化。

若要直接相加，至少需要：

- 统一“越大越好”的方向。
- 对两路分数做归一化或校准。
- 选择并评测权重。
- 保证后端或模型改变后重新校准。

RRF 绕开了这些问题：它只看每一路的相对名次。

### 收益

- 不依赖不同检索器的原始分数尺度。
- FAISS 与 Milvus 后端更容易共享同一融合思想。
- 对分数分布变化相对稳健。

### 代价

- 丢弃了分数差距信息。
- 第一名仅比第二名稍好，和第一名远胜第二名，在 RRF 看来没有区别。
- 无法表达某一路检索器对当前 Query 的高置信度。

## 十一、8. `rrf_k` 的作用是什么

RRF 对某文档在某一路的贡献是：

```text
1 / (rrf_k + rank)
```

`rrf_k` 是一个平滑常数，不是最终返回数量。

### `rrf_k` 较小

前几名之间的分数差异更明显。

直觉上：

```text
更奖励某一路的榜首
更强调名次高低
```

风险是：某一路错误的第一名也会获得更大优势。

### `rrf_k` 较大

候选池前几名之间的贡献更接近。

直觉上：

```text
弱化 rank 1 与 rank 5 的差距
更强调是否被两路共同召回
```

但如果过大，列表内部排序信息被压得太平，低位候选与高位候选差异变小。

### 当前项目值

- 配置：`config.py` → `RAGConfig.rrf_k = 60`
- FAISS：`_rrf_rerank(..., self.rrf_k)`，真实使用配置值。
- Milvus：`RRFRanker(60)`，当前硬编码为 60。

默认候选池通常只有 10 个。`k=60` 时：

```text
rank 1 贡献 = 1/61 ≈ 0.016393
rank 10 贡献 = 1/70 ≈ 0.014286
```

差距不大。因此在当前配置中，一个同时进入 Dense 与 BM25 的 Child，通常比只进入单路的 Child 更占优势。

## 十二、9. `candidate_k` 与 `top_k` 的区别是什么

### `candidate_k`

含义：每一路召回并提供给融合阶段的候选规模。

默认值：

```text
candidate_k = 10
```

作用位置：

```python
candidate_count = max(
    pool_size,
    candidate_k or self.candidate_k,
)
```

FAISS 默认让 Dense 和 BM25 各取 10 个候选。

Milvus 默认让 Dense `AnnSearchRequest` 和 Sparse `AnnSearchRequest` 各自使用 `limit=10`。

### `top_k`

含义：Hybrid Fusion 和可选 Reranker 完成后，最终交给后续 Parent Retrieval 的 Child 数量。

默认值：

```text
top_k = 3
```

### 默认数据流

```text
Dense Top-10 ┐
             ├─ RRF → Final Top-3 Child
BM25  Top-10 ┘
```

### 为什么候选池要大于最终结果

如果两路各自只取 3 个，某个正确 Child 在 Dense 第 4、BM25 第 4，就完全没有进入融合机会。

先各取 10 个，再融合为 3 个，可以让两路在较深位置共同认可的候选浮上来。

### 调参影响

#### `candidate_k` 调大

- Recall 通常提高。
- RRF 处理的候选更多。
- 查询、BM25、Milvus 和可选 reranker 成本增加。
- 更多低质量候选可能进入融合。

#### `candidate_k` 调小

- 延迟和计算量降低。
- 正确 Child 可能在单路截断时被丢弃，RRF 无法恢复。

#### `top_k` 调大

- 更多 Child 能映射为 Parent，Recall 可能提高。
- 噪声、Parent 数量和 Context 长度压力增加。

#### `top_k` 调小

- 后续 Context 更精炼、生成成本更低。
- 融合排名稍靠后的正确 Child 可能被截掉。

### Reranker 开启时的额外一层

`_pool_size(top_k)` 在 reranker 开启时返回：

```python
max(top_k, reranker.pool_size)
```

默认 reranker pool 配置为 20。因此启用 reranker 后，RRF 会先保留更大的结果池给 Cross-Encoder，再由 `_apply_rerank()` 返回最终 `top_k`。

当前项目 reranker 默认关闭。

### Metadata Filtered Search 的特殊情况

FAISS 无法下推过滤条件，所以 `metadata_filtered_search()` 将候选规模扩大为：

```python
min(
    len(self.chunks),
    max(self.candidate_k, top_k * 5),
)
```

然后先 Hybrid，再过滤。

Milvus 则把 `expr` 同时挂到 Dense 和 Sparse 请求，在合法范围内检索和融合。

## 十三、10. 哪些情况下 RRF 仍然会失败

## 1. 正确文档没有进入任何一路的候选池

RRF 只能重排已有候选，不能生成新候选。

```text
正确 Child：Dense rank 25，BM25 rank 40
candidate_k：10
```

它在融合前已经被两路截掉，RRF 看不到它。

## 2. Dense 与 BM25 犯同一个错误

例如一个错误菜谱同时拥有语义相似和大量关键词重合，两路都把它排第一。RRF 会把“双路一致”视为强信号，反而强化错误。

## 3. Query 包含否定、排除或安全约束

RRF 不理解“不要”“不含”“排除”。如果 Dense 和 BM25 都因“花生”一词召回含花生菜谱，RRF 不会判断这违反了“不含花生”。

## 4. 一路结果质量很差，但仍被等权对待

当前 RRF 没有 Query-aware 权重。例如对精确菜名查询，BM25 可能比 Dense 更可信；对抽象描述查询，Dense 可能更可信。当前主融合始终等权累加名次贡献。

## 5. 排名差距无法表达真实置信度差距

RRF 只看到 rank 1 和 rank 2，不知道：

- 第一名只是略高于第二名；还是
- 第一名远高于第二名。

有价值的原始 score margin 被丢弃。

## 6. Chunking 已经切坏了证据

如果一个 Child 缺少关键上下文，Dense 和 BM25 对它的排序都可能不可靠。RRF 不会修复 Chunk 内容本身。

## 7. Parent 层面的重复没有参与融合

RRF 按 `chunk_id` 去重，而不是按 `parent_id` 聚合。同一篇 Parent 的多个 Child 可以分别占据融合结果位置。

Parent 层的命中计数与去重由后续 `get_parent_documents()` 完成，不属于 RRF。

## 8. FAISS 过滤发生在召回之后

带 metadata/visibility 条件时，FAISS 先召回融合再过滤。合法目标如果没有进入扩大的候选池，RRF 也无法补回。

## 9. 分词或 Embedding 模型不理解领域表达

Dense 和 BM25 的基础表示如果都不好，融合不会凭空产生领域知识。

## 十四、具体菜谱 Query 演算示例

## Query

```text
红烧鲤鱼怎么做？
```

以下排名是为了展示当前 `_rrf_rerank()` 的计算方式而构造的示例，不是本机实际运行 BGE、FAISS 或 Milvus 得到的测量结果。

为便于演算，只展示每路前三名；项目默认实际 `candidate_k=10`。

### Dense 排名

| Dense rank | Child | 可能原因 |
|---:|---|---|
| 1 | 红烧草鱼 | “红烧 + 鱼”的整体语义很接近 |
| 2 | 红烧鲤鱼 | 正确目标，语义也高度相关 |
| 3 | 清蒸鲤鱼 | 同为鲤鱼做法，但烹饪方式不同 |

### BM25 排名

| BM25 rank | Child | 可能原因 |
|---:|---|---|
| 1 | 红烧鲤鱼 | 精确共享“红烧”“烧鲤”“鲤鱼”等 token |
| 2 | 清蒸鲤鱼 | 共享“鲤鱼” |
| 3 | 红烧草鱼 | 共享“红烧”和“鱼” |

### 使用 `rrf_k=60` 融合

RRF 公式：

```text
RRF(document) = Σ 1 / (60 + rank_in_each_list)
```

#### 红烧鲤鱼

```text
Dense rank 2 + BM25 rank 1
= 1/62 + 1/61
≈ 0.016129 + 0.016393
= 0.032522
```

#### 红烧草鱼

```text
Dense rank 1 + BM25 rank 3
= 1/61 + 1/63
≈ 0.016393 + 0.015873
= 0.032266
```

#### 清蒸鲤鱼

```text
Dense rank 3 + BM25 rank 2
= 1/63 + 1/62
≈ 0.015873 + 0.016129
= 0.032002
```

### 融合结果

| RRF rank | Child | RRF score |
|---:|---|---:|
| 1 | 红烧鲤鱼 | 0.032522 |
| 2 | 红烧草鱼 | 0.032266 |
| 3 | 清蒸鲤鱼 | 0.032002 |

这个例子体现了 RRF 的价值：Dense 将语义非常相似的“红烧草鱼”排在第一，但 BM25 的精确菜名信号把正确的“红烧鲤鱼”提升到融合第一。

它也体现了 RRF 的限制：三个候选都被两路召回且名次接近，因此最终分差非常小。

## 十五、RRF 无法修复的 Bad Case

## Query

```text
不含花生的宫保鸡丁怎么做？
```

假设知识库中：

- 标准“宫保鸡丁”菜谱明确包含花生。
- 另有一个不含花生的替代做法，但标题和措辞不明显，或相关 Child 位于两路候选池之外。

可能出现：

### Dense 排名

```text
1. 标准宫保鸡丁（含花生）
2. 宫保鸡丁传统做法（含花生）
3. 辣子鸡
```

### BM25 排名

```text
1. 标准宫保鸡丁（含花生）
2. 宫保鸡丁传统做法（含花生）
3. 花生鸡丁
```

错误的标准菜谱在两路都是第一。RRF 会给它：

```text
1/61 + 1/61
```

使它更稳地排在融合第一。

### 为什么 RRF 修不了

RRF 只知道：

```text
这个 Child 被 Dense 排第一
这个 Child也被 BM25 排第一
```

它不知道：

```text
用户说的是“不含花生”
文档却明确“含花生”
```

如果正确替代菜谱没进入 Dense 或 BM25 的 `candidate_k`，RRF 连重新排序它的机会都没有。

这类问题需要在 RRF 之外解决，例如：

- 把过敏原或禁用食材做成结构化 metadata 并在检索前过滤。
- 用能理解 Query-Document 关系的 reranker 验证否定约束。
- 改善 Query rewrite / expansion，让“无花生替代”成为明确检索意图。
- 扩大候选池并配合评测，而不是只依赖双路一致。

这些是优化方向，不是当前代码已经完整实现的能力。当前 metadata filter 支持的字段中没有过敏原字段。

## 十六、RRF 与可选 Reranker 的关系

当前项目的主链不是简单的：

```text
Dense + BM25 → RRF → Top-K
```

更完整地说是：

```text
Dense + BM25
→ 主 RRF
→ 可选 Cross-Encoder Reranker
→ Cross-Encoder 名次与主召回名次再做一次 RRF
→ Top-K
```

位置：

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`_apply_rerank()`

当 reranker 启用时，它先调用：

```python
reranked = self.reranker.rerank(query, documents)
```

随后将 Cross-Encoder rank 与主召回 rank 再融合：

```python
1 / (self.rrf_k + ce_rank)
+ 1 / (self.rrf_k + recall_rank)
```

源码注释给出的原因是：当前语料中单独使用 Cross-Encoder 会削弱 BM25 的精确菜名信号。

不过 `config.py` 默认：

```python
rerank_enabled = False
```

因此默认运行链路只有主 Dense/BM25 RRF，不会进入二次融合。

## 十七、项目实现的优点与局限

### 优点

- Dense 与 BM25 的互补关系明确，不依赖单一路径。
- FAISS 和 Milvus 共用统一的 `VectorStoreBackend` 抽象。
- RRF 不要求手工对齐 L2、COSINE 和 BM25 的分数尺度。
- 使用稳定 `chunk_id` 做跨列表去重。
- `candidate_k` 与 `top_k` 分离，给融合留出候选空间。
- Milvus 可以在服务端同时执行过滤、双路召回和融合。
- 测试覆盖了 RRF 去重、同分顺序和候选池行为。

### 局限

- 主 RRF 两路固定等权，不能根据 Query 类型动态调整。
- RRF 丢弃原始 score 和置信度差距。
- Milvus `RRFRanker(60)` 写死，未使用 `RAG_RRF_K`。
- RRF 只按 Child 聚合，不按 Parent 聚合。
- FAISS 的 metadata filter 是召回后过滤，存在过滤目标被提前漏掉的风险。
- 候选池之外的正确结果无法被 RRF 找回。
- 两路高度相关地犯错时，RRF 可能强化错误。

## 十八、面试时可以如何概括

> 这个项目的 Hybrid Search 不是简单把向量分数和 BM25 分数相加。FAISS 的 Dense 使用 L2 distance，BM25 使用另一套查询相关分数，两者方向和尺度都不同，所以项目使用 RRF，只根据每条结果在各自列表中的 rank 做融合。FAISS 模式下，Dense 来自 `FaissBackend.similarity_search()`，BM25 来自本地 `BM25Retriever.invoke()`，然后由 `_rrf_rerank()` 在 Python 中按 `chunk_id` 去重并计算分数。Milvus 模式下，Dense、Sparse 和 `RRFRanker(60)` 都在服务端执行。
>
> `candidate_k` 是两路进入融合前的候选数，默认 10；`top_k` 是融合后进入 Parent Retrieval 的 Child 数，默认 3。候选池比最终结果大，是为了让两路中排名稍后的共同候选有机会浮上来。RRF 的优势是无需校准两种原始分数，但它只看排名，不理解文本，也无法找回候选池之外的文档。如果 Dense 和 BM25 同时犯错，RRF甚至可能强化错误，所以它解决的是多路排序融合，不是 Query 理解或事实验证。

## 十九、源码事实边界

当前源码可以确认：

- FAISS 模式分别调用 FAISS Dense 和本地 BM25。
- FAISS 的 RRF 由 `_rrf_rerank()` 在 Python 中执行。
- RRF 使用 rank 和 `chunk_id`，不使用原始 Dense/BM25 score。
- Milvus 构造 Dense 与 Sparse 两个 `AnnSearchRequest`。
- Milvus 使用服务端 `RRFRanker(60)`。
- 默认 `candidate_k=10`、`top_k=3`、`rrf_k=60`。
- Reranker 默认关闭；开启后还有一轮 CE rank 与 recall rank 的 RRF。

以下内容需要保留边界：

- 示例中的 Dense/BM25 排名是按真实代码逻辑构造的演算，不是实际模型测量结果。
- 当前代码没有记录或返回 FAISS Dense 与本地 BM25 的原始 score，因此无法从一次普通返回结果反推出两路原始置信度。
- Milvus 返回 Hit 的 `distance` 被代码改名为 `rrf_score`；具体服务端数值语义由当前 Milvus `RRFRanker` 实现决定。
- RRF 对各类 Query 的真实收益必须依赖 evaluation；源码注释中的 MRR 是整体实验结论，不是所有单条 Query 的保证。
