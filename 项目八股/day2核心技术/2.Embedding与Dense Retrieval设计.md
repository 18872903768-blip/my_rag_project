# Embedding 与 Dense Retrieval 设计

本文基于当前仓库源码，梳理 Embedding 与 Dense Retrieval 的真实数据流。

范围说明：

- 分析的是当前版本目录中的 `config.py`、`main.py` 和 `rag_modules/`，不是 `*_old.py` 或 `rag_modules_old/`。
- 重点是直觉、调用关系和工程作用，不展开复杂数学推导。
- 文中会区分“源码事实”和“工程解释”。

---

## 一、先建立直觉

Embedding 模型把一段文本转换成一个向量。语义相近的文本，其向量通常也更接近。

在这个项目里，可以把 Dense Retrieval 理解成：

```text
建库阶段
Child Chunk 文本
→ Embedding 模型
→ 文档向量
→ 写入 FAISS 或 Milvus

查询阶段
用户 Query（Classic 中通常是 rewrite 后的 Query）
→ 同一个 Embedding 模型
→ Query 向量
→ 在向量库中寻找最接近的 Child Chunk
→ 作为 Hybrid Retrieval 的 Dense 候选
```

它擅长处理“说法不同、含义相近”的问题。例如，文档写的是“用小火慢炖”，用户问的是“怎样避免肉炖得太柴”，两边未必共享完全相同的关键词，但语义向量仍可能接近。

不过，本项目的默认在线检索并不是只用 Dense Retrieval。`RetrievalOptimizationModule.hybrid_search()` 会把 Dense 与 BM25 组合，再通过 RRF 融合。因此 Dense 是检索栈的一条重要召回通道，而不是完整检索系统的全部。

## 二、真实调用链总览

### 1. 系统初始化

```text
config.py
RAGConfig.from_env()
  ↓
main.py
RAGSystem.initialize_system()
  ↓
rag_modules/index_construction.py
IndexConstructionModule(...)
  ↓ 懒加载
IndexConstructionModule.setup_embeddings()
  ↓
HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    model_kwargs={"device": "cpu", "revision": ...},
    encode_kwargs={"normalize_embeddings": True}
)
```

### 2. 文档建库

```text
main.py
RAGSystem.build_knowledge_base()
  ↓
DataPreparationModule.load_documents()
  ↓
DataPreparationModule.chunk_documents()
  ↓
all_chunks = text chunks + image caption chunks
  ↓
  ├─ FAISS:
  │  IndexConstructionModule.build_vector_index(all_chunks)
  │  → FAISS.from_documents(...)
  │  → IndexFlatL2
  │
  └─ Milvus:
     MilvusVectorStore.build_index(all_chunks)
     → embeddings.embed_documents(...)
     → FLOAT_VECTOR 字段
     → HNSW + COSINE
```

### 3. 查询检索

Classic 模式下：

```text
main.py
RAGSystem._ask_question_inner(question)
  ↓
query_router(question)
  ↓
list route: 使用原始 question
其他 route: query_rewrite(question)
  ↓
RAGSystem.retrieve(query)
  ↓
RetrievalOptimizationModule.hybrid_search(...)
  ↓
  ├─ FAISS:
  │  FaissBackend.similarity_search(query)
  │  → LangChain FAISS.similarity_search(query)
  │  → 内部生成 Query embedding
  │  → L2 搜索
  │
  └─ Milvus:
     MilvusVectorStore.hybrid_search(query)
     → embeddings.embed_query(query)
     → Dense AnnSearchRequest
     → COSINE 搜索
```

如果存在 metadata 或 visibility 条件，会进入 `metadata_filtered_search()`；但 Dense 向量的生成方式不变。区别在于 Milvus 可以将过滤表达式下推到服务端，FAISS 分支则在召回后过滤。

## 三、逐项回答

## 1. 使用什么 Embedding 模型

### 源码事实

默认模型为：

```text
BAAI/bge-small-zh-v1.5
```

代码位置：

- 文件：`config.py`
- 类：`RAGConfig`
- 字段：`embedding_model`
- 默认值：`"BAAI/bge-small-zh-v1.5"`

同时固定了模型 revision：

```text
7999e1d3359715c523056ef9478215996d62a620
```

对应字段是 `RAGConfig.embedding_revision`。

`RAGConfig.from_env()` 允许通过以下环境变量覆盖：

- `RAG_EMBEDDING_MODEL`
- `RAG_EMBEDDING_REVISION`
- `RAG_EMBEDDING_DEVICE`
- `RAG_NORMALIZE_EMBEDDINGS`

因此，准确说法是：**源码默认使用 `BAAI/bge-small-zh-v1.5`，实际运行值可以被环境变量覆盖。**

### 工程解释

该模型面向中文语义表示，适合当前中文菜谱语料。固定 revision 的价值是保证重建索引时尽量使用相同模型版本，避免“模型名称没变，但模型文件变化”导致文档向量与 Query 向量不兼容或结果漂移。

当前代码没有把向量维度硬编码为某个数字。`IndexConstructionModule._get_embedding_dimension()` 和 `MilvusVectorStore._get_embedding_dimension()` 都通过：

```python
embed_query("维度检查")
```

在运行时探测维度。

## 2. 在哪里初始化

Embedding 初始化分成两层。

### 第一层：创建索引模块

- 文件：`main.py`
- 类：`RAGSystem`
- 函数：`initialize_system()`

它使用配置创建：

```python
IndexConstructionModule(
    model_name=self.config.embedding_model,
    model_revision=self.config.embedding_revision,
    device=self.config.embedding_device,
    normalize_embeddings=self.config.normalize_embeddings,
    index_save_path=self.config.index_save_path,
)
```

这一步只保存配置，不一定立刻加载模型。

### 第二层：真正加载模型

- 文件：`rag_modules/index_construction.py`
- 类：`IndexConstructionModule`
- 函数：`setup_embeddings()`

该函数懒加载 `HuggingFaceEmbeddings`：

```python
HuggingFaceEmbeddings(
    model_name=self.model_name,
    model_kwargs=model_kwargs,
    encode_kwargs={"normalize_embeddings": self.normalize_embeddings},
)
```

`setup_embeddings()` 如果发现 `self.embeddings` 已存在，会直接复用，不重复初始化。

代码还实现了本地缓存优先策略：先尝试 Hugging Face 离线加载；本地没有缓存且未强制离线时，再恢复在线模式下载。环境变量 `RAG_HF_OFFLINE` 可以强制只用本地缓存。

### 后端如何获得同一个 Embedding 实例

- Milvus 分支：`RAGSystem.build_knowledge_base()` 调用 `self.index_module.setup_embeddings()`，并将结果传给 `MilvusVectorStore(embeddings=...)`。
- FAISS 分支：`IndexConstructionModule.build_vector_index()` 将 `self.setup_embeddings()` 传给 `FAISS.from_documents()`。

因此，文档编码与 Query 编码复用同一套模型配置。

## 3. 文档什么时候生成 Embedding

文档在**构建或增量更新向量索引时**生成 embedding，不是在 Markdown 被加载时生成。

建库入口：

- 文件：`main.py`
- 类：`RAGSystem`
- 函数：`build_knowledge_base()`

该函数先产生：

```python
all_chunks = chunks + image_chunks
```

进入索引的对象是 Child Chunk，包括文本 Child 和启用图片摄取后产生的图片描述 Child。

### FAISS 分支

- 文件：`rag_modules/index_construction.py`
- 类：`IndexConstructionModule`
- 函数：`build_vector_index()`

调用：

```python
FAISS.from_documents(
    documents=chunks,
    embedding=self.setup_embeddings(),
    ids=self._storage_ids(chunks),
)
```

**源码边界：** 当前仓库没有在 FAISS 分支显式写出 `embed_documents()`；它把 `Document` 列表与 Embedding 对象交给 LangChain 的 `FAISS.from_documents()`，批量编码发生在该依赖内部。

如果已有索引的 manifest、语料指纹、Embedding 配置和索引文件校验全部匹配，`load_index()` 会复用已有向量，不会重新编码整个语料。

### Milvus 分支

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 函数：`build_index()`

源码显式按 64 条一批编码：

```python
vectors = self.embeddings.embed_documents(
    [chunk.page_content for chunk in batch]
)
```

随后 `_rows_for_insert()` 将向量与 Chunk 的文本、`chunk_id`、`parent_id` 等字段一起写入 Milvus。

增量添加时：

- FAISS：`IndexConstructionModule.add_documents()` → LangChain `vectorstore.add_documents()`。
- Milvus：`MilvusVectorStore.add_documents()` → `embed_documents()` → `client.insert()`。

## 4. Query 什么时候生成 Embedding

Query embedding 在**真正执行 Dense 搜索时**生成，而不是 API 刚收到 Query 时生成。

Classic 模式下，前面可能已经发生：

1. `GenerationIntegrationModule.query_router(question)`。
2. 非 `list` route 执行 `query_rewrite(question)`。
3. `RAGSystem.retrieve(rewritten_query, ...)`。
4. Retrieval 层选择普通 Hybrid Search 或 Metadata Filtered Search。
5. 进入 Dense 分支时才生成 Query embedding。

所以，Classic 模式中被编码的通常是 `rewritten_query`；但 `list` route 不执行 rewrite，此时编码的是原始问题。

### FAISS 分支

真实仓库调用链：

```text
RetrievalOptimizationModule.hybrid_search()
→ FaissBackend.similarity_search(query)
→ self.vectorstore.similarity_search(query, k=k)
```

仓库将字符串 Query 交给 LangChain FAISS。Query embedding 在该封装内部通过已配置的 Embedding 对象生成。

**源码边界：** `FaissBackend` 自己没有显式调用 `embed_query()`，所以不能把这一步说成是本项目手写的编码逻辑；它是 LangChain FAISS 封装承担的。

### Milvus 分支

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 函数：`similarity_search()`、`hybrid_search()`

源码显式调用：

```python
vector = self.embeddings.embed_query(query)
```

然后将向量传入 `client.search()`，或作为 Dense `AnnSearchRequest` 的 `data=[vector]`。

注意：`_get_embedding_dimension()` 还会用固定文本“维度检查”做一次探测编码。这是初始化 Schema/manifest 所需的维度检查，不是用户 Query 的检索编码。

## 5. `normalize_embeddings` 是否开启

### 源码事实

默认开启：

```python
normalize_embeddings: bool = True
```

代码位置：

- `config.py` → `RAGConfig.normalize_embeddings`
- `config.py` → `RAGConfig.from_env()`
- `main.py` → `RAGSystem.initialize_system()`
- `rag_modules/index_construction.py` → `IndexConstructionModule.setup_embeddings()`

最终传入：

```python
encode_kwargs = {"normalize_embeddings": self.normalize_embeddings}
```

环境变量 `RAG_NORMALIZE_EMBEDDINGS` 可以关闭它。

### 工程解释

开启后，每个文档向量和 Query 向量都会被缩放到相同长度。这样，相似度排序主要由向量方向决定，而不会被向量自身长度干扰。

它对 FAISS 的 `IndexFlatL2` 尤其重要，因为归一化后，L2 距离排序与 cosine 相似度排序等价。若关闭归一化，这个等价关系不再成立。

## 6. FAISS 使用什么距离度量

### 源码事实

FAISS 使用：

```text
IndexFlatL2
metric = L2
```

证据位置：

- 文件：`rag_modules/index_construction.py`
- 函数：`IndexConstructionModule.build_manifest()`
- manifest 字段：`"faiss": {"index_type": "IndexFlatL2", "metric": "L2"}`

`build_vector_index()` 使用 LangChain `FAISS.from_documents()` 构建默认索引；`load_index()` 还会检查：

```python
type(index).__name__ == manifest["faiss"]["index_type"]
```

测试 `tests/test_index_construction.py` 也断言 manifest 中的索引类型为 `IndexFlatL2`、度量为 `L2`。

### 工程解释

`IndexFlatL2` 是精确搜索，不是近似索引。它会在已有向量中按 L2 距离寻找最近项。优点是实现简单且检索结果没有近似索引带来的召回损失；代价是语料规模增大后，查询计算量和内存压力会更明显。

## 7. Milvus 使用什么 metric

### 源码事实

Milvus Dense 向量默认使用：

```text
COSINE
```

代码位置：

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 构造函数参数：`metric_type: str = "COSINE"`

该值被用于三个地方：

1. `_create_collection()` 创建 Dense HNSW 索引时的 `metric_type`。
2. `similarity_search()` 的 `client.search(..., search_params={"metric_type": self.metric_type})`。
3. `hybrid_search()` 中 Dense `AnnSearchRequest` 的 `param={"metric_type": self.metric_type}`。

当前 `main.py` 创建 `MilvusVectorStore` 时没有覆盖 `metric_type`，所以实际默认值就是 `COSINE`。

Milvus 的 Sparse/BM25 字段使用另一个 metric：`BM25`。它不属于 Dense metric，不应与 Dense 的 `COSINE` 混为一谈。

Milvus Dense 索引类型是 `HNSW`。本节只说明它是近似向量索引，不展开其参数原理。

## 8. 为什么 FAISS 的 L2 与归一化 Embedding 下的 cosine ranking 有关系

不需要复杂推导，只需抓住一个前提：**两个向量都已经归一化为长度 1。**

此时：

```text
两向量方向越接近
→ cosine 相似度越大
→ L2 距离越小
```

更精确但仍简化地写：

```text
L2 距离的平方 = 2 - 2 × cosine 相似度
```

因此：

- 按 L2 从小到大排列；
- 按 cosine 从大到小排列；

得到相同的邻居顺序。

这解释了本项目为什么可以同时采用：

- Embedding：`normalize_embeddings=True`
- FAISS：`IndexFlatL2`

而仍然得到与 cosine 相似度一致的 ranking。

必须注意：

- 这个结论依赖归一化。
- 如果文档向量或 Query 向量没有归一化，向量长度会进入 L2 距离，排序不一定与 cosine 相同。
- 这说明的是排序关系，不是说 L2 距离数值与 cosine 相似度数值相等。

## 9. Dense Retrieval 擅长解决什么问题

### 1. 用户与文档用词不同，但语义相近

例如：

```text
Query：怎样让肉吃起来不柴？
Document：小火慢炖能够保持肉质软嫩。
```

关键词重合可能不多，但 Dense Retrieval 有机会识别“肉不柴”和“肉质软嫩”的语义关系。

### 2. 自然语言描述和文档表达存在同义改写

例如“新手容易做”“操作简单”“适合初学者”之间不是严格字符串匹配，但语义接近。

### 3. Query 是描述性意图，而不是准确菜名

例如“适合夏天的清爽凉菜”“想做一道不太油的家常菜”。这类 Query 往往没有一个必须精确匹配的词，Dense 召回比纯关键词更有价值。

### 4. 图片描述参与文本检索

图片摄取模块生成的 caption 也作为 Child Chunk 进入相同向量索引。用户的文本 Query 可以通过语义向量检索图片描述，实现 text-to-image 的 Dense 召回通路。

### 5. 为 Hybrid Retrieval 补足 BM25 的语义召回

当前项目让 Dense 负责“语义相近”，BM25 负责“词面精确”，再使用 RRF 融合。Dense 的主要价值不是单独包打天下，而是补充关键词检索容易漏掉的候选。

## 10. Dense Retrieval 的典型失败情况

以下是工程层面的典型风险。其中“项目如何缓解”均能在当前源码中找到相应设计；具体某条 Query 是否一定失败，需要通过评测确认。

### 1. 精确实体名称、菜名或罕见词

Query 明确询问一个精确菜名时，Dense 可能召回语义相似但不是目标菜品的文档。

当前项目的缓解方式：`RetrievalOptimizationModule.hybrid_search()` 同时使用 BM25，并通过 RRF 合并结果。`config.py` 的注释还记录了当前菜谱评测中 BM25 的精确菜名信号很强。

### 2. 数字、用量、型号和短字符串

“200 克”“焖 15 分钟”之类的信息对答案很关键，但 embedding 未必能稳定区分非常接近的数字或细粒度差异。

当前项目的缓解方式：BM25 可以提供词面召回，但是否能完全解决仍需针对数字问题做评测。

### 3. 否定、排除和复杂约束

“不要辣”“不含花生”“不是红烧做法”中的否定关系，可能被语义相近内容干扰，召回含有对应关键词但不满足否定条件的文档。

当前项目只对 `category`、`difficulty` 等部分字段做结构化 metadata filter；其他自然语言约束仍依赖检索和生成模型理解。

### 4. 语义接近，但业务答案不同

两道菜可能都有相似的制作步骤，向量很接近，但用户真正问的是某一道特定菜。Dense 容易产生“主题正确、对象错误”的候选。

当前项目用 BM25 精确词信号、metadata filter、Parent 回溯和可选 reranker 共同缓解，但不能保证消除。

### 5. Query 太长或包含多个意图

Embedding 会把整条 Query 压缩成一个向量。多个条件和意图可能彼此稀释，导致最关键的检索意图不突出。

当前 Classic 链路在非 `list` route 中先执行 `query_rewrite()`，有机会把问题改写得更适合检索；具体改写是否改善召回，需要评测确认。

### 6. Chunk 边界导致语义不完整

如果答案信息跨越多个 Child，单个 Child embedding 可能只表达其中一部分。Dense 可以找到相关 Child，却未必找齐完整事实。

当前项目通过 Parent-Child Retrieval，在检索 Child 后恢复完整 Parent 供生成使用。但如果相关 Child 没有进入候选池，Parent 回溯也无法补救召回失败。

### 7. 模型与语料领域不匹配

通用中文 embedding 对非常专业的领域术语可能表示不足。当前菜谱领域相对日常，但换成法律、医学或企业专有知识后，必须重新评测模型。

### 8. Approximate Search 自身的召回损失

FAISS 当前使用 `IndexFlatL2`，属于精确搜索；Milvus 使用 HNSW，属于近似搜索。在大规模下近似索引更快，但有可能漏掉真实最近邻。

当前代码没有在 Query 搜索请求中显式设置 HNSW 查询参数；实际搜索行为还受 Milvus 默认值和服务端版本影响。仅凭当前仓库，无法确认具体查询阶段的 `ef` 值。

## 四、FAISS 与 Milvus 的 Dense Retrieval 对比

| 维度 | FAISS 分支 | Milvus 分支 |
|---|---|---|
| 后端入口 | `IndexConstructionModule.build_vector_index()` | `MilvusVectorStore.build_index()` |
| 文档编码 | `FAISS.from_documents()` 内部执行 | `embed_documents()` 显式执行 |
| Query 编码 | LangChain FAISS 封装内部执行 | `embed_query()` 显式执行 |
| Dense 索引 | `IndexFlatL2` | `HNSW` |
| Dense metric | `L2` | `COSINE` |
| 是否近似搜索 | 否，精确搜索 | 是，近似搜索 |
| Metadata 过滤 | 不能下推，召回后过滤 | `expr` 下推服务端 |
| Hybrid 执行位置 | 本地 Dense + 本地 BM25 + 本地 RRF | Milvus 内 Dense + BM25 + RRF |
| 适合场景 | 本地、小规模、简单部署 | 服务化、规模化、服务端过滤和混合检索 |

### 一个重要的一致性点

两个后端都使用由 `IndexConstructionModule.setup_embeddings()` 创建的同一 Embedding 配置。因此切换后端时，语义编码模型本身不变，变化的是索引结构、距离计算方式和检索执行位置。

## 五、Dense Retrieval 在整个项目中的真实位置

不要把当前项目介绍成“用户 Query 经过向量搜索后直接生成答案”。真实结构是：

```text
Query router / rewrite
        ↓
metadata + visibility 条件
        ↓
Hybrid Retrieval
  ├─ Dense Retrieval
  │    └─ Embedding + FAISS/Milvus Vector Search
  └─ BM25 Retrieval
        ↓
RRF Fusion
        ↓
可选 Reranker（默认关闭）
        ↓
Top-K Child Chunks
        ↓
Parent Document 恢复
        ↓
Context + Generation
```

所以 Dense Retrieval 改善的是候选召回，尤其是语义改写、同义表达和描述性 Query；最终结果还受到 BM25、RRF、过滤、Top-K、Parent 回溯与 Generation 的共同影响。

## 六、五个最重要的参数 / 设计点

## 1. `embedding_model` 与 `embedding_revision`

当前默认：

```text
model = BAAI/bge-small-zh-v1.5
revision = 7999e1d3359715c523056ef9478215996d62a620
```

影响：

- 决定语义表示质量、语言和领域适配能力。
- 改模型通常必须重建全部文档向量。
- 固定 revision 提高索引的可复现性。
- 更大的模型可能提高语义召回，也会增加建库时间、查询延迟和内存占用；是否提升必须用当前语料评测。

## 2. `normalize_embeddings=True`

影响：

- 保证 FAISS L2 排序与 cosine 排序一致。
- 关闭后，向量长度会影响 L2，现有相似度语义发生变化。
- 修改该参数会改变索引签名；FAISS manifest 不匹配时会触发重建。

## 3. 后端及 Dense metric

当前默认后端：

```text
backend = milvus
```

度量组合：

```text
FAISS  → IndexFlatL2 + L2
Milvus → HNSW + COSINE
```

影响：

- FAISS 更简单且是精确搜索，但扩展性有限。
- Milvus 支持近似索引、服务端过滤和 Hybrid Search，更适合规模化。
- metric 必须和 embedding 生成方式保持一致，不能只改搜索 metric 而复用不兼容的旧索引。

## 4. `candidate_k=10`

位置：`config.py` → `RAGConfig.candidate_k`。

作用：Dense 与 BM25 各自需要召回多少候选，随后再进行融合。

- 调大：通常提高 Recall，为 RRF 或 reranker 提供更多候选；同时增加检索、融合和可能的重排成本。
- 调小：速度更快，但相关 Child 可能在融合前就被截掉。

Milvus 的 `hybrid_search()` 会使用 `candidate_k` 确定 Dense 与 Sparse 请求的候选规模；FAISS 分支则用它作为 `similarity_search()` 的 `k`。

## 5. Child 级建索引 + `top_k=3`

这是比单纯 metric 更重要的系统设计点：被编码和检索的是 Child Chunk，不是完整 Parent。

- Child 较聚焦，Dense 相似度更容易突出局部相关主题。
- 检索后再通过 `parent_id` 恢复 Parent，给生成阶段更完整的上下文。
- `top_k=3` 决定最终保留多少个融合后的 Child，而不是 Dense 单路最初只找 3 个。
- `top_k` 太小容易漏掉相关 Parent；太大会增加噪声、Parent 数量和 Context 压力。

## 七、A. 面试口述版本

> 这个项目默认使用 `BAAI/bge-small-zh-v1.5` 做中文文本向量化，并固定模型 revision 保证索引可复现。Embedding 在 `IndexConstructionModule.setup_embeddings()` 中懒加载，默认运行在 CPU，同时开启 `normalize_embeddings`。建库时，系统不是给整篇 Parent 文档编码，而是给 Markdown 切分后的文本 Child 和图片 caption Child 编码。
>
> 后端可以选择 FAISS 或 Milvus。FAISS 通过 LangChain 的 `FAISS.from_documents()` 生成文档向量，索引是 `IndexFlatL2`；因为向量已经归一化，L2 从小到大的排序与 cosine 从大到小的排序一致。Milvus 分支则显式调用 `embed_documents()`，将向量写进 FLOAT_VECTOR 字段，并使用 HNSW 索引和 COSINE metric。
>
> 查询时不会在 API 入口立刻生成向量。Classic 链路先做 route，非列表类问题还会先 rewrite，然后在 Retrieval 层真正进入 Dense Search 时编码 Query。FAISS 把字符串交给 LangChain 封装内部编码，Milvus 则在 `similarity_search()` 或 `hybrid_search()` 中显式调用 `embed_query()`。
>
> Dense Retrieval 的优势是解决用户表达和文档用词不一致的问题，例如同义改写和描述性需求。但它对精确菜名、数字、否定条件和复杂约束可能不稳定。所以项目没有把 Dense 当成唯一检索方式，而是让它与 BM25 双路召回，再用 RRF 融合。最终取得 Top-K Child 后，再根据 `parent_id` 恢复完整 Parent 给 LLM。这个设计兼顾了局部语义定位和生成上下文完整性。

---

## 八、B. 五个最重要的参数 / 设计点速记

1. **模型与版本**：`BAAI/bge-small-zh-v1.5` + 固定 revision；换模型后应重建索引。
2. **向量归一化**：`normalize_embeddings=True`；它使 FAISS L2 ranking 与 cosine ranking 一致。
3. **后端度量**：FAISS 为 `IndexFlatL2/L2`，Milvus 为 `HNSW/COSINE`。
4. **候选池**：`candidate_k=10`；控制 Dense/BM25 融合前的 Recall 与成本。
5. **检索粒度**：Child 建索引、Top-K Child 检索、Parent 恢复；兼顾定位精度和上下文完整性。

## 九、源码事实边界

以下结论可以从当前仓库直接确认：

- 默认 Embedding 模型、revision、device 与归一化开关。
- `HuggingFaceEmbeddings` 的初始化参数。
- Milvus 文档和 Query 的显式编码位置。
- FAISS 通过 `FAISS.from_documents()` 建库、通过 `similarity_search(query)` 查询。
- FAISS manifest 与加载校验要求 `IndexFlatL2/L2`。
- Milvus Dense 使用 `HNSW/COSINE`。
- 当前默认检索是 Dense + BM25 + RRF，而非纯 Dense。

以下内容必须保留边界：

- FAISS 分支的 `embed_documents()` 与 `embed_query()` 由 LangChain FAISS 封装内部调用，当前仓库没有手写这两个调用。
- 当前仓库动态探测 embedding 维度，没有在业务源码中硬编码具体维度。
- Milvus Query 阶段没有显式设置 HNSW 的 `ef`；具体采用什么值，当前代码不足以确认。
- Dense 的失败类型是工程风险判断；某一类 Query 在本语料上的真实失败率，需要由 evaluation 数据确认。
