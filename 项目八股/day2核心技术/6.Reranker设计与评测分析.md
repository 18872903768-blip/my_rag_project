# Reranker 设计与评测分析

本文基于当前仓库真实源码、README、配置注释和 `.artifacts/eval/` 中的评测产物，分析 Cross-Encoder Reranker 的实现、位置、实际效果和取舍。

范围说明：

- 分析当前版本的 `rag_modules/reranker.py`、`rag_modules/retrieval_optimization.py`、`main.py`、`config.py`、`eval/run_eval.py` 及相关测试和评测产物。
- 当前代码保留 Reranker 能力，但默认不进入主检索链路。
- “纯 CE”是项目做过的一组历史对照实验；当前启用 Reranker 后执行的是“CE rank + recall rank 二次融合”，不是纯 CE 独立定序。

---

## 一、先建立直觉

Dense 和 BM25 的第一阶段检索更像“快速海选”：

```text
全库 Child Chunks
→ Dense + BM25
→ RRF
→ 一小批候选
```

Cross-Encoder 更像“对候选逐个面试”：

```text
Query + Candidate 1 文本 → 一个相关性分数
Query + Candidate 2 文本 → 一个相关性分数
Query + Candidate 3 文本 → 一个相关性分数
...
```

Embedding/Dense Retrieval 会分别编码 Query 和 Document，所以文档向量可以提前建好；Cross-Encoder 则把 Query 与 Document 作为一个文本对联合输入模型，让两边 token 直接交互，通常能做更细粒度的相关性判断。

但代价也很直接：

- 每次 Query 都要重新计算每个 Query-Document pair。
- 文档无法像 Dense embedding 那样全部提前离线算好。
- 候选越多，推理次数和延迟越高。

所以真实 pipeline 不是全库 Cross-Encoder，而是：

```text
Retriever 负责 Recall
→ Reranker 只处理候选池
→ 最终 Top-K
```

当前项目更重要的结论是：**理论上表达能力更强，不等于在当前数据分布和指标上一定更好。**

## 二、真实调用链

```text
config.py
RAGConfig.rerank_enabled / rerank_model / rerank_pool
  ↓
main.py
RecipeRAGSystem._build_reranker()
  ↓ disabled
  ├─ False → return None
  │
  ↓ enabled
RerankerModule(
    model_name="BAAI/bge-reranker-base",
    pool_size=20,
    device="cpu"
)
  ↓
RetrievalOptimizationModule(reranker=...)
  ↓
hybrid_search()
  ↓
Dense + BM25 → 主 RRF 候选序
  ↓
_apply_rerank(query, documents, top_k)
  ↓
RerankerModule.rerank()
  ↓ 首次调用才发生
RerankerModule._load_model()
  ↓
CrossEncoder.predict([(query, child.page_content), ...])
  ↓
CE rank + recall rank 二次 RRF
  ↓
最终 Top-K Child
```

## 三、1. 使用什么 Cross-Encoder

### 源码事实

默认模型：

```text
BAAI/bge-reranker-base
```

代码位置：

- 文件：`rag_modules/reranker.py`
- 常量：`DEFAULT_RERANKER_MODEL`
- 类：`RerankerModule`

配置位置：

- 文件：`config.py`
- 类：`RAGConfig`
- 字段：`rerank_model = "BAAI/bge-reranker-base"`

真正加载使用的是：

```python
from sentence_transformers import CrossEncoder

CrossEncoder(
    self.model_name,
    device=self.device,
)
```

`RecipeRAGSystem._build_reranker()` 当前显式传入：

```python
device="cpu"
```

因此默认实现是 CPU 上的 `sentence_transformers.CrossEncoder`。

### 可配置项

环境变量：

```text
RAG_RERANK_ENABLED
RAG_RERANK_MODEL
RAG_RERANK_POOL
```

默认：

```text
enabled = false
model = BAAI/bge-reranker-base
pool = 20
```

### 一个可复现性边界

Embedding 模型在配置中固定了 revision，但 Reranker 当前只保存模型名称，没有独立的 `rerank_revision` 参数。

因此仅从当前源码看，Reranker 的模型版本固定程度弱于 Embedding 模型。这不影响本次功能说明，但属于后续追求严格可复现评测时需要注意的工程点。

## 四、2. Lazy Load 在哪里体现

Lazy Load 有两层。

## 第一层：默认关闭时连 Reranker 对象都不创建

- 文件：`main.py`
- 类：`RecipeRAGSystem`
- 函数：`_build_reranker()`

```python
if not self.config.rerank_enabled:
    logger.info("重排已关闭（RAG_RERANK_ENABLED=false）")
    return None
```

只有配置开启时，才延迟 import：

```python
from rag_modules.reranker import RerankerModule
```

并创建 `RerankerModule`。

默认关闭意味着：

- 不加载 Cross-Encoder。
- 不占用模型运行内存。
- 不发生模型下载。
- Retrieval 直接把主 RRF 结果截断为 `top_k`。

## 第二层：创建模块后仍不立刻加载模型

- 文件：`rag_modules/reranker.py`
- 类：`RerankerModule`
- 函数：`__init__()`、`_load_model()`、`rerank()`

构造函数只保存：

```python
self._model = model
```

正常运行时传入的 `model` 是 `None`，所以此时没有加载权重。

直到第一次执行：

```python
RerankerModule.rerank()
```

才调用：

```python
model = self._load_model()
```

`_load_model()` 如果发现：

```python
self._model is not None
```

会直接复用缓存模型。因此模型在进程生命周期中只加载一次。

## 离线优先与下载降级

`_load_model()` 的顺序是：

```text
优先强制 Hugging Face 离线模式读取本地缓存
  ↓ 失败且未设置 RAG_HF_OFFLINE
恢复在线直连 Hugging Face 下载
  ↓ 仍失败且用户未自定义 HF_ENDPOINT
切换 https://hf-mirror.com 再试一次
  ↓ 仍失败
抛出带操作建议的 RuntimeError
```

源码日志注明首次下载约：

```text
1.1 GB
```

如果显式启用 `RAG_HF_OFFLINE`，本地没有缓存时会直接抛出错误，不会联网下载。

## 五、3. Reranker 在 Retrieval Pipeline 的哪个位置

### 默认顺序

- 文件：`rag_modules/retrieval_optimization.py`
- 类：`RetrievalOptimizationModule`
- 函数：`hybrid_search()`、`_apply_rerank()`

真实顺序：

```text
Dense Retrieval
  +
BM25 Retrieval
  ↓
主 RRF Fusion
  ↓
Cross-Encoder Rerank
  ↓
CE rank 与主 Recall rank 再融合
  ↓
Final Top-K Child
```

FAISS 分支：

```python
vector_docs = ...
bm25_docs = ...
fused = self._rrf_rerank(vector_docs, bm25_docs, self.rrf_k)
return self._apply_rerank(query, fused, top_k)
```

Milvus 分支：

```python
pool = self.vectorstore.hybrid_search(...)
return self._apply_rerank(query, pool, top_k)
```

其中 Milvus 的 `pool` 已经是服务端 Dense + BM25 + RRF 的融合结果。

### 它处理的是 Child 还是 Parent

Reranker 处理的是检索返回的 Child `Document`。

Parent 恢复发生在 Retrieval 完成之后：

```text
Top-K Child
→ DataPreparationModule.get_parent_documents()
→ Parent Context
```

因此 Cross-Encoder 比较的是：

```text
Query 与 Child.page_content
```

不是 Query 与完整 Parent 文档。

### Metadata Filter 的位置差异

- Milvus：filter pushdown 后产生合法候选，再 RRF，再本地 CE。
- FAISS 的 `metadata_filtered_search()`：先调用较大规模 Hybrid Search，其中可能已经执行 CE+recall 融合；然后外层再对结果做 metadata post-filter。

所以 FAISS filtered 路径中，Cross-Encoder 可能会为之后被 metadata 删除的非法候选付出推理成本。

## 六、4. Reranker 的输入输出是什么

- 文件：`rag_modules/reranker.py`
- 函数：`RerankerModule.rerank()`

## 输入

```python
query: str
documents: list[Document]
```

每个 `Document` 至少包含：

```python
Document(
    page_content="Child Chunk 文本",
    metadata={...},
)
```

函数构造模型输入：

```python
pairs = [
    (query, document.page_content)
    for document in documents
]
```

数据结构：

```python
list[tuple[str, str]]
```

例如：

```python
[
    ("红烧肉需要什么材料", "# 红烧肉\n## 必备原料\n五花肉、冰糖……"),
    ("红烧肉需要什么材料", "# 拍黄瓜\n## 必备原料\n黄瓜、蒜……"),
]
```

## 模型输出

调用：

```python
model.predict(pairs)
```

项目将每个 score 转为：

```python
float
```

得到与候选一一对应的分数列表。

## RerankerModule 输出

按 score 从大到小排序：

```python
ranked: list[Document]
```

并原地向每个 Document metadata 增加：

```python
document.metadata["rerank_score"] = score
```

`RerankerModule.rerank()` 自己不会截断 Top-K，只负责给整个输入池打分和排序。

最终截断发生在：

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`_apply_rerank()`

而且当前代码不是直接返回纯 CE 的前 K 名，而是先把 CE rank 与 recall rank 再融合，最后：

```python
[:top_k]
```

## 禁用或空输入

如果：

```text
enabled=False
或 documents=[]
```

`rerank()` 直接返回原列表，不加载模型。

正常主链中，配置关闭时 `_build_reranker()` 直接返回 `None`，所以甚至不会调用该函数。

## 七、5. 为什么 Retriever Top-K 后再 Rerank，而不是全库 Rerank

这里的“Retriever Top-K”应理解为较大的候选池 Top-N，不是最终 `top_k=3`。

### 原因 1：Cross-Encoder 不能像文档 Embedding 一样完全预计算

Dense Retrieval 可以离线保存每个 Document embedding，查询时只需生成一个 Query embedding 并做向量搜索。

Cross-Encoder 的分数依赖具体 Query-Document 组合：

```text
score(query A, document X)
score(query B, document X)
```

必须分别计算。

如果全库有 N 个 Child，每次 Query 都要执行 N 个 pair 的模型推理。

### 原因 2：当前运行在 CPU

`RecipeRAGSystem._build_reranker()` 固定传入 `device="cpu"`。全库逐条 Cross-Encoder 推理会造成明显延迟，很难作为在线检索路径使用。

### 原因 3：模型和输入本身更重

源码日志注明模型首次下载约 1.1GB。Cross-Encoder 还要对 Query 与每个 Child 做联合编码，比简单向量距离或 BM25 排名昂贵。

### 原因 4：两阶段检索的职责不同

```text
第一阶段 Retriever：尽量不要漏掉正确答案
第二阶段 Reranker：在小候选池内提高前几名顺序
```

Reranker 不能召回候选池之外的文档，所以第一阶段 Recall 仍是基础。

### 工程结论

不是“Reranker 越强就可以替代 Retriever”，而是：

```text
Retriever 用低成本缩小范围
Cross-Encoder 用高成本精细判断
```

## 八、6. `rerank_pool` 是什么

### 配置

- 文件：`config.py`
- 字段：`RAGConfig.rerank_pool`
- 默认值：`20`
- 环境变量：`RAG_RERANK_POOL`

传入位置：

```python
RerankerModule(
    ...,
    pool_size=self.config.rerank_pool,
)
```

### Retrieval 如何使用

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`_pool_size(top_k)`

```python
if self.reranker is not None and self.reranker.enabled:
    return max(top_k, self.reranker.pool_size)
return top_k
```

因此开启重排、默认 `top_k=3` 时：

```text
pool_size = max(3, 20) = 20
```

随后：

```python
candidate_count = max(
    pool_size,
    candidate_k or self.candidate_k,
)
```

默认 `candidate_k=10`，所以：

```text
candidate_count = max(20, 10) = 20
```

### Milvus 路径

Milvus 服务端 Hybrid Search 接收：

```text
Dense request limit = 20
Sparse request limit = 20
Server RRF final limit = pool_size = 20
```

因此传给本地 Cross-Encoder 的候选最多约为 20 条，然后二次融合截断为最终 `top_k=3`。

### FAISS 路径的重要实现细节

FAISS 本地路径让：

```text
Dense 取 20
BM25 取 20
```

然后 `_rrf_rerank()` 对两路结果取去重并集。

代码没有在调用 `_apply_rerank()` 前把这个并集再次截成 20。因此：

```text
两路完全重合 → CE 大约处理 20 条
两路完全不重合 → CE 最多可能处理 40 条
```

所以当前 `rerank_pool=20` 在 FAISS 路径不是严格的“Cross-Encoder 最多处理 20 条”，而更接近“每条召回通路至少取到 20 的候选池下限”。

这是估算 latency 时必须以真实源码说明的细节。

### 参数影响

#### 调大

- 正确 Child 进入 CE 的概率提高。
- Cross-Encoder 有更多纠正粗排的机会。
- Dense/BM25 候选搜索、RRF 和 CE 推理延迟增加。
- CPU 和内存压力增加。

#### 调小

- 延迟下降。
- 正确 Child 如果不在较小池内，CE 无法恢复。
- 可能削弱 Reranker 的实际价值。

## 九、7. 当前为什么默认关闭 Reranker

### 配置事实

- 文件：`config.py`

```python
rerank_enabled: bool = False
```

`.env.example` 同样说明：

```text
本语料实测无增益，默认关闭
```

### 直接原因不是“模型太大”

模型下载、CPU 延迟和部署复杂度确实是代价，但当前项目默认关闭的首要依据是：

> 在 73 条 golden set 上，开启重排后 MRR 下降，而不是提升。

项目先得到 RRF baseline，再尝试纯 CE，发现下降；随后尝试 CE 与 recall 排名的二次 RRF，虽然比纯 CE 恢复了一部分，但仍低于 baseline。

所以最终决策是：

```text
默认关闭
保留实现和配置开关
换语料时重新评测
```

这是一种评测驱动的功能开关，而不是否定 Cross-Encoder 这类算法。

## 十、8. 项目评测中 RRF / CE / CE+RRF 的结果

## 评测条件

从 README、`eval/run_eval.py` 和 `.artifacts/eval/` 可确认：

```text
backend = milvus
top_k = 5
golden set = 73 条
指标 = Retrieval Hit@5 / MRR 等
不调用 LLM generation
```

`eval/run_eval.py` 直接调用：

```python
system.retrieve(item["query"], top_k=top_k, role=...)
```

因此这里比较的是检索排序质量，不是最终 Answer 的 faithfulness 或 relevance。

## 结果

| 方案 | 评测产物 MRR | 注释中的四舍五入值 | Hit@5 |
|---|---:|---:|---:|
| RRF 基线 | 0.9315 | 0.931 | 1.000 |
| 纯 CE 定序 | 0.8790 | 0.879 | 1.000 |
| CE rank + recall rank 二次 RRF | 0.9018 | 0.902 | 1.000 |

对应产物：

- RRF baseline：`.artifacts/eval/retrieval_eval_20260823-122239.json`
- 纯 CE：`.artifacts/eval/retrieval_eval_20260823-124424.json`
- CE+RRF：`.artifacts/eval/retrieval_eval_20260823-130000.json`

源码与文档的最终排序：

```text
RRF baseline 0.9315
>
CE+RRF 0.9018
>
pure CE 0.8790
```

### 如何理解 Hit@5 不变但 MRR 下降

三种方案 Hit@5 都是 1.000，说明目标仍然位于前 5 或满足相应评测条件。

MRR 下降说明目标文档虽然没有完全掉出 Top-5，但在列表中的位置被推后了。

换句话说，Cross-Encoder 没有破坏“是否找得到”，却破坏了“正确结果是否尽量靠前”。

### 评测集组成

README 显示 73 条包括：

- detail：40
- keyword：5
- browse：18
- permission_allowed：5
- permission_denied：5

其中 detail 类是大量“X 怎么做”式精确菜名问题。这种数据分布对 BM25 的精确词面信号非常友好。

## 十一、9. 为什么理论上更强的 Cross-Encoder 反而下降

需要把“表达能力”和“当前任务指标”分开。

## 原因 1：Baseline 已经很强，提升空间很小

RRF baseline：

```text
Hit@5 = 1.000
MRR = 0.9315
```

正确结果几乎已经处在非常靠前的位置。Cross-Encoder 没有多少正向空间，却有把正确第一名交换到第二、第三名的风险。

这是一种典型 ceiling effect。

## 原因 2：评测集以精确菜名 Query 为主

README 中 detail 类有 40 条，例子是“X 怎么做”。

BM25 能直接利用完整菜名、字符和双字 token；主 RRF 又保留 Dense 与 BM25 的共同信号。

源码注释明确将下降归因为：

```text
本语料 BM25 精确菜名信号已足够强
```

`docs/模块5精讲.md` 进一步记录：分桶后看到 detail 类掉分，精确菜名被 CE 的语义偏好干扰。

## 原因 3：语义相近不等于实体准确

例如 Query 是“红烧鲤鱼怎么做”，很多鱼类菜谱的步骤、食材和语言模式都很相似。

Cross-Encoder 可能偏好正文语义更丰富或步骤更匹配的“红烧草鱼”，而 BM25 对精确“红烧鲤鱼”具有更直接的实体证据。

这是工程解释；具体每条 bad case 的分数仍需查看评测 records 才能确认。

## 原因 4：通用 Reranker 不一定匹配当前领域和目标

`BAAI/bge-reranker-base` 是通用相关性模型，并没有在当前菜谱 golden set 上专门训练。

模型认为的“语义相关”与评测要求的“正确菜名尽量排第一”可能不完全一致。

## 原因 5：Cross-Encoder 只看到 Child 文本

输入是：

```text
(query, child.page_content)
```

不是完整 Parent，也没有显式把 `dish_name` 作为独立高权重字段输入。

虽然 Markdown 标题保留在 Child 中，但模型仍需自己在正文中学习标题精确匹配的重要性。

## 原因 6：纯 CE 会覆盖已经有效的 Recall 排序

纯 CE 实验直接按 CE score 定序，相当于丢掉主 RRF 已经融合好的 BM25 精确词信号。

项目后来用 CE rank + recall rank 二次 RRF，把 MRR 从：

```text
0.8790 → 0.9018
```

恢复了一部分，证明保留原召回序确实有价值。

但二次融合仍会改变 baseline 的原始次序，所以仍未恢复到 `0.9315`。

## 原因 7：Reranker 不是 Recall 修复器

如果正确 Chunk 没进入候选池，Cross-Encoder 无法找回；如果正确结果本来已经第一，它能做的主要是保持或打乱。

在一个高 Recall、高 MRR 的 baseline 上，额外模型并不自动带来净收益。

## 十二、10. 当前代码如何将 CE Rank 和 Recall Rank 再融合

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`_apply_rerank()`

### 第一步：记录主 Recall 排名

输入 `documents` 已经按主 RRF 排好序。

```python
recall_rank = {
    id(doc): rank
    for rank, doc in enumerate(documents, start=1)
}
```

这里使用 Python 对象身份 `id(doc)`，不是 `chunk_id`。

之所以能工作，是因为 `RerankerModule.rerank()` 对原来的 Document 对象重新排序，并没有创建新的 Document。

### 第二步：执行 CE 排序

```python
reranked = self.reranker.rerank(query, documents)
```

`reranked` 的列表位置就是 CE rank。

### 第三步：对两个 Rank 等权融合

```python
def fused_score(document, ce_rank):
    return (
        1.0 / (self.rrf_k + ce_rank)
        + 1.0 / (
            self.rrf_k
            + recall_rank[id(document)]
        )
    )
```

含义：

```text
最终分数
= CE 名次贡献
+ 主 Recall 名次贡献
```

两路权重相同，都使用同一个 `self.rrf_k`，默认 60。

### 第四步：重新排序并截断

```python
fused = sorted(
    enumerate(reranked, start=1),
    key=lambda pair: -fused_score(pair[1], pair[0]),
)

return [document for _, document in fused][:top_k]
```

### 它使用了什么

- CE rank
- 主 RRF recall rank
- `rrf_k`

### 它没有使用什么

- 原始 `rerank_score` 数值大小
- 主 RRF 的 `rrf_score` 数值大小
- Dense distance
- BM25 score
- 动态 Query 类型权重

也就是说，`rerank_score` 被写入 metadata 供观察，但二次融合只使用 CE 的排名位置，不使用 CE 分数差距。

### 输出 metadata

最终 Document 通常同时保留：

```text
rrf_score       # 主召回阶段分数
rerank_score    # Cross-Encoder 原始分数
```

代码没有把“CE rank + recall rank”的二次融合分数写入一个新的 metadata 字段。

因此从最终结果 metadata 可以看到两个原始阶段分数，但不能直接看到当前最终二次融合 score。

### 同分行为

二次 `sorted()` 的输入顺序是 CE 排名顺序。若两个候选的融合分数完全相同，Python 稳定排序会保留 CE 顺序。

## 十四、A. “为什么项目没有盲目开启 Reranker”的面试答案

> 我们实现了 `BAAI/bge-reranker-base` Cross-Encoder 精排，但没有因为它理论表达能力更强就默认上线。检索主链先做 Dense + BM25 + RRF，然后将候选池交给 CE。我们用 Milvus、Top-5 和 73 条覆盖详情、关键词、浏览及权限场景的 golden set 做了三组对照。
>
> 结果是 RRF baseline 的 Hit@5 为 1.0、MRR 为 0.9315；纯 CE 虽然 Hit@5 仍是 1.0，但 MRR 降到 0.879；为了避免 CE 覆盖已经很强的 BM25 精确菜名信号，我们又把 CE rank 与 recall rank 做二次 RRF，MRR 恢复到 0.9018，但仍低于 baseline。
>
> 原因不是 Cross-Encoder 没价值，而是当前评测集有大量“菜名怎么做”的精确实体查询，中文 BM25 加 RRF 已经很强。CE 的语义偏好反而可能把相似菜谱提升到精确菜名之前。在 baseline 已经 Hit@5 100% 的情况下，额外模型没有 Recall 收益，却增加 CPU 延迟、约 1.1GB 模型依赖、冷启动和下载维护成本。
>
> 所以我们的决策是默认关闭、保留配置开关和实现。当语料换成更长、更语义化、词面匹配更弱的知识库时，用新的 golden set 重新评测再决定开启。这体现的是评测驱动，而不是按算法名堆模块。

## 十五、B. 收益 / Latency / Cost / Complexity Trade-off

| 维度 | 开启 Reranker 的潜在收益 | 当前项目中的实际代价 / 结果 |
|---|---|---|
| Ranking Quality | 联合建模 Query-Child，可纠正仅靠向量或词面的粗排错误 | 当前 MRR 从 baseline 0.9315 降到 CE+RRF 0.9018 |
| Recall | 较大候选池可避免过早截断，并给精排更多选择 | Reranker 本身不能召回池外文档；三组 Hit@5 均为 1.0，无新增 Hit 收益 |
| Precision@Top | 对复杂语义 Query 理论上更有机会把真正相关结果提前 | 当前精确菜名分布中，CE 可能把语义相似但实体错误的菜谱提前 |
| Latency | 无直接收益 | 每次 Query 为候选池执行 Cross-Encoder；CPU 默认，FAISS 极端可超过配置名义上的 20 条 |
| Cold Start | 无直接收益 | 首次使用才懒加载；本地无缓存时下载约 1.1GB |
| API Cost | 本地模型，不产生按次 LLM API token 费用 | 仍有 CPU 时间、内存、磁盘、网络下载和机器成本 |
| Retrieval Cost | 更大候选池给精排提供空间 | 默认候选规模从 10 扩到至少 20；Dense、BM25 和 RRF 也随之变贵 |
| Memory | 无直接收益 | 需要常驻 Cross-Encoder 模型和推理中间状态 |
| Deployment | 可通过环境变量按语料启用 | 增加模型缓存、离线/直连/镜像下载路径和故障处理 |
| Reproducibility | 可保留 score 便于 bad case 分析 | Reranker revision 未像 embedding 一样固定；二次融合最终 score 未写入 metadata |
| Code Complexity | 抽象为独立模块，保留实验能力 | 增加候选池管理、模型生命周期、二次 RRF、配置和测试复杂度 |
| Maintainability | 默认关闭可避免影响稳定 baseline | 仍需保证可选代码、依赖和评测脚本随版本正常工作 |

### 当前决策

```text
收益：在当前语料和指标上未验证到
Latency：增加
本地计算成本：增加
模型与部署复杂度：增加
最终选择：默认关闭，保留开关，换语料后复测
```

### 什么情况下值得重新开启实验

- Query 与文档经常是同义表达而不是精确名称匹配。
- 文档更长，候选之间需要细粒度 Query-Document 交互判断。
- Baseline MRR 或 Precision@Top 明显不足，但 Recall 已经较高。
- 有 GPU 或可接受的 CPU latency 预算。
- 新语料 golden set 证明 CE 或 CE+RRF 有稳定收益。

这些是复测条件，不表示当前代码已在其他领域证明收益。

## 十六、当前实现的优点与改进空间

## 优点

- 默认关闭，不让实验模块拖慢稳定主链。
- 两层 lazy load，未启用时不承担模型成本。
- 离线缓存优先，并提供直连和镜像下载降级。
- Reranker 与 Retrieval 编排解耦，支持依赖注入和 fake model 测试。
- 通过扩大候选池避免只对最终 3 条做没有意义的重排。
- 发现纯 CE 掉点后，没有直接放弃，而是验证 CE+recall 二次融合。
- 最终决策由 golden set 指标驱动，并写入配置注释和 README。

## 改进空间

- 给 Reranker 增加固定 revision，提高实验可复现性。
- 让 FAISS 在主 RRF 后、CE 前显式截断为严格 `rerank_pool`，避免最多约两倍候选的延迟漂移。
- 将二次融合后的最终 score 写入 metadata，方便 Observability 和 bad case 分析。
- 对不同 Query 类型尝试条件化开启，例如只对语义型 Query 使用，而不是全量开启。
- 用分桶指标决定策略：精确菜名保留 baseline，复杂描述才走 CE。
- 评估带 `dish_name` 显式字段的 Cross-Encoder 输入格式，而不是只输入 `page_content`。
- 对新的领域语料重新标注 golden set，不能直接复用菜谱结论。

以上属于基于当前实现的优化建议，不是项目已经实现的功能。

## 十七、源码事实边界

当前源码和仓库产物可以确认：

- 默认模型是 `BAAI/bge-reranker-base`。
- 使用 `sentence_transformers.CrossEncoder`，当前主系统传入 CPU。
- 模型在第一次非空 `rerank()` 时才加载，并缓存复用。
- Reranker 位于 Dense+BM25 主 RRF 之后、最终 Top-K 之前。
- 输入是 `(query, child.page_content)` pairs。
- 输出是重新排序的 `list[Document]`，metadata 增加 `rerank_score`。
- 默认 `rerank_pool=20`、`rerank_enabled=False`。
- 当前启用路径执行 CE rank + recall rank 二次 RRF。
- 73 条、Milvus、Top-5 评测产物为 0.9315 / 0.8790 / 0.9018。

需要明确保留的边界：

- 当前代码没有独立的“纯 CE / CE+RRF”运行模式开关；纯 CE 是项目实验过程中记录的一组对照，当前实现保留的是 CE+RRF 路径。
- 评测结果是 Retrieval MRR，不是 LLM 最终答案质量分数。
- “精确菜名信号被 CE 干扰”来自项目注释和分桶分析文档；每一条具体 bad case 的模型原因仍需结合评测 record 和 score 检查。
- 更换领域、Query 分布、Reranker 模型或硬件后，当前关闭结论不能直接外推，必须重新评测。
