# Chunking 与 Parent-Child Retrieval 设计

本文基于当前仓库真实源码，分析项目如何切分 Markdown、如何建立 Parent 与 Child 的关系，以及为什么检索 Child、生成时恢复 Parent。

## 先建立直觉

可以先把一篇菜谱想成一本很短的说明书：

```text
Parent Document：整篇菜谱
├── Child 1：标题和菜品介绍
├── Child 2：必备原料和工具
├── Child 3：计算用量
├── Child 4：操作步骤
└── Child 5：附加内容
```

如果用户问“红烧肉需要什么食材”，最适合参与相似度比较的是“必备原料”这一小段，而不是整篇菜谱；但让 LLM 回答时，只提供这一小段又可能缺少用量、步骤和注意事项。

因此本项目采用：

```text
用 Child 做检索定位
→ 用 parent_id 找回完整 Parent
→ 用 Parent 构造生成 Context
```

这就是当前项目 Parent-Child Retrieval 的核心思路。

---

## 一、真实数据流

```text
Markdown 文件
→ load_documents()
→ 一个文件产生一个 Parent Document
→ chunk_documents()
→ _markdown_header_split()
→ 一个 Parent 产生多个文本 Child Chunk
→ Child 写入 FAISS/Milvus
→ Query 检索返回 Top-K Child
→ get_parent_documents(Child)
→ 根据 parent_id 找回并去重 Parent
→ _build_context(Parent)
→ LLM Generation
```

图片 caption 也会成为 Child，并通过同一个 `parent_id` 指向所属菜谱 Parent。

## 二、原始 Markdown 如何切分

### 1. Parent Document 的来源

**文件**

`rag_modules/data_preparation.py`

**类 / 函数**

```python
DataPreparationModule.load_documents()
```

源码使用：

```python
data_root.rglob("*.md")
```

递归发现 Markdown 文件。每个文件完整读取后创建一个 LangChain `Document`：

```python
Document(
    page_content=完整 Markdown 文本,
    metadata={...},
)
```

因此当前项目中：

> 一个有效 Markdown 文件对应一个 Parent Document。

Parent Document 保存在：

```python
self.documents: list[Document]
self._parent_documents: dict[str, Document]
```

### 2. Child Chunk 的切分入口

**文件**

`rag_modules/data_preparation.py`

**函数**

```python
DataPreparationModule.chunk_documents()
```

它要求先执行：

```python
load_documents()
```

随后调用：

```python
self._markdown_header_split()
```

### 3. 按什么标题层级切分

`_markdown_header_split()` 创建：

```python
MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "主标题"),
        ("##", "二级标题"),
        ("###", "三级标题"),
    ],
    strip_headers=False,
)
```

因此源码明确处理三个 Markdown 标题层级：

```text
#   主标题
##  二级标题
### 三级标题
```

真正的标题解析和分段行为由 LangChain 的 `MarkdownHeaderTextSplitter.split_text()` 完成。

当前代码没有在标题切分之后再调用 `RecursiveCharacterTextSplitter`，也没有设置固定字符长度或重叠窗口。

### 4. 标题是否保留

源码设置：

```python
strip_headers=False
```

所以标题文本会保留在 Child 的 `page_content` 中。

架构上的作用是让类似“必备原料”“操作步骤”这样的章节语义继续参与检索，而不是只保留标题下面的正文。

### 5. 切分失败或没有结果时怎么办

如果 `split_text()` 抛出异常，代码记录警告并将：

```python
split_chunks = []
```

如果最终没有任何切分结果：

```python
split_chunks = [
    Document(
        page_content=parent.page_content,
        metadata={},
    )
]
```

也就是把整篇 Parent 内容作为一个 Child Chunk。

因此单篇 Markdown 的切分失败不会导致整个语料停止建库。

## 三、Parent Document 和 Child Chunk 分别是什么

### Parent Document

Parent 是完整 Markdown 文件对应的 `Document`。

典型结构：

```python
Document(
    page_content="完整菜谱 Markdown",
    metadata={
        "parent_id": str,
        "revision_id": str,
        "doc_type": "parent",
        "file_type": "markdown",
        "modality": "text",
        "source": str,
        "source_path": str,
        "dish_name": str,
        "category": str,
        "difficulty": str,
        "visibility": str,
        ...
    },
)
```

Parent 的主要用途：

```text
保存完整原文
→ Child 命中后用于回溯
→ 构造最终生成 Context
→ 提供确定性来源信息
```

### 文本 Child Chunk

Child 是 `MarkdownHeaderTextSplitter` 产生的局部章节 `Document`。

典型结构：

```python
Document(
    page_content="某个标题章节及内容",
    metadata={
        # 从 Parent 继承的字段
        "parent_id": str,
        "revision_id": str,
        "source_path": str,
        "dish_name": str,
        "category": str,
        "difficulty": str,
        "visibility": str,
        "modality": "text",

        # Child 自己的字段
        "chunk_id": str,
        "doc_type": "child",
        "chunk_index": int,
        "chunking_version": "markdown-headers-v1",
        "batch_index": int,
        "chunk_size": int,

        # 标题切分器可能产生的标题 metadata
        "主标题": str,
        "二级标题": str,
        "三级标题": str,
        ...
    },
)
```

Child 的主要用途：

```text
生成 Embedding
写入 FAISS/Milvus
参与 Dense/Sparse Retrieval
携带 parent_id 指向完整 Parent
```

### 图片 Child Chunk

图片也会转换为 Child：

```python
Document(
    page_content="视觉模型生成的 caption",
    metadata={
        "chunk_id": str,
        "parent_id": str,
        "doc_type": "child",
        "modality": "image",
        "file_type": "image",
        "image_path": str,
        ...
    },
)
```

所以 Parent-Child 回溯不仅用于文本章节，也用于图片 caption 命中后找回所属菜谱。

## 四、parent_id 如何建立

### 1. parent_id 的创建位置

**文件**

`rag_modules/data_preparation.py`

**函数**

```python
DataPreparationModule.load_documents()
```

源码：

```python
parent_id = self._stable_id("parent", source_path)
```

`_stable_id()` 的实现是将 namespace 和输入字段组合后计算 SHA-256：

```python
payload = "\0".join((namespace, *parts)).encode("utf-8")
return hashlib.sha256(payload).hexdigest()
```

### 2. parent_id 依赖什么

当前 `parent_id` 只依赖：

```text
"parent"
+
Markdown 相对于 data_root 的 source_path
```

它不依赖绝对磁盘路径，也不依赖文件正文。

因此：

- 同一语料复制到不同机器目录，`parent_id` 可以保持一致。
- 文件内容修改但相对路径不变时，`parent_id` 保持不变。
- 文件移动或改名导致 `source_path` 改变时，`parent_id` 改变。

### 3. 内容变化如何表示

源码另外创建：

```python
revision_id = self._stable_id(
    "revision",
    source_path,
    content_hash,
)
```

因此：

```text
parent_id   = 文档逻辑身份
revision_id = 当前内容版本身份
```

### 4. Child 的 chunk_id 如何关联 Parent

文本 Child：

```python
child_id = self._stable_id(
    "chunk",
    parent.metadata["parent_id"],
    parent.metadata["revision_id"],
    str(chunk_index),
    split_chunk.page_content,
)
```

随后保存为：

```python
metadata["chunk_id"] = child_id
metadata["parent_id"] = parent.metadata["parent_id"]
```

当前源码没有名为：

```python
metadata["child_id"]
```

实际使用的是 `chunk_id`。

### 5. parent_id 保存在哪里

Parent 注册表：

```python
self._parent_documents[parent_id] = parent_document
```

文本 Child metadata：

```python
child.metadata["parent_id"] = parent_id
```

父子映射：

```python
self.parent_child_map[chunk_id] = parent_id
```

图片 Child 也继承：

```python
image_chunk.metadata["parent_id"] = parent_id
```

### 6. `parent_child_map` 是否用于回溯

当前 `get_parent_documents()` 没有读取：

```python
self.parent_child_map
```

它直接读取：

```python
chunk.metadata.get("parent_id")
```

然后查询：

```python
self._parent_documents[parent_id]
```

这也解释了为什么图片 Child 即使没有写入 `parent_child_map`，仍然可以参与 Parent 回溯：图片 metadata 自身已经带有 `parent_id`。

## 五、为什么检索 Child，生成时恢复 Parent

这一节是基于真实数据流的架构解释。

### 1. Child 更适合作为检索单元

一篇完整菜谱可能同时包含：

```text
菜品介绍
原料
用量
步骤
技巧
附加内容
```

用户 Query 往往只对应其中一个局部问题。

例如：

```text
Query：红烧肉需要哪些香料？
```

“必备原料”章节与 Query 的主题更集中；如果直接用整篇菜谱参与检索，其他章节会与目标问题混在一个表示中。

因此项目将索引建立在 Child Chunk 上。

### 2. Parent 更适合作为生成上下文

检索到一个 Child 只能证明：

```text
这一局部章节和 Query 相关
```

但最终回答可能还需要：

```text
菜品完整材料
材料用量
步骤顺序
上下文中的注意事项
其他章节里的补充说明
```

因此命中 Child 后，代码使用 `parent_id` 找回完整 Parent，再把 Parent 交给 Generation。

### 3. 本项目的真实边界

当前实现不是：

```text
命中 Child
→ 只取 Child 附近的窗口
```

也不是：

```text
命中 Child
→ 重新对 Parent 内部做精细选择
```

而是：

```text
命中任意 Child
→ 取回该 Child 所属的完整 Markdown Parent
```

## 六、get_parent_documents 的具体逻辑

**文件**

`rag_modules/data_preparation.py`

**函数**

```python
DataPreparationModule.get_parent_documents(
    child_chunks: list[Document],
) -> list[Document]
```

### 1. 输入

```python
child_chunks: list[Document]
```

通常来自：

```text
RetrievalOptimizationModule
→ Top-K 检索结果
```

### 2. 创建两个统计字典

```python
relevance: dict[str, int] = {}
first_seen: dict[str, int] = {}
```

含义：

```text
relevance[parent_id]
= 这个 Parent 拥有多少个命中 Child

first_seen[parent_id]
= 这个 Parent 第一次在哪个 Child 排名位置出现
```

### 3. 遍历检索到的 Child

```python
for position, chunk in enumerate(child_chunks):
    parent_id = chunk.metadata.get("parent_id")
```

如果：

```python
not parent_id
```

或者：

```python
parent_id not in self._parent_documents
```

这个 Child 会被忽略。

### 4. 统计每个 Parent 的命中 Child 数量

```python
relevance[parent_id] = relevance.get(parent_id, 0) + 1
first_seen.setdefault(parent_id, position)
```

同一 Parent 的多个 Child 被命中时，`relevance` 会累计。

### 5. 对 Parent ID 排序

```python
ranked_ids = sorted(
    relevance,
    key=lambda parent_id: (
        -relevance[parent_id],
        first_seen[parent_id],
    ),
)
```

排序规则：

```text
第一优先级：命中 Child 数量更多的 Parent 在前
第二优先级：首次出现得更早的 Parent 在前
```

### 6. 取回完整 Parent

```python
parents = [
    self._parent_documents[parent_id]
    for parent_id in ranked_ids
]
```

输出：

```python
list[Document]  # 唯一、完整、已排序的 Parent Documents
```

### 7. 当前逻辑没有做什么

`get_parent_documents()` 当前没有：

- 使用 Child 的 `rrf_score` 数值重新计算 Parent 分数。
- 使用 `rerank_score` 聚合 Parent 分数。
- 给不同 Child 排名设置不同权重。
- 限制 Parent 返回数量。
- 截取 Parent 内最相关的章节。
- 使用 `parent_child_map` 进行查询。

它使用的是简单的：

```text
命中 Child 数量
+
首次出现位置
```

## 七、如果不用 Parent-Child 会发生什么

需要区分两种替代方式。

### 情况一：直接检索完整 Parent

数据流变成：

```text
完整 Markdown
→ 直接生成 Embedding 并入库
→ Query 直接检索整篇菜谱
```

可能的问题：

1. **检索粒度过粗**
   - 一个 Query 只关心“原料”，但整篇文档还包含大量步骤和附加内容。

2. **局部相关信号被其他内容稀释**
   - 某个小章节非常相关，不代表整篇文档的整体表示同样突出。

3. **精确定位困难**
   - 无法知道命中是因为菜名、原料还是操作步骤。

4. **长文档处理压力更大**
   - 单条索引内容更长，稀疏检索字段、Embedding 输入和返回内容都更重。

收益则是实现简单，不需要维护 Parent-Child 映射。

### 情况二：只检索 Child，也只把 Child 交给 LLM

数据流变成：

```text
Query
→ Top-K Child
→ 直接拼接 Child Context
→ LLM
```

可能的问题：

1. **上下文不完整**
   - 命中“步骤”时可能缺少食材用量。

2. **跨章节关系丢失**
   - 操作步骤中提到“加入前面准备的调料”，但对应调料列表不在命中 Child 中。

3. **回答容易拼接碎片**
   - 多个菜谱的局部 Child 可能被混合到同一个答案里。

4. **重复内容增多**
   - 同一 Parent 的多个 Child 都进入 Context 时，可能重复菜名、标题和公共信息。

收益则是 Context 更紧凑、Token 成本更低，且通常更贴近命中位置。

## 八、当前设计的收益和代价

### 主要收益

#### 1. 兼顾检索粒度和生成完整性

```text
Child：局部主题更集中
Parent：生成信息更完整
```

#### 2. 同一菜谱多个命中 Child 会增强 Parent 排名

如果某篇菜谱同时在标题、原料和步骤上与 Query 相关，它可能有多个 Child 进入 Top-K，`get_parent_documents()` 会把该 Parent 排在更前面。

#### 3. Parent 自动去重

多个 Child 指向同一 Parent 时，最终只向 Generation 提供一份完整菜谱。

#### 4. 图片和文本共享 Parent

图片 caption 命中后可以通过 `parent_id` 找回所属菜谱，并把 `image_path` 单独交给 Generation。

#### 5. ID 可复现

`parent_id` 基于相对路径，Child `chunk_id` 基于 Parent、版本、顺序和正文，支持索引一致性校验。

### 主要代价

#### 1. Context 容易膨胀

即使只命中一个很小的 Child，系统也会把整篇 Parent 放入 Context。

#### 2. Parent 中可能重新引入无关内容

Child 检索阶段获得的局部精度，可能在恢复完整 Parent 时被其他章节的噪声部分抵消。

#### 3. Parent 排序逻辑较粗

当前只统计命中 Child 数量和首次位置，没有聚合 Child 的真实检索分数。

#### 4. Top-K Child 不等于 Top-K Parent

例如：

```text
Top-K Child = 3
```

可能出现：

```text
3 个 Child 全属于同一个 Parent
→ 最终只有 1 个 Parent
```

也可能出现 3 个不同 Parent。

因此 Child `top_k` 无法直接保证 Parent 数量。

#### 5. Parent 必须在内存中可用

`get_parent_documents()` 依赖：

```python
self._parent_documents
```

因此即使向量索引已存在，系统启动时仍然需要重新加载当前 Markdown，建立 Parent 注册表并验证索引与当前语料匹配。

#### 6. Chunking 结果变化会导致 Chunk 身份变化

Child `chunk_id` 包含：

```text
revision_id
chunk_index
chunk content
```

文档内容或切分顺序变化可能导致多个 Chunk ID 改变，从而触发索引重建。

## 九、Context 长度限制如何影响 Parent Retrieval

### 1. Context 构建位置

**文件**

`rag_modules/generation_integration.py`

**函数**

```python
GenerationIntegrationModule._build_context()
```

输入是已经回溯并排序的：

```python
docs: list[Document]  # Parent Documents
```

当前默认限制来自：

```python
RAGConfig.max_context_chars = 6000
```

注意它是字符数限制，不是模型 Token 数限制。

### 2. Parent 按顺序加入 Context

每个 Parent 被格式化为：

```text
【食谱 N】 菜名 | 分类 | 难度
完整 Parent page_content
```

`_build_context()` 按 `get_parent_documents()` 返回的顺序依次加入。

因此 Parent 排名直接决定谁优先占用 Context 预算。

### 3. 第一篇 Parent 太长

如果第一篇 Parent 加上 metadata 后已经超过剩余长度：

```python
if not context_parts:
    context_parts.append(doc_text[:remaining])
break
```

结果：

- 第一篇 Parent 会被字符级截断。
- 可能从句子、Markdown 表格或步骤中间截断。
- 后续 Parent 全部不再加入。

### 4. 后续 Parent 放不下

如果已经加入至少一篇 Parent，下一篇完整内容放不下：

```python
break
```

该 Parent 不会部分加入，后面的 Parent 也不再尝试。

因此可能出现：

```text
Retrieval 找回 3 个 Parent
但最终 Context 只包含前 1～2 个
```

### 5. 没有突出命中的 Child

当前 Context 中只加入完整 Parent，没有显式标记：

```text
这个 Parent 的哪个 Child 被检索命中
```

也不会将命中 Child 放到 Parent 开头。

所以当 Parent 很长时，真正相关的章节可能位于后部，并在字符截断时被删除。

### 6. 图片路径的长度处理

同步生成中，`image_paths` 会在 Parent 文本处理完后作为额外部分追加。

当前代码没有把图片路径列表的长度计入前面的 `current_length` 预算，因此最终 Context 字符数可能略微超过 `max_context_chars`。

### 7. 对效果的总体影响

```text
max_context_chars 较小
→ Context 更便宜、更聚焦
→ 但后排 Parent 和 Parent 后部章节更容易丢失

max_context_chars 较大
→ 更多完整 Parent 能进入 Generation
→ 但 Token、延迟、成本和噪声增加
```

Parent-Child Retrieval 保证的是“系统能找到完整 Parent”，不保证“完整 Parent 一定全部进入最终 LLM Context”。

## 十、关键参数与影响

### 1. `headers_to_split_on`

**位置**

`DataPreparationModule._markdown_header_split()`

**当前值**

```python
[
    ("#", "主标题"),
    ("##", "二级标题"),
    ("###", "三级标题"),
]
```

**增加更多标题层级，例如 `####`**

- 可能产生更细的 Child。
- 局部检索粒度可能更精确。
- Child 数量、索引规模和父文档重复命中概率增加。

**减少标题层级**

- Child 更粗、更长。
- 索引条目减少。
- 局部问题的相关信号可能被更大章节稀释。

该配置当前写死在代码中，不是环境变量参数。

### 2. `strip_headers`

**当前值**

```python
False
```

**改为 `True`**

- Child 正文更短。
- 但“必备原料”“操作步骤”等标题词不再出现在 `page_content` 中。
- 可能损失有价值的章节语义。

**保持 `False`**

- 标题参与检索。
- 不同 Child 可能重复携带部分标题信息。

### 3. 固定字符 `chunk_size`

当前项目没有用于控制切分的固定字符 `chunk_size` 参数。

metadata 中的：

```python
chunk.metadata["chunk_size"] = len(chunk.page_content)
```

只是记录切分结果长度，不参与切分决策。

因此不存在“把当前 chunk_size 调大或调小”的运行配置。

### 4. `chunk_overlap`

当前项目没有 `chunk_overlap` 参数，也没有额外的重叠字符切分。

如果未来增加重叠：

- 可能减少语义跨边界丢失。
- 但索引条目、重复命中和 Context 重复会增加。

这是替代方案分析，不是当前源码行为。

### 5. `CHUNKING_VERSION`

**位置**

```python
DataPreparationModule.CHUNKING_VERSION
```

```python
"markdown-headers-v1"
```

### 6. `top_k`

**位置**

`RAGConfig.top_k`

**当前默认值**

```python
3
```

它控制最终保留多少个 Child 检索结果。

**调大**

- 更多 Child 和潜在 Parent 被召回。
- Parent Recall 和多样性可能提高。
- 同一 Parent 可能重复占据多个 Child 名额。
- Parent 数量和 Context 压力可能增加。

**调小**

- 延迟和后续 Context 压力降低。
- 但相关 Parent 更容易未进入回溯阶段。
- 一个错误的前排 Child 对最终结果影响更大。

**位置**

`RAGConfig.max_context_chars`

**当前默认值**

```python
6000
```

**调大**

- 更多完整 Parent 可以进入 Prompt。
- 信息完整性可能提高。
- Token 成本、延迟和噪声增加。

**调小**

- Context 更短，生成成本降低。
- 第一篇 Parent 更容易被截断。
- 后排 Parent 更容易被完全丢弃。

### 8. `include_templates`

**位置**

**当前默认值**

```python
False
```

- `template` 目录中的 Markdown 也会变成 Parent 和 Child。
- 可能把模板占位文本带入知识库。

**保持 `False`**

### 9. `strict`

**位置**

`DataPreparationModule.__init__()`

**当前默认值**

```python
True
```

**`True`**

- 任意文件读取失败后拒绝构建部分索引。
- 数据一致性更强。

**`False`**

- 可用性更高，但知识库可能不完整。

## 十一、优点、问题与优化方向总表

| 维度 | 当前设计 | 收益 | 代价 / 风险 |
|---|---|---|---|
| 切分方式 | Markdown 标题结构切分 | 尊重菜谱天然章节 | 不限制极长章节长度 |
| 标题处理 | 保留标题 | 标题语义参与检索 | 标题文本可能重复 |
| 检索对象 | Child Chunk | 局部检索更聚焦 | Top-K 名额可能被同一 Parent 多个 Child 占据 |
| 生成对象 | 完整 Parent | 信息更完整 | Context 膨胀和噪声增加 |
| Parent 排序 | 命中 Child 数量 + first_seen | 简单、确定、可解释 | 不使用真实检索分数聚合 |
| Parent 去重 | 按 `parent_id` | 避免同一菜谱重复进入 Context | 多个强 Child 最终只产生一个 Parent |

## 十二、2 分钟口述版本

这个项目采用的是典型的 Parent-Child Retrieval，但实现比较直接。原始语料是一篇篇 Markdown 菜谱，`DataPreparationModule.load_documents()` 会把每个 Markdown 完整加载成一个 Parent Document。Parent 保存完整正文，并根据相对路径生成稳定的 `parent_id`；文件内容版本则通过 `revision_id` 单独表示。

接着，`chunk_documents()` 使用 LangChain 的 `MarkdownHeaderTextSplitter`，按照一级、二级和三级标题切分，而且 `strip_headers=False`，所以标题仍保留在 Child 内容中。项目没有固定字符 chunk size，也没有 overlap；metadata 里的 `chunk_size` 只是记录实际长度。每个 Child 会生成自己的 `chunk_id`，并在 metadata 中保留 `parent_id` 和 `doc_type=child`。图片也会先生成 caption，再作为 `modality=image` 的 Child 指向所属菜谱 Parent。

建库时只有 Child 被写入 FAISS 或 Milvus。用户查询得到的 Top-K 也是 Child Chunk。之后 `get_parent_documents()` 读取每个 Child 的 `parent_id`，在内存中的 `_parent_documents` 里找回完整 Parent。它按照一个 Parent 命中了多少个 Child 排序；命中数量相同时，首次出现更早的 Parent 排在前面，然后完成 Parent 去重。

这样做的直觉是：Child 的主题更集中，适合检索；Parent 信息更完整，适合生成。如果直接检索 Parent，局部问题可能被整篇内容稀释；如果只把 Child 给 LLM，又可能缺食材、步骤或跨章节信息。

代价是完整 Parent 会扩大 Context，并重新引入无关章节。当前 `_build_context()` 默认最多保留 6000 个字符，第一篇 Parent 太长时会被直接截断，后续 Parent 放不下时会整体丢弃。因此 Parent Retrieval 只能保证找回完整文档，不能保证完整文档一定全部进入最终 Prompt。这也是后续可以优化成命中 Child 加相邻窗口、Parent 分数聚合或 Token 级预算管理的原因。

## 事实边界

以下内容可以从当前源码直接确认：

- Markdown 按 `# / ## / ###` 切分。
- `strip_headers=False`。
- 当前没有字符长度切分和 overlap。
- 一个 Markdown 对应一个 Parent Document。
- 文本章节和图片 caption 都是 Child Chunk。
- Child 身份字段是 `chunk_id`，不是 `child_id`。
- Parent 回溯直接读取 Child metadata 的 `parent_id`。
- `get_parent_documents()` 使用命中 Child 数量和首次出现位置排序。
- Context 默认按字符数限制为 6000。

“Child 更适合局部检索”“Parent 更适合完整生成”等表述属于基于真实数据流的架构解释，不是额外的源码行为。
