# Metadata Filtering 设计

本文基于当前仓库真实源码，分析 metadata filter 从产生到执行的完整链路，并重点比较 Milvus filter pushdown 与 FAISS post-filter。

范围说明：

- 分析当前版本的 `main.py`、`rag_modules/data_preparation.py`、`rag_modules/domain_config.py`、`rag_modules/retrieval_optimization.py`、`rag_modules/vector_store.py`、`rag_modules/agentic_rag.py` 及相关测试。
- 不分析 `*_old.py` 或 `rag_modules_old/` 中的旧实现。
- “FAISS 不能过滤”在本文中指当前项目的 `FaissBackend` 实现不能把表达式下推到向量索引，不代表所有 FAISS 封装在任何情况下都绝对不支持 metadata 处理。

---

## 一、先建立直觉

向量检索与 BM25 解决的是：

```text
哪些 Chunk 与 Query 最相关？
```

Metadata Filtering 解决的是：

```text
哪些 Chunk 有资格参加这次检索？
```

例如用户问：

```text
推荐几道简单的素菜
```

相关性检索可能找到：

- 简单的素菜
- 非常简单的素菜
- 简单的荤菜
- 与“简单做法”语义接近的内部工艺文档

但用户实际施加了两个结构化约束：

```text
category == "素菜"
difficulty == "简单"
```

系统还会根据访问角色自动增加权限约束。例如普通用户只能看到：

```text
visibility in ["public"]
```

于是完整约束是：

```text
category == "素菜"
&& difficulty == "简单"
&& visibility in ["public"]
```

Milvus 与 FAISS 的最大差异是过滤发生的时间：

```text
Milvus：先过滤合法范围，再在范围内召回和排名
FAISS：先从全库召回和排名，再过滤不合法结果
```

这不仅影响速度，还影响 Recall。因为后置过滤时，正确候选可能在进入过滤步骤之前就被 Top-N 截掉。

## 二、Metadata 从哪里产生

过滤能工作，前提是 Parent 和 Child 已经带有相应 metadata。

- 文件：`rag_modules/data_preparation.py`
- 类：`DataPreparationModule`
- 函数：`_enhance_metadata()`

### `category`

源码读取文档的 `source_path`，将路径目录名映射为业务分类：

```python
for key, value in get_domain().category_mapping.items():
    if key.casefold() in path_parts:
        category = value
        break
```

当前菜谱领域配置位于：

- 文件：`rag_modules/domain_config.py`
- 对象：`RECIPE_DOMAIN`

分类映射产生以下去重后的分类值：

```text
荤菜、素菜、汤品、甜品、早餐、主食、水产、调料、饮品、半成品
```

无法匹配目录时，`category` 为：

```text
其他
```

注意：`其他` 是运行时可能出现的 metadata 值，但不在当前 `category_labels` 的标准 Query 枚举中。

### `difficulty`

`_enhance_metadata()` 从 Markdown 正文中寻找第一段连续的 `★`：

```text
★     → 非常简单
★★    → 简单
★★★   → 中等
★★★★  → 困难
★★★★★ → 非常困难
```

没有星级或星级数量不在映射中时为：

```text
未知
```

标准 Query 枚举为：

```text
非常简单、简单、中等、困难、非常困难
```

`未知` 同样是可能存在的 metadata 值，但不会被 Classic 的标准难度词表自动抽取。

### `visibility`

`_enhance_metadata()` 根据分类是否属于 `internal_categories` 产生：

```python
"internal" if category in self.internal_categories else "public"
```

当前 `RAGConfig.internal_categories` 默认是：

```text
半成品
```

`RecipeRAGSystem.initialize_system()` 将逗号分隔的配置转为集合，再传给 `DataPreparationModule`。

因此默认菜谱配置下：

- `半成品` → `internal`
- 其他分类 → `public`

测试 `tests/test_permissions.py::test_internal_categories_get_internal_visibility()` 验证：

- 速冻水饺（半成品）为 `internal`。
- 番茄蛋汤（汤品）为 `public`。
- Child 会继承 Parent 的 `visibility`。

### 其他 metadata

项目还建立了：

- `dish_name`
- `modality`
- `doc_type`
- `parent_id`

它们也可在底层过滤表达式中使用。具体来源分别位于数据准备、Chunking 和图片摄取链路中，本篇不重复展开其生成算法。

## 三、1. 当前支持哪些 Metadata Filter

这个问题需要分三个层次回答，不能把“底层支持”和“Query 自动提取”混为一谈。

## 1.1 底层表达式白名单

- 文件：`rag_modules/vector_store.py`
- 常量：`FILTERABLE_FIELDS`

当前白名单是：

```python
{
    "category",
    "difficulty",
    "dish_name",
    "modality",
    "visibility",
    "doc_type",
    "parent_id",
}
```

`build_filter_expr()` 只接受这些字段。未知字段会抛出：

```text
ValueError: 不支持作为过滤条件的字段
```

这是输入安全边界，防止不受信任的字段名直接拼入 Milvus 表达式。

支持两种表达式形式：

```text
单值：field == "value"
多值：field in ["value1", "value2"]
```

多个字段之间使用：

```text
&&
```

即 AND 关系。

当前 Builder 不生成范围比较、NOT、OR、数值大小比较或嵌套逻辑。

## 1.2 Classic Query 自动提取

Classic 模式只从自然语言 Query 中自动提取：

```text
category
difficulty
```

它不会从自然语言中自动提取：

- `dish_name`
- `modality`
- `visibility`
- `doc_type`
- `parent_id`

其中 `visibility` 来自访问角色，不应由用户 Query 自己声明。

## 1.3 专用入口与 Agent Tool

其他字段进入检索的方式：

- `RecipeRAGSystem.retrieve_images()` 固定传入 `{"modality": "image"}`。
- Agent 的 `search_recipes` tool 支持 `category`、`difficulty`。
- Agent 的 `list_by_metadata` tool 支持 `category`、`difficulty`。
- Agent 的 `search_images` tool 固定使用 `modality=image`。
- `visibility` 始终由 role 对应的权限表达式产生。
- `dish_name`、`doc_type`、`parent_id` 可通过底层 `metadata_filtered_search(filters=...)` 编程调用，但 Classic 自然语言入口没有自动提取它们。

## 四、2. Query 中 Filter 如何被提取

## 2.1 Classic 模式

- 文件：`main.py`
- 类：`RecipeRAGSystem`
- 函数：`_extract_filters_from_query(query)`

源码采用确定性的子串匹配，不调用 LLM：

```python
filters = {}

for category in DataPreparationModule.get_supported_categories():
    if category in query:
        filters["category"] = category
        break

for difficulty in sorted(
    DataPreparationModule.get_supported_difficulties(),
    key=len,
    reverse=True,
):
    if difficulty in query:
        filters["difficulty"] = difficulty
        break
```

### 输入

```python
query: str
```

### 输出

```python
dict[str, str]
```

例如：

```python
_extract_filters_from_query("推荐几道简单的素菜")
```

产生：

```python
{
    "category": "素菜",
    "difficulty": "简单",
}
```

### 为什么难度按长度倒序

“非常简单”包含“简单”。如果先检查“简单”，Query 中的“非常简单”会被错误识别成“简单”。

因此源码先检查较长标签：

```text
非常简单 → 简单
非常困难 → 困难
```

### 这套提取的能力边界

它只能识别标准标签的原文子串。

例如：

```text
“新手菜” 不一定提取为 “非常简单”
“蔬菜类” 不一定提取为 “素菜”
“别太难” 不会自动转换为 difficulty 条件
```

它也只保留第一个命中的 category 和第一个命中的 difficulty，不支持一个 Query 同时提取多个分类。

### Classic 中使用原始问题还是 Rewrite 后问题

`RecipeRAGSystem._ask_question_inner()` 调用：

```python
self.retrieve(
    rewritten_query,
    filters=self._extract_filters_from_query(question),
    role=role,
)
```

因此：

- 检索文本使用 `rewritten_query`。
- metadata filter 从原始 `question` 提取。

这能避免 LLM rewrite 意外删掉“素菜”“简单”等显式约束。

如果外部直接调用 `RecipeRAGSystem.retrieve(query, filters=None)`，则函数内部会从传入的 `query` 自动提取。

如果调用者显式传入 `filters`，即使是空字典 `{}`，就不会再自动提取 Query filter。

## 2.2 Agent 模式

Agent 不是用 `_extract_filters_from_query()` 做子串匹配，而是让路由 LLM 在 tool arguments 中选择结构化字段。

- 文件：`rag_modules/agentic_rag.py`
- 函数：`build_agent_tools()`

`search_recipes` 和 `list_by_metadata` 的 schema 暴露：

```text
category enum
difficulty enum
```

执行时：

- `_search_recipes()` 清除空值后调用 `metadata_filtered_search()`。
- `_act_node()` 的 `list_by_metadata` 分支把非空 tool args 作为 filters。

这属于 Agent 模式的结构化 tool routing，不是 Classic 的字符串提取逻辑。

## 五、3. Visibility Filter 如何产生

Visibility 不是从 Query 里抽取的，而是从调用者的访问角色产生。

- 文件：`main.py`
- 常量：`ROLE_ALLOWED_VISIBILITY`

当前角色表：

```python
{
    "guest": ["public"],
    "user": ["public"],
    "staff": ["public", "internal"],
}
```

默认角色：

```python
DEFAULT_ROLE = "user"
```

生成函数：

- 文件：`main.py`
- 函数：`RecipeRAGSystem._visibility_expr_for_role(role)`

### `guest` / `user`

调用：

```python
build_filter_expr({"visibility": ["public"]})
```

产生：

```text
visibility in ["public"]
```

### `staff`

`staff` 同时允许 `public` 与 `internal`。源码认为已覆盖全部可见性值，所以返回：

```python
None
```

即无需额外 visibility filter。

### 未知角色

例如 `admin` 不在当前映射中，会直接抛出 `ValueError`，不会默认提升权限或静默降级。

测试：

- `tests/test_permissions.py::TestRoleVisibility`

验证了 guest/user 只看 public、staff 无需过滤、未知角色被拒绝。

### Visibility 如何与 Query Filter 合并

`RecipeRAGSystem.retrieve()` 将：

```text
active_filters       = Query / caller filters
visibility_expr      = role filter
```

一起传给：

```python
metadata_filtered_search(
    query,
    active_filters,
    top_k=limit,
    extra_expr=visibility_expr,
)
```

在 Milvus 路径中：

```python
combine_expr(
    build_filter_expr(filters),
    extra_expr,
)
```

将它们用 `&&` 合并。

## 六、4. Milvus 如何做 Filter Pushdown

## 4.1 Metadata 随 Child 一起写入 Milvus

- 文件：`rag_modules/vector_store.py`
- 类：`MilvusVectorStore`
- 函数：`_build_schema()`、`_rows_for_insert()`

Milvus collection 把以下 metadata 保存为 scalar fields：

- `parent_id`
- `revision_id`
- `doc_type`
- `category`
- `dish_name`
- `difficulty`
- `modality`
- `visibility`
- `source_path`
- `source`
- `source_hash`
- `chunking_version`
- `image_path`
- `file_type`
- `chunk_index`
- `chunk_size`

其中：

- `category` 被设为 partition key。
- `difficulty`、`visibility`、`modality` 显式建立 `INVERTED` index。

`dish_name`、`doc_type`、`parent_id` 虽属于过滤白名单，但当前 `_create_collection()` 没有为它们显式建立独立 inverted index。语义上仍可过滤，具体性能可能不同。

## 4.2 将安全字典转换成表达式

- 函数：`build_filter_expr(filters)`

例如：

```python
{
    "category": "素菜",
    "difficulty": "简单",
}
```

转换成：

```text
category == "素菜" && difficulty == "简单"
```

字符串值会通过 `_escape_literal()` 转义反斜杠和双引号；字段名必须在白名单内。

再与 visibility 合并：

```text
category == "素菜"
&& difficulty == "简单"
&& visibility in ["public"]
```

## 4.3 Expression 同时下推到 Dense 和 Sparse 请求

- 文件：`rag_modules/vector_store.py`
- 函数：`MilvusVectorStore.hybrid_search()`

源码把同一个 `expr` 挂到：

```python
dense_request = AnnSearchRequest(..., expr=expr)
sparse_request = AnnSearchRequest(..., expr=expr)
```

然后交给：

```python
client.hybrid_search(
    reqs=[dense_request, sparse_request],
    ranker=RRFRanker(60),
    limit=k,
)
```

所以执行语义是：

```text
先限定满足 category / difficulty / visibility 的 Child
→ Dense 在合法 Child 中取候选
→ BM25 在合法 Child 中取候选
→ 服务端 RRF
→ 返回 Top-K
```

源码注释特别说明：当前 `pymilvus 2.5` 的 `hybrid_search` 会忽略外层 `filter` 关键字，因此表达式必须附着在每个 `AnnSearchRequest` 上。

这不是装饰性写法，而是确保权限和 metadata 条件在两条检索通路都生效。

## 七、5. FAISS 为什么只能 Post-filter

### 源码事实

- 文件：`rag_modules/vector_store.py`
- 类：`FaissBackend`
- 类属性：`supports_server_side_hybrid = False`

`FaissBackend.similarity_search()` 如果收到 `expr`，只会记录 warning：

```python
logger.warning("FAISS 后端不支持表达式过滤，已忽略: %s", expr)
```

然后仍然调用：

```python
self.vectorstore.similarity_search(query, k=k)
```

当前 FAISS 索引保存的是向量与 docstore 映射，没有像 Milvus 那样建立可下推的 scalar schema、partition key 和 inverted metadata indexes。

同时，本地 BM25 也针对全体 `self.chunks` 建立，并非针对每次过滤条件临时构建。

因此当前实现只能：

```text
全库 Dense 召回
+ 全库 BM25 召回
→ 本地 RRF
→ Python 检查 Document.metadata
→ 丢弃不满足 filter 的结果
```

### 实际过滤代码

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`metadata_filtered_search()`

普通 filters 直接比较：

```python
actual = document.metadata.get(key)
actual == expected
```

列表值使用：

```python
actual in expected
```

`extra_expr`，例如 visibility，则由：

- 函数：`document_matches_expr()`

解析项目生成的受限表达式子集，目前支持：

```text
==
in [...]
&&
```

测试 `tests/test_permissions.py::test_hybrid_search_client_path_post_filters_visibility()` 验证 FAISS/client 路径会在融合后删除 `internal` Chunk。

## 八、6. 为什么不只是性能差异，还可能影响 Recall

假设全库 Hybrid 排名是：

```text
1～15：相关但不满足 “素菜 + 简单 + public” 的 Chunk
16：真正满足全部条件的目标 Chunk
```

如果 FAISS 只召回前 15 个再过滤：

```text
先取全库 Top-15
→ 过滤后全部被删除
→ 返回 0 条
```

目标 Chunk 排在全库第 16，根本没有进入 Python 过滤阶段。

Milvus pushdown 的逻辑则是：

```text
先留下满足 “素菜 + 简单 + public” 的集合
→ 目标 Chunk 在合法集合中重新排名
→ 有机会成为合法集合的 Top-1
```

因此两种方式的差异是：

```text
Post-filter：全库排名后截断，再过滤
Pushdown：过滤后的子集内排名，再截断
```

这会直接影响 Filtered Recall，并可能导致 FAISS 最终返回数量少于 `top_k`。

### 为什么扩大候选池也不能彻底解决

扩大到 15、50 或 100 只能降低漏检概率，不能提供严格保证。

只要满足条件的目标在全库排名中低于候选池边界，它仍然会被提前丢弃。

理论上召回全部 Chunk 后再过滤，可以避免这种候选截断问题，但那会使每次查询的 Dense、BM25、RRF、内存和延迟成本显著增大，失去 Top-K 检索的工程意义。

## 九、7. FAISS 为了补偿 Post-filter 如何扩大候选池

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`metadata_filtered_search()`

FAISS/client 路径计算：

```python
candidate_count = min(
    len(self.chunks),
    max(self.candidate_k, top_k * 5),
)
```

然后调用：

```python
candidates = self.hybrid_search(
    query,
    top_k=candidate_count,
    candidate_k=candidate_count,
)
```

这相当于先让 Hybrid Search 尽量返回一个更大的融合结果池，再逐条检查 metadata，直到收集到 `top_k` 条合法结果。

默认配置：

```text
self.candidate_k = 10
top_k = 3
```

于是外层计算：

```text
max(10, 3 × 5) = 15
```

如果知识库至少有 15 个 Child，则过滤查询会先获取 15 个融合候选，再选出最多 3 个合法 Child。

### 一个容易忽略的真实影响

默认角色是：

```text
user
```

`user` 总会产生：

```text
visibility in ["public"]
```

因此 `RecipeRAGSystem.retrieve()` 中：

```python
if active_filters or visibility_expr:
```

对默认 user 恒为真。

也就是说，FAISS 默认用户查询即使没有出现“素菜”“简单”等显式条件，也会为了权限过滤走 `metadata_filtered_search()`，默认外层候选池通常是 15，而不是普通 Hybrid 的 10。

`staff` 在没有 Query filter 时没有 visibility expression，因此会走普通 `hybrid_search()`，默认候选池为 10。

## 十、8. `candidate_count` 实际如何计算

项目中不是只有一个 `candidate_count` 公式，需要分场景。

## 8.1 普通 Hybrid Search

- 文件：`rag_modules/retrieval_optimization.py`
- 函数：`hybrid_search()`

先计算：

```python
pool_size = self._pool_size(top_k)
```

如果 reranker 未启用：

```text
pool_size = top_k
```

如果 reranker 启用：

```text
pool_size = max(top_k, reranker.pool_size)
```

再计算：

```python
candidate_count = max(
    pool_size,
    candidate_k or self.candidate_k,
)
```

默认 reranker 关闭、`top_k=3`、`self.candidate_k=10`：

```text
pool_size = 3
candidate_count = max(3, 10) = 10
```

## 8.2 FAISS Metadata Filtered Search

外层补偿池：

```python
filtered_candidate_count = min(
    len(self.chunks),
    max(self.candidate_k, top_k * 5),
)
```

默认 `top_k=3`：

```text
filtered_candidate_count
= min(total_chunks, max(10, 15))
= min(total_chunks, 15)
```

然后这个值同时作为内层：

```text
hybrid_search.top_k
hybrid_search.candidate_k
```

### 默认 reranker 关闭

如果总 Chunk 数不少于 15：

```text
Dense 取 15
BM25 取 15
RRF 最多返回 15
Post-filter 最多保留 3
```

### reranker 开启

默认 `rerank_pool=20`。外层虽然先算出 15，但进入 `hybrid_search(top_k=15)` 后：

```text
pool_size = max(15, 20) = 20
内部 candidate_count = max(20, 15) = 20
```

因此 Dense/BM25 实际可能各取 20，主 RRF 产生较大池，reranker 再返回 15 给外层 metadata post-filter。

所以不能脱离 reranker 状态，只看外层那一行就断言实际检索永远是 15。

## 8.3 Milvus Metadata Filtered Search

Milvus 路径：

```python
pool_size = self._pool_size(top_k)

self.vectorstore.hybrid_search(
    query,
    k=pool_size,
    expr=expr,
    candidate_k=max(pool_size, self.candidate_k),
)
```

`MilvusVectorStore.hybrid_search()` 内部再计算：

```python
limit = max(k, candidate_k or k)
```

默认 reranker 关闭：

```text
top_k = 3
pool_size / k = 3
candidate_k = max(3, 10) = 10
Dense request limit = 10
Sparse request limit = 10
Milvus hybrid final limit = 3
```

关键区别是：这 10 个 Dense/BM25 候选都从已经满足 `expr` 的合法集合中产生。

### 公式汇总

| 场景 | 默认参数下的候选行为 |
|---|---|
| 普通 Hybrid，reranker 关闭 | 每路 10 → final 3 |
| FAISS filtered，reranker 关闭 | 每路 15 → RRF 15 → post-filter final ≤3 |
| Milvus filtered，reranker 关闭 | 合法集合内每路 10 → server RRF final 3 |
| 开启默认 pool=20 的 reranker | 每路至少扩大到 20，再重排到目标 Top-K |

---

## 十一、9. 大 Candidate Pool 的收益和代价

## 收益

### 1. 提高 Post-filter 后的存活数量

候选池越大，越有机会包含满足 category、difficulty 和 visibility 的结果。

### 2. 提高 Filtered Recall

合法目标如果在全库排名第 12，候选池 10 会漏掉，候选池 15 有机会召回。

### 3. 给 RRF 更多交叉验证机会

某个 Child 可能在 Dense 第 8、BM25 第 7。候选池太小，它不会进入融合；扩大候选池后，双路命中可能使它上升。

### 4. 给 Reranker 足够候选

Cross-Encoder 只能重排已有候选。较大的池能提高 reranker 看到正确文档的概率。

## 代价

### 1. 检索与排序成本增加

- FAISS 需要返回更多近邻。
- 本地 BM25 需要选出更多结果。
- RRF 需要合并更多 Child。
- Milvus 需要处理更大的 Dense/Sparse request limit。

### 2. 内存与网络开销增加

更多 `Document`、metadata 和文本需要在组件之间传递。Milvus 模式还会增加服务端到应用端的候选返回量，尤其在需要本地 reranker 时。

### 3. Reranker 成本可能显著增加

如果启用 Cross-Encoder，候选池越大，需要计算的 Query-Document pair 越多，延迟增长通常比简单 RRF 更明显。

### 4. 噪声增加

更深的候选往往相关性更弱。虽然最终仍会过滤和截断，但噪声可能影响 RRF 或 reranker 的排序稳定性。

### 5. 不能提供严格 Recall 保证

候选池只是概率性补偿。合法目标只要仍在池外，就会丢失。

### 6. 生成 Token 成本不会必然同步增加

默认最终仍只返回 `top_k` Child，并映射到 Parent。因此扩大中间候选池主要增加检索和可选重排成本，不会自动把全部候选塞入 LLM Context。

不过候选池变化可能改变最终 Parent 的数量和排序，从而间接改变 Context 内容。

## 十二、“素菜 + 难度 + Visibility”具体示例

## 输入

```text
Query：推荐几道简单的素菜
role：user
top_k：3
backend：分别看 Milvus 与 FAISS
```

## 第一步：提取 Query Filter

- 文件：`main.py`
- 函数：`_extract_filters_from_query()`

得到：

```python
{
    "category": "素菜",
    "difficulty": "简单",
}
```

“简单”不会被误识别为“非常简单”；两者是精确 metadata 值，不是包含关系。

## 第二步：生成 Visibility Filter

- 文件：`main.py`
- 函数：`_visibility_expr_for_role("user")`

得到：

```text
visibility in ["public"]
```

## 第三步：组合表达式

Milvus 路径通过：

```python
combine_expr(
    build_filter_expr(filters),
    visibility_expr,
)
```

得到：

```text
category == "素菜"
&& difficulty == "简单"
&& visibility in ["public"]
```

## 示例候选

| Child | category | difficulty | visibility | 是否满足 |
|---|---|---|---|---|
| 清炒西兰花步骤 | 素菜 | 简单 | public | 是 |
| 拍黄瓜步骤 | 素菜 | 非常简单 | public | 否：难度不等于“简单” |
| 红烧肉步骤 | 荤菜 | 简单 | public | 否：分类不符 |
| 速冻水饺工艺 | 半成品 | 简单 | internal | 否：分类和可见性均不符 |

### 关于“internal 素菜”的源码边界

在默认数据准备规则下，`visibility` 完全由 `category in internal_categories` 决定，而默认 internal category 只有“半成品”。

所以当前默认语料中：

```text
category == "素菜"
```

通常已经意味着：

```text
visibility == "public"
```

因此这个具体默认示例里，visibility 条件可能不会进一步删除“素菜”结果。但系统仍然显式施加权限条件，因为：

- `internal_categories` 可由配置修改。
- 换领域配置后，分类与 visibility 关系可能变化。
- 不带 category 的普通查询仍必须阻止 user 看到内部文档。
- 权限约束不应该依赖调用者猜测当前语料分布。

## Milvus 执行

默认：

```text
合法集合 = 素菜 && 简单 && public
```

然后：

```text
Dense 在合法集合内取最多 10 个候选
BM25 在合法集合内取最多 10 个候选
Milvus RRF 返回 Top-3
```

“清炒西兰花”只需在合法集合内与其他“简单、公开、素菜”竞争。

## FAISS 执行

默认 user 一定走 filtered 路径：

```text
candidate_count = min(total_chunks, max(10, 3×5))
                = min(total_chunks, 15)
```

如果总 Chunk 数不少于 15：

```text
Dense 从全库取 15
BM25 从全库取 15
本地 RRF 生成最多 15 个融合候选
逐条检查 category == 素菜
逐条检查 difficulty == 简单
再检查 visibility in [public]
收集到 3 条或候选耗尽
```

如果全库前 15 大多是“简单荤菜”“非常简单素菜”或其他不满足条件的高相关 Chunk，过滤后可能只剩 0～2 条，即使库中实际还有符合条件但排在全库第 16 以后的 Child。

这就是 pushdown 与 post-filter 在 Recall 上的真实差异。

## 十三、设计优点与局限

## 优点

- Classic 的 filter 提取是确定性规则，不额外调用 LLM。
- 从原始问题提取 filter，避免 Query rewrite 丢失显式条件。
- Visibility 独立于用户 Query，由 role 强制产生。
- 未知 role 直接拒绝，不静默扩大权限。
- Milvus 将同一权限表达式同时下推到 Dense 和 Sparse 请求。
- Filter 字段采用白名单并转义字符串，降低表达式注入风险。
- FAISS 虽不能下推，但通过 `top_k * 5` 扩大候选池补偿 Recall。
- 测试覆盖 visibility 继承、角色范围、表达式生成与 post-filter。

## 局限

- Classic 只做精确子串匹配，无法理解“新手菜”“别太难”等隐式约束。
- 只提取一个 category 和一个 difficulty，不支持 OR 或多选自然语言条件。
- `未知`、`其他` 可能存在于 metadata，但不在标准自动提取枚举中。
- FAISS post-filter 无法保证 Filtered Recall，可能返回少于 `top_k`。
- FAISS 的补偿倍数 `5` 写死在代码中，不是配置项。
- `dish_name`、`doc_type`、`parent_id` 虽在过滤白名单中，却没有 Classic Query 自动提取入口。
- Milvus 只为部分字段显式建立 inverted index；其他白名单字段的过滤性能需要实际压测。
- 当前角色与 visibility 映射定义在 `main.py`，角色体系较简单。

## 十四、面试口述版本

> 这个项目把 metadata filtering 分成业务约束和权限约束两部分。Classic 模式用 `_extract_filters_from_query()` 从原始问题中做确定性子串匹配，目前只提取 category 和 difficulty；权限则由 `_visibility_expr_for_role()` 根据 guest、user、staff 角色强制产生，普通用户只能访问 public。两类条件最终在 `metadata_filtered_search()` 汇合。
>
> Milvus 模式会把 filter dict 转成白名单约束的布尔表达式，并把同一个 expr 同时挂到 Dense 和 Sparse `AnnSearchRequest` 上，所以是先过滤合法范围，再做双路召回和 RRF。FAISS 当前没有 scalar index 和表达式下推能力，只能先在全库做 Dense、BM25、RRF，再在 Python 里检查 Document metadata。
>
> 这不只是性能差异。Post-filter 的目标文档如果排在候选池之外，过滤器根本看不到它，所以会损失 Filtered Recall。项目用 `min(total_chunks, max(candidate_k, top_k*5))` 扩大 FAISS 候选池作为补偿。默认 top_k 是 3、candidate_k 是 10，因此普通 user 的过滤检索通常先取 15 个融合候选再过滤。但这只是降低漏检概率，不能像 Milvus pushdown 那样保证在合法子集内排名。

## 十五、源码事实边界

当前源码可以确认：

- 底层过滤白名单包含 7 个字段。
- Classic 自动 Query 提取只识别 category 和 difficulty。
- Classic 问答从原始 question 提取 filter，从 rewritten query 执行检索。
- guest/user 只允许 public，staff 允许 public 与 internal。
- Milvus 把 expr 同时附着到 Dense 和 Sparse 请求。
- FAISS 在 Hybrid 之后逐条检查 metadata。
- FAISS filtered candidate count 使用 `min(len(chunks), max(candidate_k, top_k*5))`。
- 默认 user 的 visibility expression 会让无显式 Query filter 的查询也进入 filtered 路径。

需要保留的边界：

- `FILTERABLE_FIELDS` 表示表达式层允许的字段，不表示 Classic 自然语言能自动提取全部字段。
- 当前默认数据准备把“素菜”设为 public；“素菜 + internal”不是默认语料自然产生的组合。
- 扩大候选池对 Recall 的实际提升，需要在当前语料的 filtered evaluation 上测量，源码只能确认补偿机制，不能证明具体提升幅度。
- Milvus 为未显式建立 inverted index 的白名单字段执行过滤时的性能，当前代码不足以确认，需要服务端 explain/benchmark。
