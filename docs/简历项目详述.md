## 一、检索链路优化（Retrieval Engineering）

### 1.1 混合检索架构

- **双路召回**：Dense（BAAI/bge-small-zh-v1.5，归一化向量，Milvus HNSW + COSINE）+ BM25（Milvus 服务端 BM25 Function + SPARSE_INVERTED_INDEX，jieba 分词器优先）；
- **RRF 融合**：`score(d) = Σ 1/(60 + rank_i(d))`，只比排名不比分数——Dense 是 COSINE 相似度、BM25 是另一套量纲，直接加权没有意义；
- **过滤下推**：权限与业务过滤表达式同时下推到 Dense/Sparse 两个 `AnnSearchRequest`，实现"先过滤后召回"（FAISS 后端无法下推，用 `min(全库, max(candidate_k, top_k*5))` 扩池后过滤补偿）；
- **实测**：73 条精确查询 Hit@5 100%、MRR 0.9315（多轮复现一致）。

### 1.2 Parent-Child 分块检索

- `MarkdownHeaderTextSplitter` 按 #/##/### 结构切分，`strip_headers=False` 保留标题语义；
- **子块定位检索、父文档回溯生成**：子块主题集中适合相似度匹配，父文档信息完整适合生成——子块命中后按 `parent_id` 取回整篇菜谱，同一菜谱多子块命中自动去重并按命中数排序；
- 已知代价（诚实记录）：整篇 parent 会扩大 Context，早期版本首篇超长会被字符级拦腰截断（后被 Context Manager 的 token 预算机制替代）。

### 1.3 精排：本地 Cross-Encoder + 云端 Rerank 双方案

- **本地**：BAAI/bge-reranker-base（CPU，约 1.1 亿参数），对候选池逐对 `(query, 文档)` 联合编码打分；打分序与召回序再做一次 RRF 二次融合；
- **云端**：阿里云百炼 qwen3-vl-rerank API（20 候选单次约 1s），超时重试 + 失败自动回退本地模型，环境变量一键切换策略；
- **关键实验结论（详见第六节实验 1/2/3）**：单独让 CE 定序会削弱 BM25 的精确菜名信号（MRR 0.931→0.879），二次融合可恢复部分（0.902）但仍不及基线；**盲段修复后**云端精排首次超过基线（0.896 vs 0.861）。

### 1.4 盲段修复（Title 注入，本项目最有代表性的优化）

- **问题定位**：检索子块平均仅 128 字符，菜名标题只落在每篇第一个子块——"制作步骤""小贴士"等后续片段自描述不完整，精排模型是"盲段"打分；
- **归因过程**：先发现"重排无增益"（原评测集 62% 的 query 字面包含期望菜名，BM25 白捡分）→ 补建 24 条模糊集（同义改写/错别字/间接描述/易混淆四类，期望菜名全部对着语料校验）→ 对照实验证明标准答案（同语料内容）faithfulness 0.93 / MRR 显著更高 → 锁定盲段为主因而非模型能力；
- **方案**：精排打分文本注入"菜名（分类）｜"前缀（等价于企业方案一的 title 注入）；
- **结果**：模糊集 MRR 0.767（本地 CE）→ 0.854（+8.7pp），0.854（qwen3 无注入）→ 0.896（+4.2pp，首超不重排基线 0.861）；精确集 keyword Recall 0.738 → 0.768（历史最优）；同时证明"本地小模型换云端强模型"在模糊场景差距达 0.08+ MRR。

## 二、Agentic RAG（编排层）

- **LangGraph 状态机**：`Router → Act → Reflect → Generate`，`recursion_limit=8` 防死循环；Router 用 OpenAI function calling 选择工具；
- **工具集**：`search_recipes`（带 category/difficulty 结构化过滤的混合检索）、`search_images`（图文检索）、`list_by_metadata`（浏览聚合）、`direct_answer`（无需检索的直答）；
- **三级降级链**（部分模块失败 ≠ 系统不可用）：
  1. 检索 0 命中 → LLM 改写查询重试一次（reflect 节点）；
  2. 工具执行异常 → 降级为纯混合检索；
  3. 检索完全不可用 → 规则化离线摘要（列出命中条目，不虚构）；
- **多轮指代消解（Query Contextualization）**：结合对话历史把"那第二种需要哪些食材"改写为含"红烧鱼头"的独立完整查询后再检索——多轮用例实测改写后命中目标菜品，这是多轮 RAG 的经典失败模式；
- **全链路可观测**：QueryTrace 以 `query_id` 贯穿 route/rewrite/retrieve/context/generate 各阶段事件，落 JSONL 可回放，API 提供 `/api/traces/{query_id}` 查询。

## 三、记忆与上下文管理（状态层）

### 3.1 统一 Context Manager

- **问题**：改造前对话历史被硬拼进 question（固定 4 轮 × 120 字符）、检索文档按字符顺序拼接、首篇超长被拦腰截断——三类来源（对话/检索/记忆）没有统一的预算与降级机制；
- **设计**：所有来源抽象为 `ContextItem`（content/source_type/priority/token 计数），`ContextManager` 按 token 预算分配：retrieval P1（整条保留/整条丢弃，首篇可部分保留兜底）→ conversation P2（可截断，最新轮次优先保留）→ memory P3（超限直接丢弃）；分配超限时按优先级确定性降级；
- **去重**：精确内容去重 + embedding 语义去重（cosine > 0.93 保留先到项）；
- **兼容性**：classic 链路零改动——生成函数只新增 `context_text` 旁路参数，classic 不传即行为不变（有单测锁定该行为）；
- **token 计数**：tiktoken（评测依赖已带入，零新增依赖）+ 中文长度降级估算；
- **A/B 实测（45 条 agent 臂）**：faithfulness 0.921→0.917、relevancy 0.849→0.852、correctness 0.685→0.690、context_precision 0.866→0.866——全部持平；context_recall 0.774→0.737（整篇丢弃 vs 字符部分保留的语义差异，如实记录）。**结论：质量不回退，且为记忆注入提供载体，属架构投资而非指标投资**。

### 3.2 会话持久化

- 改造前会话存 API 进程内存 dict（重启即失、多实例不可用）；
- 现由 `SessionStore` 协议的 SQLite 实现（WAL 模式 + 线程锁）持久化，保留最近 6 轮，函数签名不变、读写失败降级为无历史不影响主回答。

### 3.3 长期记忆（饮食偏好领域化）

- **记忆类型**：allergen 过敏原 / diet_preference 饮食方式 / taste_preference 口味偏好 / constraint 阶段性约束——每个记忆机制都有菜谱场景的天然对应物；
- **写入策略（Write Policy）**：LLM 抽取候选记忆后过滤——临时性表述（"今晚想吃面"）不写、importance/confidence < 0.6 不写、非法类型不写；
- **冲突更新（Supersede）**：同 (user_id, type, key) 的新记忆写入时旧记忆标记 superseded（"以前不吃辣"→"现在能吃微辣"）——key 按 prompt 规范约束（口味/饮食方式/当前约束为固定键，过敏原用名称），这是第一版评测暴露的 LLM key 不稳定问题；
- **时效（TTL + 衰减）**：阶段性约束带 expires_at（"最近在减脂"→7~30 天），检索时按 30 天半衰期指数衰减加权；
- **注入方式**：相关记忆作为 memory 类型 ContextItem 软注入（"用户对花生过敏，避免推荐含花生菜品"）；过敏原的 Milvus 硬过滤需要语料增加食材元数据并重建索引，如实标注为未来项；
- **隐私**：`GET/DELETE /api/memory` 列出/删除/清空当前用户记忆；敏感信息默认不自动写入由写入策略兜底；
- **存储选型**：SQLite（标准库、WAL）+ `MemoryStore`/`SessionStore` Protocol 抽象——迁移到英语平台项目（Gin + MySQL 栈）时新写 MySQLStore 即可，策略层零改动；
- **评测**：7 组多轮用例（指代消解/写入/生效/supersede/临时不写/跨会话/TTL）规则断言 + LLM 判分，**7/7 通过**。

## 四、多模态与权限（企业约束层）

### 4.1 多模态

- 视觉模型（deepseek-vision）为菜谱图片生成 caption，作为 `modality=image` 的子块入库，`parent_id` 指回所属菜谱——文本查询可通过语义向量检索到图片，回答时附带图片路径；
- agent 的 `search_images` 工具 + 生成上下文的【相关图片】区块，构成完整的 text-to-image 检索回答链。

### 4.2 权限

- **角色模型**：guest/user → 仅 public；staff → public + internal；未知角色直接拒绝不静默降级；
- **实现**：权限表达式与业务过滤合并后同时下推双路检索请求，先过滤后召回——对比 FAISS 后端只能召回后过滤（合法目标排在候选池外即漏检，需扩池补偿且无保证）；
- **安全细节**：过滤字段白名单 + 值转义防表达式注入；角色以 JWT 为准、请求体不可越权；
- **评测**：5 类越权查询零泄漏（权限隔离用例通过率 100%）。

## 五、评测体系（质量闭环）

### 5.1 数据资产

| 数据集 | 规模 | 用途 |
|---|---|---|
| golden_set.json | 73 条 × 5 类 intent（detail/browse/keyword/permission×2） | 检索层回归基线 |
| golden_set_fuzzy.json | 24 条 × 4 类难度（同义/错字/间接/混淆） | 模糊场景专项，期望菜名全部经语料校验 |
| reference_answers.json | 45 条标准答案 | RAGAS 参考类指标（LLM 合成 + 人工审核） |
| multi_turn_eval.json | 7 组多轮对话 | 记忆/指代消解行为断言 |

### 5.2 分层指标（每层用对工具）

- **检索层**：Hit@k / MRR / Recall——确定性指标，无 LLM 参与，可高频回归；
- **生成层**：RAGAS faithfulness / answer_relevancy / context_precision / context_recall / answer_correctness——LLM-as-judge（judge=DeepSeek，embeddings 复用业务 bge 模型）；
- **记忆层**：规则断言（store 状态）+ LLM 判分（约束遵守）。

### 5.3 工程化

- 一条命令全量流水线：`run_full_eval.py`（检索评测 → RAGAS 评测 → 合成 markdown 总报告）；
- 逐 case 归因：`compare_eval.py` 并排对照 + 差异 query 定位——项目里每个优化结论都来自逐条差异而非均分；
- 产物格式统一（`{"summary", "records"}` envelope + UTC 时间戳命名），跨轮次可比。

### 5.4 接入 RAGAS 的兼容性工程（踩坑实录，面试可讲）

1. ragas 0.4.3 导入期无条件引用 langchain-community 已移除的 VertexAI 模块 → 导入前注入占位模块（shim）；
2. collections 指标拒绝 Langchain 包装 embeddings（要求 modern 接口）→ 改用 ragas 原生 HuggingFaceEmbeddings 离线加载业务同款 bge；
3. judge 输出截断：llm_factory 默认 max_tokens=1024，中文 claim 拆解 JSON 很占 token → 提至模型上限 8192；并发下仍偶发截断 → 逐指标自动重试，失败率从 ~1.4% 降到 0（均值剔除 + 报告标注剩余）；
4. **env 默认值与字段默认值不一致的配置 bug**：grounding 开关字段默认 True、env 默认 false，导致一轮 A/B 静默关闭了忠实性约束——逐 case 归因（context 逐字节相同、答案风格突变）才暴露。这类"字段默认值与 env 默认值漂移"与 Milvus `RRFRanker(60)` 写死同类，是配置治理的真实教训。

## 七、高频追问预案（面试弹药）

**Q: 为什么用 RRF 而不是把两路分数加权相加？**
两路分数方向与量纲都不同（L2 距离越小越好 vs BM25 越大越好，且受 query 长度/词稀有度影响），加权需要归一化校准且换模型后要重调。RRF 只用排名，天然免校准；代价是丢弃分数差距信息——实测在本语料够用。

**Q: 为什么纯 CE 重排反而掉分？**
基线 Hit@5 已 100%、MRR 0.93，提升空间小；且评测集大量"菜名怎么做"式精确查询，CE 的语义偏好会把"红烧草鱼"这类语义近邻提到正确菜名之前。后来证明其中一部分其实是盲段问题（CE 看不到菜名），title 注入后云端精排在模糊场景才真正赢。

**Q: 盲段问题是怎么发现的？**
先发现"重排无增益"→ 质疑评测集分布 → 统计出 62% query 字面含菜名 → 补四类模糊集 → 对照实验（标准答案 vs 系统答案）分离出检索与生成的贡献 → 读 prompt 源码确认 step_by_step 模板要求"大概所需时间"（语料没有的信息）→ title 注入验证。

**Q: Context Manager 到底提高了什么？（诚实回答）**
生成质量指标持平——它不是指标投资而是架构投资：把三类上下文来源从"字符串拼接"升级为"有预算、有优先级、有确定性降级的管道"，是记忆注入的前置载体；同时 trace 里有了 input/dropped/final tokens，上下文变得可观测。附带收益：answer_correctness +1pp、context_precision +3pp。

**Q: 记忆怎么防止越记越乱？**
四道闸：抽取时 LLM 判 temporary（一次性需求不写）→ 写入策略双阈值（importance/confidence ≥0.6）→ 同 key 冲突 supersede（旧记忆不删除可审计）→ TTL 过期 + 检索 recency 衰减。且有 7 组行为用例锁定这些策略不回归。

**Q: 为什么记忆不用向量库、会话不用 Redis？**
记忆量级是每用户个位数条，SQLite 条件查询 + recency 排序足够；面试考点在策略层而非存储层。Store 是 Protocol 抽象，迁移到公司 MySQL/Redis 栈时只换实现。

**Q: 上线还差什么？（诚实清单）**
人工抽查校准 judge 分数（当前 judge 与生成同源，可能有同源偏好）；无答案 query 的优雅降级评测（框架暂不支持）；多实例部署的存储升级；真实流量灰度。

**Q: 这个项目和你另一个 AI 编程助手项目的记忆系统有什么区别？**
编程助手是"JSONL 分级加载的自动记忆提取"（单用户、文件级）；本项目是"策略化记忆"——写入有门槛、更新有冲突裁决、生命周期有 TTL/衰减、有隐私端点、有多轮行为评测。两个项目合起来展示的是记忆系统的方法论，不是同一实现的复制。

## 八、简历版本（三档）

### 完整版（5 条，定稿）

**项目简介**：面向菜谱知识库的 Agentic RAG 问答系统，覆盖 Parent-Child 结构化分块、混合检索与精排、LangGraph Agent 编排、上下文与记忆管理、图文多模态检索、权限控制与服务化，全程以自建评测集 + RAGAS 的单变量 A/B 实验驱动迭代。

**技术栈**：Python、LangGraph、Milvus、BM25、Dense Retrieval、RRF、Reranker、RAGAS、FastAPI

**技术亮点**：

1. **混合检索与精排**：构建 Milvus Dense+BM25 双路召回与 RRF 融合、Parent-Child 分块（子块检索、父文档回溯生成）；实现本地 Cross-Encoder/云端 Reranker 可插拔精排并 A/B 验证，针对子块不含菜名标题的"盲段"打分失准问题设计精排文本标题注入，24 条模糊查询集 MRR 0.854→0.896（首超不精排基线）。
2. **Agent 编排**：基于 LangGraph 构建"路由→工具调用→反思→生成"状态机，function calling 选择检索/聚合/直答等 4 类工具；设计三级降级链：0 命中自动查询改写重试、工具异常降级纯混合检索、检索不可用输出不虚构的离线摘要。
3. **上下文与记忆管理**：统一 Context Manager 按 token 预算与优先级（检索>对话>记忆）及精确/语义去重管理三类上下文，A/B 验证生成质量不回退；SQLite 持久化会话与长期记忆，设计写入门槛、同键冲突 supersede、TTL 过期与时间衰减策略，7 组多轮用例（含指代消解、跨会话记忆）7/7 通过。
4. **多模态、权限与服务化**：视觉模型生成菜谱图片语义描述入库，实现文本-图片统一检索与回答附图；JWT 三级角色权限过滤下推双路检索请求（先过滤后召回），5 类越权查询零泄漏；FastAPI 提供 SSE 流式统一问答 API。
5. **量化评测**：自建 73 条×5 类意图 golden set、24 条模糊集与 45 条标准答案，检索层确定性指标+生成层 RAGAS 分层评测，6 轮单变量 A/B 驱动全部优化决策；全量检索 Hit@5 100%、MRR@5 0.9315，生成忠实性硬约束使 Faithfulness 0.650→0.950。

> 顺序即叙事：地基 → 编排 → 状态 → 约束 → 度量。
