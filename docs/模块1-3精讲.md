## 1.3 `_stable_id`：全项目最重要的 10 行代码

```python
@staticmethod
def _stable_id(namespace: str, *parts: str) -> str:
    payload = "\0".join((namespace, *parts)).encode("utf-8")   # ① 用 \0（不可能出现在文本里）拼接
    return hashlib.sha256(payload).hexdigest()                  # ② 64位十六进制
```

**为什么这 10 行是地基**：
- `parent_id = _stable_id("parent", "dishes/soup/番茄蛋汤.md")` —— 同一文件永远同 ID；
- `revision_id = _stable_id("revision", path, content_hash)` —— 内容变一个字，修订 ID 变；
- `chunk_id = _stable_id("chunk", parent_id, revision_id, "3", content)` —— 块位置+内容全绑。
- **▶ 收益链**：ID 稳定 → Milvus 主键稳定 → 指纹校验/缓存/未来增量更新全部可行。
- **▶ `namespace` 前缀防碰撞**：同样是 "abc" 这个字符串，作为 parent 和作为 chunk 必须得到不同 ID。
- **▶ 用相对路径而非绝对路径**：语料挪盘 ID 不变。

## 1.7 `get_parent_documents`：检索后的回溯排序

```python
def get_parent_documents(self, child_chunks: list[Document]) -> list[Document]:
    relevance: dict[str, int] = {}      # parent_id → 命中子块数
    first_seen: dict[str, int] = {}     # parent_id → 第一次出现的位置

    for position, chunk in enumerate(child_chunks):
        parent_id = chunk.metadata.get("parent_id")
        if not parent_id or parent_id not in self._parent_documents:
            continue                     # ① 脏数据防御：跳过而非崩溃
        relevance[parent_id] = relevance.get(parent_id, 0) + 1
        first_seen.setdefault(parent_id, position)   # ② 记录首现位置做稳定排序的平局裁决

    ranked_ids = sorted(
        relevance,
        key=lambda parent_id: (-relevance[parent_id], first_seen[parent_id]),
    )                                    # ▶ ③ 主键=命中块数(降序)，平局=先出现者在前（稳定）
    return [self._parent_documents[pid] for pid in ranked_ids]
```

- **▶ ③ 排序语义**："一篇菜谱被 5 个子块命中"比"被 1 个子块命中"更相关——这是免费的相关性信号。
  平局用 first_seen 保证**结果顺序确定**（同样输入永远同样输出，评测才可复现）。

**本模块知识点回顾**：确定性哈希 ID / 状态可重置的类设计 / 防御性遍历 / 元数据三级提取 /
父子块继承 / 稳定排序。**一句话总结**：数据准备的目标是"**同样的语料，永远产出同样的结构化数据**"。

# 模块二：vector_store.py（向量存储）

**解决什么**：把 Document 存进 Milvus 并提供"混合检索 + 表达式过滤"；抽象接口把 FAISS 包成降级后端。

## 2.1 模块级常量：schema 的"设计图纸"

```python
SCALAR_FIELDS: dict[str, int] = {       # 字段名 → VARCHAR 最大长度
    "content": 16384,                    # ① 正文（最长，带 BM25 分词器）
    "parent_id": 64, "revision_id": 64,  # ② sha256 hex 恰好64字符，长度精确卡位
    "dish_name": 128, ...
}
INT_FIELDS = ("chunk_index", "chunk_size")
FILTERABLE_FIELDS = frozenset(           # ▶ 过滤白名单——安全核心
    {"category","difficulty","dish_name","modality","visibility","doc_type","parent_id"})
```

- **▶ ② 长度不是拍脑袋**：max_length 是字符数，sha256 hex=64，卡死 64 既省空间又是隐式约束
  （ID 格式错了插入直接失败，bug 当场暴露）。
- **▶ frozenset 不可变**：安全常量不许运行时被篡改。
- 不在白名单的字段（source 等）可存可返回，但**不能作为过滤条件**——最小权限。

## 2.2 `build_filter_expr`：表达式注入的三层防线（逐行）

```python
def build_filter_expr(filters):
    if not filters: return None                        # ① None=无过滤（调用方必须处理）
    clauses = []
    for key, expected in filters.items():
        if key not in FILTERABLE_FIELDS:               # ▶ 防线1：字段白名单，不在即抛错
            raise ValueError(f"不支持作为过滤条件的字段: {key!r}")
        if expected is None or expected == "": continue # ② 空值条件跳过不报错
        if isinstance(expected, (list, tuple, set)):   # ③ 列表值 → in 子句
            values = [v for v in expected if v not in (None, "")]
            if not values: continue
            literals = ", ".join(_escape_literal(str(v)) for v in values)
            clauses.append(f"{key} in [{literals}]")   #    → visibility in ["public"]
        else:
            clauses.append(f"{key} == {_escape_literal(str(expected))}")  # ④ 单值 → ==
    return " && ".join(clauses) if clauses else None   # ⑤ AND 连接；全空返回 None

def _escape_literal(value):
    escaped = value.replace("\\", "\\\\").replace('"', '\\"')  # ▶ 防线2：先反斜杠后引号，顺序不能反
    return f'"{escaped}"'
```

- **▶ 防线3：结构固定**——只产出 `k == v` / `k in [...]` 两种形态。即使值里藏恶意字符，
  它也只能是个"奇怪的字符串值"，变不成新语法。三层合起来：白名单管字段、转义管值、结构管语法。
- **手算一遍**：`{"category":"荤菜","visibility":["public","internal"]}`
  → `'category == "荤菜" && visibility in ["public", "internal"]'`

## 2.3 后端抽象与 FAISS 适配器

```python
class VectorStoreBackend(ABC):
    supports_server_side_hybrid: bool = False       # ▶ 能力标志，代替 isinstance 判断
    @abstractmethod
    def similarity_search(self, query, k=5, *, expr=None): ...
    @abstractmethod
    def hybrid_search(self, query, k=5, *, expr=None, candidate_k=None): ...

class FaissBackend(VectorStoreBackend):
    supports_server_side_hybrid = False
    def similarity_search(self, query, k=5, *, expr=None):
        if expr:
            logger.warning("FAISS 后端不支持表达式过滤，已忽略: %s", expr)  # ▶ 降级必须大声警告
        return self.vectorstore.similarity_search(query, k=k)
```

- **▶ 能力标志的意义**：检索层用 `if backend.supports_server_side_hybrid` 分路，
  将来加 Qdrant 后端不用改任何判断（开闭原则）；`isinstance` 链会越长越长。
- **▶ "静默忽略"是错的，"警告+忽略"是可以的**：功能上 FAISS 确实做不了，
  但必须让用户在日志里看到自己跑在降级路径上。

## 2.7 `build_index`：指纹复用主流程

```python
def build_index(self, chunks, *, force_rebuild=False) -> bool:
    if not chunks: raise ValueError("文档块列表不能为空")
    self._validate_chunks(chunks)                    # ① ID唯一性 + content长度<=16384
    client = self.connect()
    fingerprint = IndexConstructionModule._corpus_fingerprint(chunks)  # ② 语料指纹
    if not force_rebuild and self._collection_is_current(client, chunks, fingerprint):
        return False                                  # ▶ 复用：返回False=没重建
    if client.has_collection(self.collection_name):
        client.drop_collection(...)                   # ③ 指纹不匹配 → 全量重建策略
    self._create_collection(client)
    total = 0
    for start in range(0, len(chunks), INSERT_BATCH_SIZE):        # ④ 64条/批
        batch = chunks[start:start+INSERT_BATCH_SIZE]
        vectors = self.embeddings.embed_documents([c.page_content for c in batch])
        result = client.insert(collection_name=..., data=self._rows_for_insert(batch, vectors))
        total += int(getattr(result, "insert_count", len(batch)))
    client.flush(self.collection_name)
    if total != len(chunks): raise ValueError(...)    # ▶ 写入数必须精确等于chunk数
    self._write_manifest(chunks, fingerprint)         # ▶ 全部成功后才写凭证
    return True
```

- **▶ 凭证后写**：manifest 说"这份索引=这个指纹"，只有数据完整落库后才允许写——
  顺序反了会在崩溃后留下"凭证说好但数据缺"的假象。
- ④ 批量 embedding：1758 篇一次性向量化会生成巨大张量，分批是内存/吞吐折中。

```python
if (manifest.get("corpus_fingerprint") != fingerprint # ④ 指纹匹配
    or int(manifest.get("chunk_count", -1)) != len(chunks)
    or manifest.get("collection") != self.collection_name):
    return False
if self.count() != len(chunks): return False          # ⑤ 库里实际行数也对得上
return True
```

## 2.9 `hybrid_search`：两路召回 + 服务端融合（含著名大坑）

```python
def hybrid_search(self, query, k=5, *, expr=None, candidate_k=None):
    limit = max(k, candidate_k or k)
    vector = self.embeddings.embed_query(query)       # ① dense 路：查询向量化
    dense_request = AnnSearchRequest(
        data=[vector], anns_field="vector",
        param={"metric_type": self.metric_type}, limit=limit,
        expr=expr)                                    # ▶ ② 表达式挂请求上！
    sparse_request = AnnSearchRequest(
        data=[query],                                 # ▶ ③ sparse 路 data 是原文！
        anns_field="sparse", param={"metric_type": "BM25"}, limit=limit, expr=expr)
    results = client.hybrid_search(
        reqs=[dense_request, sparse_request],
        ranker=RRFRanker(60),                         # ④ 服务端 RRF，k=60
        limit=k,                                      # ⑤ 融合后截到 k
        output_fields=self._output_fields())
    hits = results[0] if results else []
    documents = [self._to_document(hit) for hit in hits]
    for d in documents:
        d.metadata["rrf_score"] = d.metadata.pop("distance")   # ⑥ 改名透出真实语义
```

- **▶ ② 本项目最著名的坑**：`client.hybrid_search(filter=expr)` 的 filter kwarg 被 pymilvus 2.5
  **静默忽略**——不报错、不过滤，权限形同虚设。对照实验定位后改为挂在每个 AnnSearchRequest.expr。
  **教训：安全相关的行为必须有实验/测试验证，不能信文档。**
- **▶ ③ 易误解**：sparse 路发原文而非向量——BM25 的分词打分全在服务端，客户端只说"查这句话"。
- ⑥ `distance` 在 RRF 语境下实为融合分，改名 `rrf_score` 免得下游瞎猜——**字段名是接口**。

**本模块一句话**：任何时刻磁盘上的索引都能证明自己对应哪份语料；任何过滤都在数据库层强制执行。

**解决什么**：把"向量库的原始能力"编排成业务可用的检索——双路召回、RRF 融合、过滤的两条执行路径、可选精排。

## 3.1 `tokenize_chinese`：无词典中文分词（客户端 BM25 用）

```python
def tokenize_chinese(text: str) -> list[str]:
    normalized = text.casefold()                        # ① 统一小写（查询和文档同规则）
    tokens = re.findall(r"[a-z0-9]+", normalized)       # ② 英文数字串整词
    for sequence in re.findall(r"[㐀-䶿一-鿿]+", normalized):  # ③ CJK连续段
        tokens.extend(sequence)                         # ④ 单字：红烧→红,烧（保召回）
        tokens.extend(sequence[i:i+2] for i in range(len(sequence)-1))  # ⑤ 二元组：红烧,烧肉（主力）
        if len(sequence) <= 8:
            tokens.append(sequence)                     # ⑥ 短语整词：精确菜名匹配
    return tokens
```

- **▶ 为什么三层粒度**：BM25 把 token 当精确匹配的原子——
  只有单字 → "红烧"和"烧红"分不开（区分度低）；只有词 → "红烧肉"切不出就没法命中；
  单字保召回、二元组保区分、短整词保精确菜名。无词典方案，效果损失可接受、零依赖。
- ③ 的 Unicode 范围覆盖 CJK 扩展A（㐀-䶿）+ 基本区（一-鿿）。

## 3.2 `__init__` + `_pool_size` + `_apply_rerank`：编排的三个旋钮

```python
def __init__(self, vectorstore, chunks, *, candidate_k=10, rrf_k=60, reranker=None):
    if not chunks: raise ValueError("文档块列表不能为空")
    if candidate_k < 1 or rrf_k < 1: raise ValueError(...)   # ① 参数校验前置
    self.vectorstore = vectorstore
    self.chunks = chunks                                      # ② chunks 留着：客户端路径建BM25要用
    self.candidate_k = candidate_k                            # ③ 每路召回量
    self.rrf_k = rrf_k                                        # ④ RRF常数
    self.reranker = reranker                                  # ⑤ 可选精排器（None=关闭）
    self.server_side_hybrid = getattr(vectorstore, "supports_server_side_hybrid", False)
    #            ▶ ⑥ getattr+默认值：旧FAISS对象/测试fake没有该属性也能工作（鸭子类型的宽容）
    self.bm25_retriever = None
    self.setup_retrievers()                                   # ⑦ 服务端路径跳过本地BM25（省内存省时间）

def _pool_size(self, top_k):
    if self.reranker is not None and getattr(self.reranker, "enabled", True):
        return max(top_k, getattr(self.reranker, "pool_size", 20))  # ▶ 精排需要更大候选池
    return top_k

def _apply_rerank(self, query, documents, top_k):
    if self.reranker is None or not documents:
        return documents[:top_k]                              # ① 无精排：直接截断
    reranked = self.reranker.rerank(query, documents)         # ② cross-encoder 重排序
    recall_rank = {id(doc): rank for rank, doc in enumerate(documents, start=1)}  # ③ 召回侧排名
    def fused_score(document, ce_rank):
        return 1.0/(self.rrf_k + ce_rank) + 1.0/(self.rrf_k + recall_rank[id(document)])
    #            ▶ ④ CE序与召回序再做一次RRF：不让CE独裁（实验证明纯CE在本语料掉点）
    fused = sorted(enumerate(reranked, start=1),
                   key=lambda pair: -fused_score(pair[1], pair[0]))
    return [doc for _, doc in fused][:top_k]
```

- **▶ ③ 用 id(doc) 做字典键**：Document 默认不可哈希的场合下，同一对象列表内用 id() 定位排名最稳。
- **▶ ④ 二次融合的设计依据**：评测三组数字（基线0.931/融合0.902/纯CE0.879）表明
  CE 语义分和 BM25 精确名信号各有盲区，融合比独裁好——**代码里每行"奇怪"的逻辑都该有评测背书**。

## 3.3 `hybrid_search`：两条路径的分水岭

```python
def hybrid_search(self, query, top_k=3, *, candidate_k=None, expr=None):
    if top_k < 1: return []
    pool_size = self._pool_size(top_k)                    # ① 精排开→池=20；否则=top_k
    candidate_count = max(pool_size, candidate_k or self.candidate_k)
    if self.server_side_hybrid:                           # ▶ ② 路径A：Milvus服务端全包
        pool = self.vectorstore.hybrid_search(
            query, k=pool_size, expr=expr, candidate_k=candidate_count)
        return self._apply_rerank(query, pool, top_k)

    assert self.bm25_retriever is not None                # ③ 路径B：FAISS客户端编排
    vector_docs = self.vectorstore.similarity_search(query, k=candidate_count)  # ④ dense路
    previous_k = self.bm25_retriever.k                    # ⑤ 临时改BM25的k取回候选量
    self.bm25_retriever.k = candidate_count
    try:
        bm25_docs = self.bm25_retriever.invoke(query)     # ⑥ sparse路
    finally:
        self.bm25_retriever.k = previous_k                # ▶ ⑦ finally恢复：异常也不能留下脏状态
    fused = self._rrf_rerank(vector_docs, bm25_docs, self.rrf_k)   # ⑧ 客户端RRF
    if expr:
        fused = [d for d in fused if document_matches_expr(d, expr)]  # ⑨ 后过滤（见3.5）
    return self._apply_rerank(query, fused, top_k)
```

- **▶ ⑦ try/finally 恢复共享状态**：bm25_retriever 是实例级共享对象，改了 k 不还回去，
  下一次调用就用错配置——"改共享状态必须 finally 恢复"是并发/复用安全的常识。
- ⑨ 后过滤的代价：过滤掉的不合格结果无法补充（top-N 已定）——这就是 pre-filter 更优的原因
  （但 FAISS 做不到，抽象的意义就是两条路径对上层透明）。

## 3.4 `_rrf_rerank`：RRF 的完整实现（逐行）

```python
@staticmethod
def _document_id(document):                      # 块的身份：优先确定性ID，退化到内容哈希
    if chunk_id := document.metadata.get("chunk_id"):
        return str(chunk_id)
    payload = " ".join((source_path, chunk_index, page_content))   # 兜底：测试fake可能没ID
    return hashlib.sha256(payload.encode()).hexdigest()

def _rrf_rerank(self, vector_docs, bm25_docs, k=60):
    scores: dict[str, float] = {}                 # ① chunk_id → 累计分
    documents: dict[str, Document] = {}           # ② chunk_id → 文档（去重容器）
    for result_set in (vector_docs, bm25_docs):   # ③ 两路一视同仁
        for rank, document in enumerate(result_set, start=1):
            did = self._document_id(document)
            documents.setdefault(did, document)   # ④ 首见保留（dense优先的隐式偏好）
            scores[did] = scores.get(did, 0.0) + 1.0/(k + rank)   # ▶ ⑤ RRF核心：按名次加分
    ranked = sorted(scores, key=scores.get, reverse=True)
    result = []
    for did in ranked:
        original = documents[did]
        result.append(Document(
            page_content=original.page_content,
            metadata={**original.metadata, "rrf_score": scores[did]},  # ⑥ 产出新Document不污染输入
        ))
    return result
```

- **▶ ⑤ 公式直觉**：第1名得1/61，第2名1/62，第61名1/121……排名越靠前加分越多但差距平滑
  （不会像原始分那样一个离群高分独大）。两路都排第1 = 2/61 ≈ 0.0328，断层领先。
- **▶ ⑥ 不可变性**：给 metadata 加分时用 `{**old, "rrf_score": ...}` 造新 dict、新 Document，
  不修改传入对象——调用方（比如同时拿 dense 结果做别的事）不会被意外污染。
- **手算**：文档A在dense第1、bm25没进榜；文档B两路都第2 → A=0.0164，B=0.0323，B胜——
  **两路一致看好 > 单路冠军**，这就是 RRF 的哲学。

## 3.5 `document_matches_expr`：客户端表达式求值器（为自产语法而写）

```python
_EXPR_CLAUSE = re.compile(r"^(\w+)\s*(==|in)\s*(.+)$")     # 只匹配我们生成的两种子句形态
_EXPR_LIST  = re.compile(r"^\[(.*)\]$")
_EXPR_LITERAL = re.compile(r'^"((?:[^"\]|\.)*)"$')
_EXPR_LITERAL_SCAN = re.compile(r'"((?:[^"\]|\.)*)"')   # 扫描用（无锚点，finditer可多次命中）

def document_matches_expr(document, expr) -> bool:
    for clause in expr.split("&&"):               # ① 只按 && 切（我们从不生成 ||）
        clause = clause.strip()
        if not clause: continue
        match = _EXPR_CLAUSE.match(clause)
        if not match:
            logger.warning("无法解析过滤表达式子句，忽略: %r", clause)  # ② 解析不了的子句放行
            continue
        key, operator, raw_value = match.groups()
        actual = document.metadata.get(key)
        if operator == "==":
            literal = _EXPR_LITERAL.match(raw_value.strip())
            if not literal or actual != _unescape(literal.group(1)):
                return False                       # ③ 一个条件不满足即整条不匹配
        else:                                      # in
            list_match = _EXPR_LIST.match(raw_value.strip())
            values = [_unescape(m.group(1)) for m in _EXPR_LITERAL_SCAN.finditer(list_match.group(1))]
            if actual not in values:
                return False
    return True
```

- **▶ 为什么敢这么简陋**：这个求值器**只求值我们自己生成的表达式**（build_filter_expr 的产物），
  语法闭环、无需完整 SQL 解析器。"自产自销"是控制复杂度的合法手段——前提是别暴露给外部输入。
- ② 解析不了的子句选择**放行**（保守的是"多返回"，调用方还有上层约束）而非误杀。
- 踩坑提示：`_EXPR_LITERAL` 带 `^$` 锚点做单值匹配；列表扫描必须用**无锚点**版本 finditer
  ——用错版本会导致 in 子句永远匹配失败（真实踩过）。

**本模块一句话**：编排层把"能用的检索原语"组合成"业务要的检索语义"，两条路径对上层透明，每个旋钮可关可调。
